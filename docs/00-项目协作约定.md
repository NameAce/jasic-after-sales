# 佳士售后系统 - 通用项目协作约定

> 本文档用于固化项目后续协作中的通用规则，包括架构边界、技术栈约束、实现原则、注释规范、状态同步和风险沟通方式。
> 本文档不再绑定任何具体需求文档、实施清单或原型文档。每轮开发需要参考哪些业务文档，由当轮任务明确指定。

---

## 1. 文档定位

- 本文档是项目级通用协作约定，适用于需求讨论、方案设计、代码实现、数据库调整、前后端联调和验收同步。
- 本文档只约束通用规则，不替代具体业务方案、接口设计、数据库设计、页面原型或专项开发文档。
- 当轮任务如指定专项文档、实施方案或验收清单，以当轮明确指定的文档作为业务基线。
- 如果当轮没有指定业务文档，应先基于当前代码和用户描述确认范围，不主动套用旧文档口径。
- 如果发现当前任务涉及的历史文档、代码实现和用户最新口径冲突，应先说明冲突和建议，不直接按旧文档落地。

## 2. 优先级规则

默认优先级如下：

1. 用户在当前对话中明确确认的规则、范围和结论。
2. 当轮明确指定的实施方案、设计文档或验收清单。
3. 当前代码中已经稳定运行的架构边界、接口契约和数据模型。
4. 本文档中的通用协作和技术约定。
5. 旧需求文档、旧原型或历史实施记录。

说明：

- 旧文档只作为理解历史背景的辅助材料，不自动作为当前业务基线。
- 页面原型只作为交互和展示参考，不直接覆盖已确认业务规则。
- 如果需要从旧文档恢复某个口径，必须在当轮任务中明确说明。

## 3. 项目架构基线

### 3.1 架构模式

- 项目采用 Maven 多模块单体架构，不默认拆微服务。
- 默认保持现有模块边界：
  - `jasic-common`：基础常量、枚举、异常、公共能力。
  - `jasic-framework`：安全、数据权限、AOP、Web 基础设施。
  - `jasic-system`：系统管理与 B 端核心业务。
  - `jasic-customer`：C 端客户业务。
  - `jasic-admin`：启动、配置、Mapper XML 和运行入口。
  - `jasic-ui-antd`： PC 管理后台。
  - `mp/aftersale`：小程序端代码。

### 3.2 技术栈约束

- 后端：Java 8、Spring Boot 2.7.x。
- ORM：MyBatis-Plus 3.5.x。
- 认证鉴权：Sa-Token。
- 缓存：Redis / Redisson。
- 数据库：MySQL 8.0、InnoDB、`utf8mb4`。
- API 文档：Knife4j。
- 工具库：Hutool、Lombok。
- PC 前端：Vue 2、Element UI、Vuex、Vue Router、Axios。

默认不引入新框架、新中间件、新存储方案、新任务系统或新的前端技术栈。确实需要引入时，必须先说明：

- 当前技术栈为什么不够。
- 可选方案和取舍。
- 影响范围。
- 部署和回退成本。
- 是否需要额外运维配置。

确认后再实施。

### 3.3 默认分层方式

- 后端默认沿用 `Controller -> Service -> Mapper` 分层。
- 数据对象默认沿用当前项目命名：
  - `Entity`：数据库实体。
  - `DTO`：请求入参或动作参数。
  - `VO`：接口返回对象。
  - `Query`：分页和筛选查询对象。
- 接口返回默认使用 `Result<T>`。
- 权限校验默认使用 `@SaCheckPermission`。
- 操作日志默认使用 `@OperLog`。
- 数据权限默认优先复用当前项目已有的数据权限能力，不另起一套。

## 4. 实现原则

### 4.1 保持现有结构优先

- 默认优先按当前项目结构直接落地，不为了“更通用”而引入额外层级。
- 不过度抽象、不过度封装。
- 只有当重复逻辑已经稳定、边界清晰，且抽取后能明显降低维护成本时，才做公共化收敛。
- 不把还没稳定的业务差异提前抽象成平台能力。

### 4.2 控制改动范围

- 每轮开发只改与目标直接相关的文件和逻辑。
- 不借机重构无关模块。
- 不随意格式化大文件，避免产生无关 diff。
- 不随意改动已稳定接口契约、数据库字段含义和权限口径。
- 如果发现必须扩大范围，应先说明原因、影响和替代方案。

### 4.3 数据库变更

- 涉及表结构、索引、初始化数据或菜单权限调整时，必须同步 SQL 脚本。
- SQL 变更应明确区分：
  - 新环境基础结构。
  - 旧环境升级脚本。
  - 初始化数据。
- 字段命名应优先表达业务语义，不为统一而牺牲含义。
- 删除字段、删表、重建表、清空历史数据等破坏性操作，必须有明确业务确认或专项文档支撑。

### 4.4 权限和数据范围

- 涉及业务对象详情、列表、状态变更、导出、附件、通知跳转时，都必须考虑数据权限。
- 列表可见不代表详情、操作、下载一定可见。
- 后端权限必须兜底，不能只依赖前端按钮隐藏。
- 如果一个入口通过通知、待办、链接或小程序跳转进入业务详情，仍必须执行业务对象权限校验。

## 5. 售后业务建模约定

- 售后业务表默认不使用 `as_` 前缀，直接使用业务语义命名，例如 `work_order`、`work_order_flow`。
- 涉及公司归属设计时，默认优先使用语义化公司字段，不盲目给所有表强塞泛化 `company_id`。
- 多角色语义表优先使用语义化公司字段，例如：
  - `work_order`：`current_accept_company_id`、`create_company_id`、`hq_company_id`。
  - `work_order_flow`：`from_company_id`、`to_company_id`、`operator_company_id`。
- 单归属业务表默认保留 `company_id`，便于数据权限、统计和责任归属，例如：
  - `work_order_participant`
  - `work_order_quote`
  - `work_order_repair`
  - `work_order_fault`
  - `work_order_review`
  - `work_order_evaluation`
- 判断原则：
  - 一条记录如果天然只归属于一个公司，优先使用 `company_id`。
  - 一条记录如果同时表达多个公司角色，优先拆成多个语义化公司字段。

## 6. 协作流程

### 6.1 讨论阶段

当用户提出需求、疑问或重构方向时，应先明确：

- 本轮目标是什么。
- 只做什么。
- 不做什么。
- 是否需要参考专项文档。
- 当前代码现状是什么。
- 可能影响哪些模块。
- 是否存在冲突或返工风险。

对于范围不清、影响较大的任务，应先输出方案或分阶段计划，等用户确认后再落地。

### 6.2 实施阶段

开始实施后，应遵循：

- 按确认范围改动。
- 遇到明显冲突、返工风险或技术路线变化时，先暂停说明。
- 不静默扩大范围。
- 不静默改变已经确认的业务口径。
- 不为了通过编译而绕过业务规则或权限规则。
- 实现后必须给出验证方式和验证结果。

### 6.3 验收阶段

交付说明应包含：

- 改了哪些关键文件或模块。
- 实现了哪些能力。
- 未做哪些内容。
- 运行了哪些验证。
- 是否存在未解决问题或环境阻塞。

只有用户明确验收通过后，才把事项写成已完成结论。

## 7. 状态和文档同步

- 讨论阶段不把草案写成正式结论。
- 已实现但未验收，不写成 `DONE` 或“已完成”。
- 用户明确确认后，才能同步正式决策、验收状态或完成记录。
- 如果需要新增专项方案文档，应写清：
  - 文档目的。
  - 当前问题。
  - 最终结论。
  - 明确不做。
  - 数据模型或接口设计。
  - 分阶段计划。
  - 验收标准。
- 如果专项文档后续被新方案替代，应在新文档中明确替代关系，不让旧文档继续误导后续线程。

## 8. 注释规范

### 8.1 总体原则

- 注释统一使用简体中文。
- 注释解释业务意图、约束、边界、状态流转、权限原因和异常兜底，不做代码字面翻译。
- 类、接口、公开方法默认使用 Javadoc。
- 复杂私有方法、关键状态流转方法、权限校验方法、跨模块协调方法，也应补充方法注释。
- 方法内部关键步骤应有必要注释，说明为什么这样做。

### 8.2 方法内部注释

以下场景必须补充方法内部注释：

- 业务状态流转。
- 幂等保护。
- 数据权限边界。
- 接收人、公司、角色等业务语义解析。
- 异步任务、重试、死信、人工补救。
- 历史兼容或历史清理。
- 特殊查询条件或索引友好写法。
- 调用其它方法的目的不是一眼能看出来时。

方法内部调用其它方法时，如果调用原因或目的不明显，应在调用前说明：

- 为什么要调用。
- 调用后要达成什么业务目的。
- 调用失败或跳过时的业务含义。

### 8.3 禁止的注释

避免以下低价值注释：

- “设置字段”
- “调用方法”
- “进入判断”
- “循环列表”
- “返回结果”
- 与代码字面含义完全重复的说明

### 8.4 修改旧代码时的注释处理

- 可以修改相关代码和相关注释。
- 如果逻辑变了，相关注释必须同步更新。
- 不要为了方便阅读、移动代码或减少文件长度，随意删除未改动区域的原有注释。
- 未涉及的代码区域，原则上不要主动清理、改写或删除原有注释。
- 如果原注释明显错误、乱码、过期或与本次修改后的逻辑冲突，可以在相关修改范围内一并修正。

## 9. 前端实现约定

- PC 管理后台默认沿用 Vue2 + Element UI 现有风格。
- 页面应优先服务业务操作效率，不做营销式、装饰性布局。
- 表单字段应贴合业务人员理解，不把后端技术字段直接暴露成主要维护项。
- 能由后端规则或注册表推导的字段，不应让用户手填。
- 前端隐藏按钮不是权限边界，后端必须兜底校验。
- 新增页面或大改页面时，应尽量复用现有 API 封装、列表布局、弹窗表单和权限按钮风格。

## 10. 测试和验证

- 后端改动应优先补充或更新单元测试。
- 涉及接口、权限、状态流转、异步任务、SQL 查询的改动，应有针对性验证。
- 前端改动至少执行构建验证。
- 如果测试或构建失败，应说明：
  - 执行了什么命令。
  - 失败在哪里。
  - 是否为本轮改动导致。
  - 已完成哪些替代验证。
- 不应因为既有测试失败而忽略本轮新增风险，应尽量缩小验证范围定位影响。

## 11. 风险沟通

遇到以下情况应主动暂停并说明：

- 用户最新口径与旧文档冲突。
- 当前实现会破坏已稳定接口或数据结构。
- 需要删除历史数据、删表、重建表或迁移大量数据。
- 权限模型存在绕过风险。
- 页面交互会让业务人员误解系统真实行为。
- 抽象程度明显超过当前业务需要。
- 原计划无法在不扩大范围的情况下完成。

说明时应给出：

- 冲突点。
- 影响范围。
- 推荐方案。
- 可选替代方案。
- 是否需要用户确认。


### 12.2 开始实施

```text
按刚才确认的方案开始实施。
只做已确认范围。
如果发现旧文档、当前代码和方案冲突，先暂停说明。
完成后说明改动、验证命令和结果。
```

### 12.3 验收同步

```text
本轮我确认通过。
请同步相关状态、决策记录或专项文档。
未验收内容不要写成已完成。
```
