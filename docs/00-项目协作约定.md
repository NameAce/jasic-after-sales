# 佳士售后系统 - 项目协作约定

> 本文档用于固化后续多轮协作中的全局约束、技术栈边界、协作节奏、状态同步规则和注释规范。
> 如无特别说明，后续需求讨论和落地默认遵循本文档。

---

## 1. 文档定位

- 作用：作为后续所有开发对话的全局约束入口，避免每轮重复说明技术栈、架构边界、协作方式和注释要求。
- 范围：约束技术实现、方案确认流程、状态同步方式、代码注释风格。
- 不替代：详细业务需求、数据库设计、接口设计和页面原型文档。
- 维护方式：当全局规则、协作方式或注释规范发生变化时，优先更新本文档。

### 1.1 长期参考文档与优先级

- 默认将以下文档作为长期上下文一起参考：

## 2. 当前项目基线

### 2.1 架构模式

- 项目采用 Maven 多模块单体架构，不拆微服务。
- 模块边界默认保持现状：
  - `jasic-common`：基础常量、枚举、异常、公共能力
  - `jasic-framework`：安全、数据权限、AOP、Web 基础设施
  - `jasic-system`：系统管理与 B 端核心业务
  - `jasic-customer`：C 端客户业务
  - `jasic-admin`：启动与配置
  - `jasic-ui`：Vue2 PC 管理后台

### 2.2 技术栈锁定

- 后端：Java 8、Spring Boot 2.7.x
- ORM：MyBatis-Plus 3.5.x
- 认证鉴权：Sa-Token
- 缓存：Redis / Redisson
- 数据库：MySQL 8.0，`utf8mb4`，InnoDB
- API 文档：Knife4j
- 工具库：Hutool、Lombok
- 前端：Vue 2 + Element UI + Vuex + Vue Router + Axios

### 2.3 默认实现约束

- 默认沿用现有技术栈和模块边界落地，不擅自引入新框架、新中间件、新存储方案、新任务系统。
- 如果确实需要引入新技术，必须先说明：
  - 现有方案为什么不够
  - 备选方案和影响面
  - 回退成本
  - 待你确认后再实施
- 默认沿用现有工程规范：
  - 分层结构：`Controller -> Service -> Mapper`
  - 对象命名：`Entity / DTO / VO / Query`
  - 统一返回：`Result<T>`
  - 权限方式：`@SaCheckPermission`
  - 日志方式：`@OperLog`
  - 数据权限方式：`@DataScope`

### 2.4 售后业务建模默认约定

- 售后业务表默认不使用 `as_` 前缀，直接采用业务语义命名，例如 `work_order`、`work_order_flow`。
- 公司归属字段默认遵循“语义优先”原则，不为了统一而给所有表强行增加一个泛化 `company_id`。
- 以下多角色语义表，默认使用语义化公司字段：
  - `work_order`：`current_accept_company_id`、`create_company_id`、`hq_company_id`
  - `work_order_flow`：`from_company_id`、`to_company_id`、`operator_company_id`
- 以下单归属业务表，默认尽量保留 `company_id`，便于数据权限、统计和责任归属：
  - `work_order_participant`
  - `work_order_quote`
  - `work_order_repair`
  - `work_order_fault`
  - `work_order_review`
  - `work_order_notify_event`
  - `work_order_evaluation` 可保留 `company_id` 作为被评价服务方快照
- 判断规则默认如下：
  - 一条记录如果天然只归属于一个公司，优先带 `company_id`
  - 一条记录如果同时表达多个公司角色，优先拆成多个语义化公司字段
- 后续若需偏离以上规则，先说明原因和影响，再确认是否调整。

## 3. 协作流程

### 3.1 总体原则

- 由你先提出本轮需求或问题。
- 由我先做需求映射：找到对应文档、当前代码位置、现状差异和潜在冲突。
- 我先给出一版计划，不直接把我自己的路线图当成既定结论。
- 计划必须经过你确认后，我再开始改代码或改数据库方案。
- 实现完成后，先给你验收，不在你确认前把事项标记为完成。

### 3.2 标准节奏

1. 你提出本轮目标。
2. 我整理对应需求、现状、差异和建议方案。
3. 我输出一版计划，明确：
   - 只做什么
   - 不做什么
   - 风险点
   - 验收标准
4. 你确认计划。
5. 我按确认后的计划实施。
6. 我给出结果和验证方式，等待你验收。
7. 只有在你明确“通过/确认/可以同步状态”后，我才更新实施清单中的状态和正式决策。

### 3.3 状态同步规则

- 讨论阶段：不更新 `docs/00-实施清单.md` 的状态栏。
- 已实施但未验收：只允许记录到“待验收记录”，不允许写成 `DONE`。
- 只有你明确验收通过后，才允许：
  - 更新 backlog 状态
  - 写入正式决策记录
  - 写入“最近完成”
- 如果实现过程中方案发生变化，先同步变更建议，确认后再继续实现。

### 3.4 变更同步规则

- 以下情况必须同步到仓库文档：
  - 需求新增
  - 原方案调整
  - 设计冲突
  - 范围降级
  - 技术策略变化
- 同步内容至少包括：
  - 变更时间
  - 变更原因
  - 影响范围
  - 最终结论
- 未确认的内容只能记为“草案”或“待确认”，不能伪装成已定结论。

## 4. 注释规范

### 4.1 总体要求

- 注释默认贴合当前仓库现有风格，使用中文，简洁、自然、像人工维护代码的写法。
- 注释解释“意图、约束、边界、业务原因”，不写逐行翻译式流水账。
- 如果代码本身已经足够清晰，就不强行补注释。
- 如果一段逻辑需要靠大段注释才能看懂，优先考虑拆方法、重命名或下沉逻辑，而不是堆注释。

### 4.2 与当前仓库对齐的写法

- 类、接口、公开方法默认使用 Javadoc。
- Javadoc 保持当前项目风格：
  - 第一行一句话说明用途
  - 需要时补 `@param`、`@return`
  - 不写空洞描述，不照抄方法名
- 行内注释只用于下面几类场景：
  - 业务分支的含义
  - 权限或数据范围边界
  - 查询或组装逻辑的关键步骤
  - 容易误解的兼容性处理
- 避免这种低价值注释：
  - “给变量赋值”
  - “调用某某方法”
  - “进入 if 判断”
  - 与代码字面意思完全重复的说明

### 4.3 注释落地标准

- Controller 注释：说明接口用途、入参含义、返回内容，不写接口内部显而易见的流程。
- Service 注释：说明业务动作和边界，尤其是权限、状态流转、事务性要求。
- Mapper 或 SQL 注释：说明筛选规则、排序原因、数据范围限定，不重复字段名本身含义。
- 复杂分支前允许加一行短注释，长度控制在一句话内。
- `TODO/FIXME` 必须写明原因和后续条件，不能只留一个空标签。

### 4.4 我的默认执行规则

- 后续我写的注释，默认以你仓库当前风格为准，而不是我自己的通用偏好。
- 如果你觉得某段注释不符合你预期，你指出一次，我会把那种写法加入本文档，后面统一遵守。

## 5. 推荐对话模板

### 5.1 讨论阶段

```text
项目：E:\桌面\jasic-after-sales
协作约定：docs/00-项目协作约定.md
实施清单：docs/00-实施清单.md
本轮需求：
已知约束：

1. 找对应需求
2. 结合当前代码看现状差异
3. 出一版实施计划
4. 不要先落地，等我确认
```

### 5.2 实施阶段

```text
按刚才确认的计划开始实施
只做：
不做：
验收标准：
如果涉及新技术/大改架构，先暂停并和我确认
如果和既有文档冲突，先给我变更建议，再落地
完成后先给我验收，不要先改实施清单状态
```

### 5.3 验收通过后

```text
本轮我确认通过
请同步：
1. 实施清单状态
2. 决策记录
3. 最近完成
```
