# 小程序订阅通知模板重构落地方案

> 本文档用于给后续另起线程的实施工作直接提供落地基线。
> 本轮目标不是继续讨论模板口径，而是基于已经确认的产品口径与技术口径，推动通知模块按统一方案完成重构优化与接入。
> 后续如另起线程实施，应以本文档为主基线，同时参考：
>
> - `docs/19-消息通知场景多目标重构方案.md`
> - `docs/21-小程序订阅消息模板场景梳理.md`
> - `docs/22-小程序通知模板产品口径确认稿.md`

---

## 1. 文档目的

- 把当前已经确认的 B/C 端小程序订阅通知方案整理为一份可直接执行的实施方案。
- 为后续另起线程的开发、联调、测试和验收提供统一基线。
- 明确本轮要做什么、不做什么、按什么顺序做，以及代码注释必须达到什么标准。

---

## 2. 本轮目标

本轮要完成的核心目标只有一句话：

**基于已经确认的 6 个保留模板场景，完成通知场景配置、业务触发、接收人收口、模板字段映射、发送链路与注释规范的一次性重构优化。**

本轮完成后，应满足：

1. B 端、C 端保留模板场景口径完全一致。
2. 后端通知场景与模板字段映射不再靠临时猜测。
3. 现有通知主链路继续沿用统一通知场景模型，不回退旧的零散发消息方式。
4. 新增或改造代码具备完整、可读、可维护的简体中文注释。

- 本轮不为该场景保留新的后端实现。

## 4. 最终确认口径

后续另起线程实施时，必须直接采用以下确认结论，不再重复讨论：

### 4.1 场景保留与取消

1. 当前 7 个模板中，只保留 6 个场景进入后续实现。
2. `B 端评价提醒` 本轮取消，不纳入后续代码开发。

### 4.2 场景分类

1. `B 端待派单通知`、`B 端工单转入通知` 属于网点级通知。
2. `B 端维修员接单通知` 属于个人级通知。
3. `C 端接单成功提醒`、`C 端网点转单通知`、`C 端客户满意度评价通知` 都属于客户感知通知。

### 4.3 B 端接收人口径

1. B 端网点级通知接收人统一为：
   - 当前目标公司下已启用用户
   - 对于“接单通知”场景，具备 `workorder:assign` 权限
   - 且已绑定小程序 `openid`
2. `B 端待派单通知`、`B 端工单转入通知` 默认允许一张工单同时通知多人。
3. 第一版不额外扩大到“只有派单权限但没有接单权限”的管理用户。
4. 模板订阅授权仍由小程序前端在用户点击链路内请求；后端当前不单独持久化授权结果，不作为事件发布前的硬筛条件。
5. 如微信发送时返回“用户未订阅/拒绝接收”，统一记录跳过结果与原因。

### 4.4 C 端发送口径

1. `C 端接单成功提醒` 只在工单第一次被工程师正式接单时发送一次。
2. 工单后续如发生转单，不再重复发送 `C 端接单成功提醒`，改由 `C 端网点转单通知` 承接客户通知。
3. `C 端客户满意度评价通知` 只发给允许评价的工单。
4. 不允许评价的工单不发送评价通知。

### 4.5 字段解释口径

1. `B 端维修员接单通知` 中的“用户名称、联系电话”统一解释为客户信息。
2. `B 端工单转入通知` 中的“网点名称”统一解释为转出网点名称。
3. `C 端网点转单通知` 中的“网点名称”统一解释为转入后的当前处理网点名称。

### 4.6 联系电话统一取值规则

模板中涉及公司联系电话时，统一按以下规则取值：

1. 优先 `sys_company.service_phone`
2. 若为空则回退 `sys_company.contact_phone`

### 4.7 用户名称展示兜底规则

模板中出现“用户名称”时，统一展示顺序为：

1. 优先客户姓名
2. 若客户姓名为空，则回退客户手机号
3. 若仍为空，则展示“客户”

### 4.8 固定文案口径

`C 端网点转单通知` 的“温馨提示”第一版固定，不按转单原因动态改写。

推荐固定文案：

`您的工单已转由其他网点继续处理，请留意后续联系。`

### 4.9 默认启用口径

本轮保留的 6 个模板场景默认启用，不作为关闭状态进入联调。

## 5. 产品场景清单

| 使用端 | 模板标题 | 业务含义 | 触发时机 | 接收人 | 跳转页面 |
|---|---|---|---|---|---|
| B 端 | 待派单通知 | 新工单进入目标网点待派单池 | 建单成功且已确定承接网点后 | 当前网点全部满足条件的派单权限用户 | B 端工单详情 |
| B 端 | 工单转入通知 | 工单从其他网点转入当前网点 | 转单成功且当前承接网点切换后 | 转入网点全部满足条件的可接单用户 | B 端工单详情 |
| B 端 | 维修员接单通知 | 网点将工单派给具体工程师 | 派单成功后 | 被派单工程师本人 | B 端工单详情 |
| C 端 | 接单成功提醒 | 工程师已经正式接单 | 第一次正式接单成功后 | 客户本人 | C 端工单详情 |
| C 端 | 网点转单通知 | 当前处理网点发生变化 | 转单成功后 | 客户本人 | C 端工单详情 |
| C 端 | 客户满意度评价通知 | 工单关闭并可评价 | 工单关闭且允许评价后 | 客户本人 | C 端评价页 |

## 6. 落地原则

### 6.1 统一模型原则

- 必须继续沿用当前通知模块“通知场景 + 通知目标 + 统一分发”的模型。
- 不允许回退为业务层直接拼模板并直接调用微信发送。
- 不允许绕开当前通知事件、通知目标、分发表与 sender 体系。

### 6.2 直接落地原则

- 默认优先按当前项目现有结构直接落地。
- 不为本轮再引入新的通知中台抽象层、规则中心、订阅偏好系统。
- 如现有能力能通过少量扩展完成，就不要额外抽象平台层。

### 6.3 注释完整原则

本轮所有新增或重构代码都必须满足以下要求：

1. 注释统一使用简体中文。
2. 新增或重构类时，必须补充类注释，说明：
   - 业务职责
   - 使用边界
   - 在通知链路中的角色
3. 新增或重构方法时，必须补充方法注释，说明：
   - 方法目的
   - 参数含义
   - 返回值含义
   - 异常场景
4. 方法内部关键步骤必须补充中文注释，尤其包括：
   - 状态流转
   - 接收人筛选
   - 权限边界
   - 幂等控制
   - 模板变量组装
   - 渠道分发
   - 失败跳过逻辑
5. 方法内部调用其它方法时，如果调用原因或目的不是一眼可知，必须在调用前说明：
   - 为什么调用
   - 调用后希望达成什么业务目的
6. 修改已有代码时，如果逻辑变了，相关注释必须同步更新。
7. 没有改动的区域，不允许为了方便阅读随意删除原有注释。

---

## 7. 本轮不做

本轮明确不做以下内容：

1. 不恢复或实现 `B 端评价提醒`
2. 不引入新的通知渠道，例如短信、邮件、公众号
3. 不引入用户通知偏好、订阅中心、自动重试策略中心
4. 不单独新建复杂接收人规则中心
5. 不为了这轮重构去大范围调整无关模块
6. 不为了简化开发而删除未改动区域的原有注释

---

## 8. 分阶段实施方案

本轮如果另起线程实施，建议分 **3 个阶段**，不要再拆得更细。

### 阶段一：通知场景与配置基线收口

目标：

- 先把保留的 6 个场景在通知场景层面收口到统一基线。
- 补齐场景注册、默认模板配置、字段映射、页面路径模板、默认说明。

本阶段要做的事情：

1. 对照 `docs/21` 与 `docs/22`，补齐或调整通知场景注册信息。
2. 保留现有已落地场景：
   - `WORK_ORDER_ASSIGNED`
   - `WORK_ORDER_EVALUATION_INVITE`
3. 新增本轮缺失的场景注册：
   - B 端待派单通知
   - B 端工单转入通知
   - C 端接单成功提醒
   - C 端网点转单通知
4. 为每个场景补齐默认的小程序模板配置：
   - 模板 ID
   - 页面路径模板
   - 字段映射
   - 默认启用状态
5. 确认并落地联系电话、用户名、固定提示文案等统一规则。
6. 明确本轮取消的 `B 端评价提醒` 不进入新场景注册。

本阶段产出：

1. 通知场景注册代码完成收口
2. 后台通知场景配置默认值与模板映射可用
3. 注释补齐，确保后续线程能看懂每个场景为什么存在

### 阶段二：业务触发与接收人链路收口

目标：

- 把 6 个保留场景真正挂到对应业务动作上。
- 让通知事件、接收人、模板变量和外部分发表形成完整主链路。

本阶段要做的事情：

1. 对现有已落地主链路做改造：
   - `B 端维修员接单通知`
   - `C 端客户满意度评价通知`
2. 补齐新增场景的业务触发链路：
   - B 端待派单通知
   - B 端工单转入通知
   - C 端接单成功提醒
   - C 端网点转单通知
3. 明确每个场景的接收人组装逻辑：
   - B 端网点级通知：当前目标公司下满足条件的全部可接单用户
   - B 端个人级通知：被派单工程师本人
   - C 端通知：客户本人
4. 完成模板变量组装与兜底规则落地：
   - 用户名称展示顺序
   - 联系电话取值规则
   - 转出/转入网点名称解释
   - 固定提示文案
5. 保证所有小程序通知仍统一进入分发表，由 sender 执行真实发送。
6. 确保已有业务层不出现直接绕过通知主链路发微信消息的代码。

本阶段产出：

1. 6 个保留模板场景全部具备完整的业务触发能力
2. 接收人逻辑、字段映射、跳转路径与最终口径一致
3. 方法内部注释完整，便于排障和二次维护

### 阶段三：联调验证与收口

目标：

- 对场景、接收人、字段映射、跳转路径和发送结果进行统一验证。
- 把这轮重构从“代码改了”推进到“行为可验收”。

本阶段要做的事情：

1. 针对 6 个保留场景补齐或更新测试。
2. 验证以下关键分支：
   - 首次接单只发一次
   - 转单后不重复发接单成功提醒
   - 不允许评价的工单不发评价通知
   - B 端网点级通知支持一单多人
   - 模板字段映射与当前申请模板一致
   - 联系电话兜底规则正确
   - 用户名称兜底规则正确
3. 检查后台通知场景配置页面中的默认配置是否与文档一致。
4. 确认取消场景 `B 端评价提醒` 没有被误接入或误启用。
5. 汇总本轮改动说明、验证结果、剩余风险与后续建议。

本阶段产出：

1. 联调通过的场景清单
2. 测试结果与验证记录
3. 最终交付说明

## 9. 代码改造关注点

后续线程落地时，重点关注以下模块：

### 9.1 通知场景注册层

- 维护保留场景
- 新增场景元数据
- 维护默认模板映射
- 补齐字段映射说明注释

### 9.2 业务事件发布层

- 工单建单后是否触发网点级通知
- 派单后是否触发个人级通知
- 接单后是否触发客户提醒
- 转单后是否分别触发 B/C 两侧通知
- 关单后是否触发评价邀请

### 9.3 接收人解析层

- 网点级通知的多人接收规则
- 个人级通知的唯一接收人规则
- 客户通知的 `openid` 获取规则
- 模板订阅授权未持久化前，发送阶段对“用户未订阅/拒绝接收”的跳过与留痕

### 9.4 模板变量组装层

- 用户名称兜底
- 联系电话统一规则
- 网点名称语义区分
- 固定提示文案
- 页面跳转参数

### 9.5 后台配置与排障层

- 通知场景配置默认值
- 模板预览能力
- 分发表结果查看
- 失败/跳过原因回写

## 10. 验收标准

后续线程交付时，至少要满足以下验收标准：

### 10.1 场景验收

1. 只保留文档确认的 6 个模板场景。
2. `B 端评价提醒` 不进入本轮代码落地范围。

### 10.2 行为验收

1. `C 端接单成功提醒` 只发首次正式接单。
2. 转单后不会重复发送 `C 端接单成功提醒`。
3. `C 端客户满意度评价通知` 只在允许评价时发送。
4. B 端网点级通知可一单多人。
5. B 端维修员接单通知只发给被派单工程师本人。

### 10.3 字段验收

1. 模板字段与当前微信模板字段一致。
2. 联系电话取值符合统一规则。
3. 用户名称兜底符合统一规则。
4. B 端与 C 端转单场景中的“网点名称”解释不混淆。
5. C 端转单固定提示文案与文档一致。

### 10.4 注释验收

1. 新增或重构类、方法都有完整简体中文注释。
2. 方法内部关键步骤都有业务目的说明。
3. 方法内部调用其它方法时，必要场景都有调用原因说明。
4. 未改动区域原注释未被随意删除。

### 10.5 测试验收

1. 至少完成针对新增/改造通知场景的后端测试或验证。
2. 明确说明执行了哪些测试、结果如何、还有哪些未覆盖风险。
