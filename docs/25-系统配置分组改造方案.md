# 系统配置分组改造方案

> 本文档用于给后续另起线程的“系统配置分组改造与配置页重构”提供直接落地基线。
> 本轮目标不是继续讨论是否分组，而是把已经确认的方案整理成可执行口径，后续实现按本文档收口。

---

## 1. 文档目标

- 明确当前 `sys_config` 的分组改造方案。
- 基于当前项目真实存在且正在使用的配置项，给出最终 `group_key` 约定。
- 明确本轮要做什么、不做什么、哪些历史配置需要隔离。
- 明确后续实现时的注释规范，避免因为重构而破坏现有注释质量。

---

## 2. 本轮背景

当前项目已经有参数管理能力，但现状仍然是传统的 `config_key + config_value` 维护方式，问题主要集中在：

- 参数列表是平铺的，缺少业务分组，后续配置项变多后维护成本会快速上升。
- 新的“系统配置”聚合页如果没有后端分组能力，前端只能完全写死，后续扩展会越来越散。
- 项目中已经出现“代码读取配置，但初始化脚本不完整”的情况，存在运行风险。
- 历史上存在 `wechat.notify.*` 这类旧通知参数，但正式链路已经废弃，不应继续纳入新配置页。

因此，本轮决定采用“`sys_config` 单表增强，仅增加分组字段 `group_key`”的中间态方案。
同时，本轮明确只做后端与数据层改造，不改前端页面。

---

## 3. 最终确认结论

本轮最终确认的结论如下：

1. 在 `sys_config` 表中新增 `group_key` 字段。
2. `group_key` 非空，历史数据一次性回填，不保留空分组状态。
3. 当前只引入分组能力，不同步引入 `value_type`、`control_type`、`options_json` 等更重的元数据字段。
4. 本轮不新增新的“系统配置”页，不改现有前端页面。
5. 原有“参数设置”列表页继续保留，作为当前唯一配置维护入口。
6. 历史废弃配置统一隔离，但本轮只做数据分组，不新增前端展示策略。
7. 代码中已读取但初始化脚本缺失的配置项，本轮一并补齐初始化 SQL。

---

## 4. 本轮范围

### 4.1 本轮要做

1. 为 `sys_config` 增加 `group_key` 字段。
2. 按当前真实配置项回填 `group_key`。
3. 补齐缺失但已被代码读取的初始化配置。
4. 后端补充分组字段的查询、保存兼容处理。
5. 保留原“参数设置”页，不替换、不删除。

### 4.2 本轮不做

1. 不新增 `sys_config_group` 表。
2. 不做完整配置中心建模。
3. 不做动态表单引擎。
4. 不做配置版本、回滚、灰度、发布流程。
5. 不做多公司作用域配置。
6. 不重新启用 `wechat.notify.*` 历史参数链路。
7. 不新增前端“系统配置”聚合页。
8. 不改现有前端参数设置页样式、结构和交互。

---

## 5. 表结构改造方案

### 5.1 字段改造

在现有 `sys_config` 表中新增字段：

```sql
ALTER TABLE sys_config
ADD COLUMN group_key varchar(64) NOT NULL DEFAULT 'org' COMMENT '配置分组标识';
```

### 5.2 字段说明

- `group_key`
  - 用途：标识配置项所属业务分组。
  - 约束：不能为空。
  - 维护方式：仅允许使用后端约定值，不允许随意自由输入。

### 5.3 当前阶段不新增的字段

本轮明确不新增以下字段：

- 配置类型字段
- 控件类型字段
- 组内排序字段
- 分组表
- 扩展 JSON 字段

原因是本轮核心问题是“配置缺少业务分组”，不是“配置元信息系统不完整”。先解决结构感问题，避免过度设计。

---

## 6. 分组约定

### 6.1 最终分组

本轮分组固定为以下 4 组：

- `org`
- `wechat`
- `work_order`
- `legacy`

### 6.2 分组含义

- `org`
  - 组织、公司初始化相关配置。

- `wechat`
  - 微信、小程序登录、绑定、基础接入相关配置。

- `work_order`
  - 工单业务默认参数相关配置。

- `legacy`
  - 历史废弃配置，仅作隔离和保留，不进入新的系统配置页。

### 6.3 页面展示名称建议

- `org` -> `组织配置`
- `wechat` -> `微信配置`
- `work_order` -> `工单配置`
- `legacy` -> `历史配置`

说明：

- 本轮不新增新的系统配置页，因此这里只是后端分组语义约定。
- `legacy` 的主要作用是隔离历史配置，便于后续页面化改造时直接排除。

---

## 7. 现有配置项分组映射

基于当前代码、初始化脚本和常量定义，现有配置项按以下规则归组。

### 7.1 `org` 分组

- `org.company.adminInitPassword`

业务含义：

- 创建公司时默认管理员账号的初始密码。

### 7.2 `wechat` 分组

- `wechat.mp.b.appid`
- `wechat.mp.b.secret`
- `wechat.mp.c.appid`
- `wechat.mp.c.secret`
- `wechat.mp.b.bind.pagePath`

业务含义：

- B 端小程序接入参数。
- C 端小程序接入参数。
- B 端微信绑定页跳转路径配置。

### 7.3 `work_order` 分组

- `default.hq.company.id`

业务含义：

- 非佳士无码报修等场景下的默认归属总部 ID。

### 7.4 `legacy` 分组

统一纳入以下历史参数：

- `wechat.notify.customer.repairFinished.*`
- `wechat.notify.customer.evaluationInvite.*`
- `wechat.notify.company.customerEvaluated.*`
- 其它历史上遗留但已明确废弃的 `wechat.notify.*`

业务含义：

- 历史旧通知口径参数。
- 当前正式主链路已不再依赖。

约束说明：

- `legacy` 分组中的配置不进入新的系统配置页。
- 后续开发中不得把新功能重新挂回这些历史 key。

## 8. 初始化与迁移口径

### 8.1 本轮需要补齐的初始化配置

本轮确认需要补齐以下已被代码读取、但初始化脚本中未完整覆盖的配置项：

1. `wechat.mp.b.bind.pagePath`
2. `default.hq.company.id`

### 8.2 默认值口径

本轮最终确认：

- `wechat.mp.b.bind.pagePath`：默认空值
- `default.hq.company.id`：默认空值

原因：

- 这两个值都带明显环境语义或业务部署差异，不适合在初始化脚本中写死。
- 先保证配置项存在，再由具体环境按需填写。

### 8.3 历史数据回填口径

建议迁移 SQL 参考如下：

```sql
ALTER TABLE sys_config
ADD COLUMN group_key varchar(64) NOT NULL DEFAULT 'org' COMMENT '配置分组标识';

UPDATE sys_config
SET group_key = 'org'
WHERE config_key = 'org.company.adminInitPassword';

UPDATE sys_config
SET group_key = 'wechat'
WHERE config_key IN (
  'wechat.mp.b.appid',
  'wechat.mp.b.secret',
  'wechat.mp.c.appid',
  'wechat.mp.c.secret',
  'wechat.mp.b.bind.pagePath'
);

UPDATE sys_config
SET group_key = 'work_order'
WHERE config_key = 'default.hq.company.id';

UPDATE sys_config
SET group_key = 'legacy'
WHERE config_key LIKE 'wechat.notify.%';
```

### 8.4 缺失配置补齐口径

建议在升级 SQL 中补齐缺失项，示例：

```sql
INSERT INTO sys_config (
  config_name,
  config_key,
  config_value,
  config_type,
  group_key,
  remark,
  create_time,
  update_time
)
SELECT
  'B端微信绑定页路径',
  'wechat.mp.b.bind.pagePath',
  '',
  0,
  'wechat',
  'B端微信绑定二维码或绑定链路使用的小程序页面路径，默认留空，由具体环境按需配置',
  NOW(),
  NOW()
WHERE NOT EXISTS (
  SELECT 1 FROM sys_config WHERE config_key = 'wechat.mp.b.bind.pagePath'
);

INSERT INTO sys_config (
  config_name,
  config_key,
  config_value,
  config_type,
  group_key,
  remark,
  create_time,
  update_time
)
SELECT
  '默认归属总部ID',
  'default.hq.company.id',
  '',
  0,
  'work_order',
  '非佳士无码报修等场景下的默认归属总部ID，默认留空，由具体环境按需配置',
  NOW(),
  NOW()
WHERE NOT EXISTS (
  SELECT 1 FROM sys_config WHERE config_key = 'default.hq.company.id'
);
```

## 9. 后端改造要求

### 9.1 查询与保存兼容要求

本轮不改前端页面，因此后端不强制新增按组接口。

本轮要求是：

- 现有参数管理接口在新增 `group_key` 字段后仍能正常工作。
- 新增、修改参数时能够正确保存 `group_key`。
- 列表查询时能够返回 `group_key`，为后续页面化改造预留基础。

如果实现过程中顺手补充按组查询能力，可以做，但不作为本轮必须交付项。

### 9.2 缓存处理

保存成功后应刷新配置缓存。

要求：

- 可以延续现有“刷新缓存”能力。
- 本轮不强制实现精细化单 key 刷新。
- 以稳定生效为优先。

### 9.3 排序口径

本轮没有引入 `sort_num` 字段，因此建议后端默认按以下顺序返回：

1. `group_key`
2. `id`

说明：

- 当前配置项数量不多，先按已有数据顺序稳定返回即可。
- 后续如果分组内配置项增多，再单独引入排序字段。

## 10. 前端处理要求

### 10.1 本轮前端范围

本轮明确不改前端。

这意味着：

- 不新增“系统配置”聚合页。
- 不改现有参数设置页的布局、表单结构、筛选结构和交互方式。
- 现有前端只需保证在后端字段增加后不因返回结构变化而报错。

---

## 11. 历史配置处理要求

### 11.1 历史配置定位

`wechat.notify.*` 及其它已废弃通知参数统一归类为 `legacy`。

### 11.2 历史配置处理原则

- 不删除历史数据
- 不进入新页面
- 不作为新链路配置入口
- 不在本轮重新启用

### 11.3 开发约束

后续任何新功能开发，如涉及通知模板、通知跳转页、通知渠道参数，不得重新依赖 `wechat.notify.*`。

正式链路继续沿用当前通知模块既有设计口径。

## 12. 代码注释与重构实施约束

本节为本轮及后续另起线程实施时的强约束，必须严格遵守。

### 12.1 注释语言要求

- 所有新增、修改或重构代码的注释，统一使用简体中文。

### 12.2 注释覆盖范围要求

所有新增、修改或重构的代码，都必须补充完整且清晰的注释，范围包括但不限于：

- 类注释
- 接口注释
- 字段注释
- 方法注释
- 方法内部关键业务步骤注释

### 12.3 类和接口注释要求

新增或重构类、接口时，必须说明：

- 业务职责
- 使用范围
- 边界条件
- 与其它模块的关系
- 在本次系统配置分组改造中的角色

### 12.4 方法注释要求

新增或重构方法时，必须说明：

- 方法的业务目的
- 参数含义
- 返回值含义
- 核心处理流程
- 异常场景
- 特殊兼容处理

### 12.5 方法内部注释要求

方法内部关键业务步骤必须补充详细中文注释，重点说明：

- 为什么这样做
- 希望达成什么业务结果
- 这样做和本次分组改造的关系
- 不这样做会有什么风险或影响

尤其要重点注释以下场景：

- 配置分组回填
- 历史配置隔离
- 配置缓存刷新
- 批量保存逻辑
- 新旧页面并存逻辑
- 缺失配置自动补齐逻辑
- 历史兼容逻辑

### 12.6 方法内部调用其它方法的注释要求

方法内部调用其它方法时，如果调用原因或业务目的不是一眼能看懂，必须在调用前补充注释，至少说明：

- 为什么调用这个方法
- 调用希望达成什么效果
- 如果不调用会造成什么业务问题

### 12.7 修改代码时的旧注释处理要求

开发过程中允许修改代码，但必须遵守以下约束：

1. 不要为了阅读方便随意删除原有注释。
2. 未改动的代码区域，不要主动清理原有注释。
3. 如果修改了逻辑，必须同步修改对应注释，保证注释与实现一致。
4. 如果原注释仍然准确，应予以保留，不要因为篇幅或个人习惯删除。
5. 如果原注释与新逻辑冲突，应在本次改动范围内一并修正。

### 12.8 重构风格要求

- 默认优先沿用项目当前结构直接落地。
- 不过度抽象。
- 不为了本轮分组改造额外引入新框架、新存储方案或新的配置中心模型。
- 所有改动必须以“当前项目可维护性提升”为目标，而不是为了做成通用平台。

## 13. 验收标准

### 13.1 数据结构验收

1. `sys_config` 成功新增 `group_key` 字段。
2. `group_key` 非空约束生效。
3. 历史数据完成分组回填。

### 13.2 配置项验收

1. `org.company.adminInitPassword` 已归入 `org`。
2. `wechat.mp.b.appid`、`wechat.mp.b.secret`、`wechat.mp.c.appid`、`wechat.mp.c.secret`、`wechat.mp.b.bind.pagePath` 已归入 `wechat`。
3. `default.hq.company.id` 已归入 `work_order`。
4. `wechat.notify.*` 已归入 `legacy`。

### 13.3 接口与兼容验收

1. 现有参数管理接口在新增 `group_key` 后仍可正常使用。
2. 原“参数设置”页仍可正常使用。
3. 参数新增、修改、查询不会因为 `group_key` 引入而破坏现有能力。

### 13.4 初始化验收

1. `wechat.mp.b.bind.pagePath` 缺失时可自动补齐。
2. `default.hq.company.id` 缺失时可自动补齐。
3. 两个新增补齐项默认值均为空字符串。

### 13.5 注释验收

1. 新增或重构的类、字段、方法均具备完整简体中文注释。
2. 方法内部关键步骤都有清晰注释。
3. 方法内部调用其它方法时，调用原因或业务目的已说明。
4. 未改动区域原注释未被随意删除。
