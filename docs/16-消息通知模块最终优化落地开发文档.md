# 消息通知模块最终优化落地开发文档

## 1. 文档目的

本文档用于定义当前系统消息通知模块的最终优化方案和分阶段落地开发步骤，作为后续多线程、多轮接力实现的统一基线。

本文档不是重新设计一个大而全的通知平台，而是在现有 `sys_notify_*` 实现基础上做一次模型收口、可靠性补齐和排障能力补齐。

后续实现如与本文档冲突，默认以本文档为准；如确需调整，必须先补充“变更记录”，再修改代码或数据库脚本。

## 3. 当前问题结论

当前通知模块已经具备以下能力：

- `sys_notify_event` 事件入库
- `sys_notify_message` 站内待办
- `sys_notify_message_log` 站内消息状态日志
- `sys_notify_template` 模板配置
- `sys_notify_template_channel` 渠道配置
- `sys_notify_dispatch` 外部渠道分发
- Quartz 定时消费事件和分发任务
- PC 消息中心和红点
- C 端小程序评价邀请通知

但当前设计存在以下需要收口的问题：

| 问题 | 说明 | 优化方向 |
| --- | --- | --- |
| 旧通知口径残留 | `work_order_notify_event`、`wechat.notify.*` 仍在部分文档和初始化数据里出现 | 明确废弃旧链路，统一到 `sys_notify_*` |
| `sys_notify_event.receiver_id` 语义混乱 | 派单场景表示系统用户，评价邀请表示客户 | 新逻辑不再依赖事件表接收人字段 |
| 事件消费类继续膨胀 | 当前通过 `if eventType` 分发不同场景 | 拆成轻量 `NotifyEventHandler` |
| 站内消息与外部渠道边界不够清晰 | 模板、路由、渠道配置职责有交叉 | 站内走 `sys_notify_message`，外部走 `sys_notify_dispatch` |
| 失败恢复不完整 | `PROCESSING` 宕机后可能卡住，缺少死信状态 | 增加超时恢复、最大重试和 `DEAD` |
| 排障能力不足 | 没有按工单查看全链路通知记录的后台 | 新增通知记录/排障页面 |
| 外部通知缺少人工补救 | 配置修复后不能从后台重试失败任务 | 支持 `FAILED/DEAD` 手动重试 |

## 4. 最终目标

最终优化后的通知模块只解决以下四件事：

1. 业务动作发生后，可靠记录一条通知事件。
2. 根据事件生成站内待办或外部发送任务。
3. 通知内容和小程序渠道配置可后台维护。
4. 通知结果可查、失败可解释、必要时可重试。

## 5. 本轮明确不做

为控制复杂度，以下内容不纳入本次优化：

- 不做规则引擎
- 不做条件表达式、循环模板、脚本化模板
- 不做用户通知偏好
- 不做多语言模板
- 不做公司级模板继承
- 不做后台自由新增未知通知场景
- 不做短信、邮件真实发送实现
- 不做企业微信真实发送实现
- 不做复杂渠道编排
- 不做通知营销、公告、运营推送

后续如果确实需要以上能力，必须单独立项，不允许混入本次优化。

## 6. 核心设计原则

### 6.1 业务只发布事件

工单、评价等业务模块只负责发布通知事件，不直接创建站内消息，不直接调用微信发送。

业务层允许做：

- 判断是否满足通知触发条件
- 组装事件快照
- 调用 `WorkOrderNotifyFacade` 发布事件

业务层不允许做：

- 直接写 `sys_notify_message`
- 直接写 `sys_notify_dispatch`
- 直接调用 `WechatMiniProgramService.sendSubscribeMessage(...)`
- 直接读取通知模板配置

### 6.2 事件只表达“发生了什么”

`sys_notify_event` 只表达业务事实，不承担“发给谁”的最终语义。

接收人应在事件消费阶段由 handler 根据场景解析。

### 6.3 站内消息和外部触达分离

站内消息中心和红点只使用 `sys_notify_message`。

微信、小程序、短信、邮件等外部触达只使用 `sys_notify_dispatch`。

两个模型不混用：

- 站内消息不保存微信模板 ID
- 外部分发不使用 `todo_status`
- 外部分发不进入 PC 消息中心红点

### 6.4 模板继续采用半配置化

模板只配置：

- 通知开关
- 标题模板
- 摘要模板
- 跳转配置
- 渠道参数

模板不配置：

- 触发时机
- 接收人策略
- 业务状态流转
- 待办完成动作

### 6.5 失败必须可查

每一次通知事件和外部分发都必须有明确状态。

失败必须能看到：

- 哪个业务对象
- 哪个通知场景
- 发给谁
- 通过哪个渠道
- 当前状态
- 失败原因
- 第三方响应
- 是否还能重试

### 6.6 代码注释要求

本次通知模块重构涉及多人、多线程接力，代码注释必须比普通功能开发更完整，避免后续线程只看代码时丢失设计意图。

总体要求：

- 类必须写中文 Javadoc，说明类的业务职责、边界和不负责的内容。
- 接口必须写中文 Javadoc，说明抽象意图、适用场景和实现约束。
- public 方法、protected 方法、private 方法都要写中文 Javadoc。
- 方法内部必须保留必要的中文步骤注释，说明关键业务判断、状态流转、幂等保护、异常兜底和数据权限边界。
- 方法内部调用其它方法时，如果调用目的不是一眼能看出来，必须在调用前写注释说明“为什么调用”或“调用后要达成什么目的”。
- 对状态流转、重试、死信、人工重试、超时恢复等关键逻辑，必须说明业务原因，不能只写代码字面含义。
- 对历史兼容逻辑，必须明确注释“兼容什么旧字段/旧数据，后续是否可删除”。
- 对不允许扩展的边界，必须在类或方法注释中明确写出，例如“不直接调用微信发送”“不直接创建站内消息”等。

类注释示例：

```java
/**
 * 工单派单通知事件处理器。
 *
 * <p>负责消费 WORK_ORDER_ASSIGNED 事件，并根据事件快照生成维修员站内待办消息。
 * 本处理器只处理站内待办，不负责外部渠道发送；外部渠道应通过 sys_notify_dispatch 处理。</p>
 */
public class WorkOrderAssignedNotifyEventHandler implements NotifyEventHandler {
}
```

方法注释示例：

```java
/**
 * 处理工单派单通知事件。
 *
 * <p>处理流程包括：解析事件快照、转派时失效旧维修员待办、渲染站内模板、
 * 幂等创建新维修员待办，并写入消息状态日志。</p>
 *
 * @param event 已抢占为 PROCESSING 的通知事件
 */
@Override
public void handle(SysNotifyEvent event) {
}
```

方法内部注释示例：

```java
// 先解析事件快照，后续接收人、模板变量和幂等键都依赖这份业务快照。
NotifyAssignedEventDTO payload = parseAssignedPayload(event);

// 转派场景需要先失效旧维修员待办，避免旧处理人继续看到可处理红点。
invalidateTransferredTodos(event, payload);

// 最后再创建新维修员待办；该方法内部通过 eventId 做幂等保护，避免重复消费生成重复消息。
createPendingMessageIfAbsent(event, payload);
```

注释禁止项：

- 不写只有“调用方法”“设置字段”“进入判断”这类无意义注释。
- 不复制粘贴错误的历史乱码注释。
- 不用英文注释解释中文业务规则。
- 不在注释中写已经过期的旧方案结论。

验收要求：

- 新增类和新增方法没有空 Javadoc。
- 重构后的关键方法内部有步骤注释。
- 复杂分支能通过注释看出业务目的。
- 代码审查时如果发现注释只解释字面动作，需要退回补充业务意图。

## 7. 术语与中文说明

| 英文字段/对象 | 中文含义 | 说明 |
| --- | --- | --- |

## 9. 数据库最终设计

### 9.1 `sys_notify_event` 通知事件表

职责：记录业务通知事件，只回答“发生了什么”。

建议最终字段：

| 字段 | 中文含义 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `id` | 主键 | 是 | 自增主键 |
| `event_key` | 事件幂等键 | 是 | 全局唯一，防止重复事件 |
| `event_type` | 事件类型 | 是 | 如 `WORK_ORDER_ASSIGNED` |
| `biz_type` | 业务类型 | 是 | 当前主要为 `WORK_ORDER` |
| `biz_id` | 业务 ID | 是 | 工单 ID |
| `biz_no` | 业务编号 | 是 | 工单号 |
| `operator_id` | 操作人 ID | 否 | 触发业务动作的系统用户 |
| `payload_json` | 事件业务快照 | 是 | 保存触发时关键业务数据 |
| `status` | 消费状态 | 是 | `NEW/PROCESSING/SUCCESS/FAILED/DEAD` |
| `retry_count` | 重试次数 | 是 | 默认 0 |
| `next_retry_time` | 下次重试时间 | 否 | 失败重试调度使用 |
| `processing_time` | 开始处理时间 | 否 | 用于 `PROCESSING` 超时恢复 |
| `error_message` | 错误信息 | 否 | 最近一次失败原因 |
| `create_time` | 创建时间 | 是 | 统一审计字段 |
| `update_time` | 更新时间 | 是 | 统一审计字段 |

兼容说明：

- 当前表中已有 `receiver_id`，新逻辑不再依赖该字段。
- 本次优化第一阶段可先保留 `receiver_id`，发布新事件时允许继续写入兼容值。
- 当所有代码和脚本确认不再依赖后，再单独做删除字段迁移。

建议索引：

| 索引 | 字段 | 说明 |
| --- | --- | --- |
| `uk_event_key` | `event_key` | 事件幂等 |
| `idx_status_next_retry` | `status, next_retry_time` | 定时消费 |
| `idx_processing_time` | `status, processing_time` | 超时恢复 |
| `idx_biz_type_id` | `biz_type, biz_id` | 按业务对象排查 |
| `idx_event_type_time` | `event_type, create_time` | 按事件排查 |

### 9.2 `sys_notify_template` 通知模板/场景配置表

职责：定义某个通知场景是否启用，以及站内内容如何生成。

| 字段 | 中文含义 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `id` | 主键 | 是 | 自增主键 |
| `template_code` | 通知场景编码 | 是 | 如 `WORK_ORDER_ASSIGNED` |
| `template_name` | 通知场景名称 | 是 | 如“工单派单通知” |
| `template_source` | 模板来源 | 是 | `BUILT_IN/CUSTOM` |
| `biz_type` | 业务类型 | 是 | 如 `WORK_ORDER` |
| `event_type` | 绑定事件类型 | 是 | 该模板处理哪类事件 |
| `message_type` | 消息类型 | 是 | `TODO/EXTERNAL_NOTIFY` |
| `notify_enabled` | 场景总开关 | 是 | 0 停用，1 启用 |
| `override_enabled` | 自定义覆盖开关 | 是 | 0 使用内置，1 使用自定义 |
| `route_type` | 站内跳转类型 | 否 | 外部通知可为空或仅作后台展示 |
| `title_template` | 标题模板 | 否 | 站内消息标题或后台展示标题 |
| `summary_template` | 摘要模板 | 否 | 站内消息摘要或后台展示摘要 |
| `route_value_template` | 跳转参数模板 | 否 | 如 `${bizId}` |
| `variables_json` | 可用变量说明 | 否 | 模板变量白名单说明 |
| `remark` | 备注 | 否 | 后台说明 |
| `create_time` | 创建时间 | 是 | 统一审计字段 |
| `update_time` | 更新时间 | 是 | 统一审计字段 |

约束：

- 每个 `template_code` 必须有且仅有一条 `BUILT_IN`。
- 每个 `template_code` 最多一条 `CUSTOM`。
- 后台不允许自由新增未知 `template_code`。
- 内置模板不允许编辑和删除。
- 自定义模板允许新增、编辑、删除。

### 9.3 `sys_notify_template_channel` 通知渠道配置表

职责：定义某个通知场景在某个外部渠道上如何发送。

| 字段 | 中文含义 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `id` | 主键 | 是 | 自增主键 |
| `template_code` | 通知场景编码 | 是 | 对应 `sys_notify_template.template_code` |
| `channel_type` | 渠道类型 | 是 | 如 `MP_SUBSCRIBE/SMS/EMAIL` |
| `channel_enabled` | 渠道开关 | 是 | 0 停用，1 启用 |
| `channel_scene` | 渠道场景 | 否 | 小程序场景：`B/C` |
| `config_json` | 渠道配置 JSON | 否 | 渠道差异化配置 |
| `remark` | 备注 | 否 | 后台说明 |
| `create_time` | 创建时间 | 是 | 统一审计字段 |
| `update_time` | 更新时间 | 是 | 统一审计字段 |

小程序订阅消息 `config_json` 示例：

```json
{
  "scene": "C",
  "templateId": "",
  "pagePathTemplate": "pages/order/evaluate?workOrderId=${workOrderId}",
  "fieldMapping": [
    { "field": "thing1", "value": "${orderNo}" },
    { "field": "phone_number2", "value": "${customerMobile}" },
    { "field": "thing3", "value": "${companyName}" }
  ]
}
```

配置要求：

- 后台页面不建议让用户直接编辑原始 JSON。
- 页面应拆成“模板 ID、页面路径模板、字段映射表格、启用开关”。
- 保存时组装为 `config_json`。
- 发送前必须再次校验配置完整性。

### 20.6 失败后进入死信规则

事件失败：

- 如果 `retry_count + 1 >= eventRetryMaxCount`，设置 `status = DEAD`。

分发失败：

- 如果 `retry_count + 1 >= dispatchRetryMaxCount`，设置 `dispatch_status = DEAD`。
- 否则设置 `dispatch_status = FAILED` 和 `next_retry_time`。

```text
  1. recoverTimeoutProcessingDispatches(...)
  2. consumePendingDispatches()
```

不需要新增单独 Quartz Job，先复用现有任务即可。

## 25. 多线程协作拆分建议

### 25.1 推荐线程拆分

| 线程 | 负责阶段 | 写入范围 | 备注 |
| --- | --- | --- | --- |
| 线程 A | Phase 1 | SQL、实体、枚举 | 数据库和实体基线 |
| 线程 B | Phase 2 | notify service/handler | 等 Phase 1 完成后开始 |
| 线程 C | Phase 3 | event/dispatch service/job | 可与 Phase 4 约定接口后并行 |
| 线程 D | Phase 4 | trace controller/service/mapper | 依赖 Phase 1 字段 |
| 线程 E | Phase 5 | PC 前端通知记录页面 | 依赖 Phase 4 接口稳定 |
| 线程 F | Phase 6 | 文档和部署说明 | 可并行，但不能改代码 |
| 线程 G | Phase 7 | 测试和验收 | 所有阶段合并后执行 |

### 25.2 并行规则

- 不允许两个线程同时修改同一个 Java 类，除非提前约定写入区域。
- Phase 2 和 Phase 3 都可能修改 `NotifyEventConsumeServiceImpl`，不能并行直接改同一文件。
- Phase 3 和 Phase 4 必须先约定 Service 方法签名，再分别实现。
- 前端线程不得擅自调整后端接口路径。
- 文档线程不得把未完成阶段写成 `DONE`。

### 25.3 每个线程完成后必须输出

每个线程完成后必须在最终回复或交接记录中说明：

- 已修改文件
- 新增文件
- 关键实现点
- 已执行验证命令
- 未执行验证命令及原因
- 遗留风险
- 是否影响其它线程

### 25.4 阶段状态记录模板

每个 Phase 完成后，在本文档对应阶段下补充：

```text
阶段状态：
- 负责人：

- 修改范围：
- 验证命令：

```
