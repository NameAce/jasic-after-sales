# 佳士售后系统 - 小程序联调约定

> 本文档用于固化“小程序业务参考”和“当前系统后端 / PC 前端联调落地”之间的全局约束。
> 如无特别说明，后续涉及小程序业务对齐时，默认同时参考本文档与 `docs/00-项目协作约定.md`。

---

## 1. 文档定位

- 作用：约束本轮及后续“小程序业务参考联调”的范围边界、参考方式、确认流程和默认口径。
- 范围：约束后端与 PC/Web 前端 `jasic-ui` 的联调讨论和落地，不约束小程序源码实现。
- 不替代：`docs/00-实施清单.md`、正式需求文档、接口文档和数据库设计。
- 维护方式：当联调范围、口径或文档同步规则发生变化时，先确认，再更新本文档。

### 1.1 长期参考文档与优先级

- 默认将以下文档作为“小程序业务联调”长期上下文一起参考：
  - `docs/00-实施清单.md`
  - `docs/00-项目协作约定.md`
  - `docs/05-小程序联调拆分清单.md`
  - `docs/售后服务系统-需求规格设计方案_V1.2.md`
  - `mp/aftersale`
  - `mp/contractor`
- 其中：
  - `docs/00-实施清单.md` 用于查看 backlog 状态、已确认事项和正式业务决策
  - `docs/00-项目协作约定.md` 用于查看全局协作方式、技术栈边界和文档同步规则
  - `docs/05-小程序联调拆分清单.md` 用于查看小程序业务参考联调的模块拆分、状态和待确认事项
  - `docs/售后服务系统-需求规格设计方案_V1.2.md` 用于查看原型、交互结构、展示文案和页面信息层级
  - `mp/aftersale`、`mp/contractor` 用于查看小程序实际业务流程、页面入口和 mock 交互表达
- 优先级默认如下：
  - 对话中明确确认过的规则优先级最高
  - 其后是 `docs/00-实施清单.md` 中已确认的正式决策
  - 其后是 `docs/00-项目协作约定.md` 与本文档中的全局约束
  - 其后是 `docs/05-小程序联调拆分清单.md` 中已确认的联调分组、状态与范围边界
  - 其后是 `mp` 目录下的小程序源码表达
  - `docs/售后服务系统-需求规格设计方案_V1.2.md` 默认作为原型和展示参考，不直接覆盖已确认业务规则
- 如果小程序源码、原型文档与已确认规则或正式基线冲突，先提出变更建议，不直接按参考资料落地。

## 2. 当前联调基线

### 2.1 参考来源

- 小程序源码默认作为业务流程、页面结构、状态流转和展示意图的参考基线。
- 设计图默认只作为视觉效果和页面层级参考。
- 小程序 mock 接口、mock 数据和当前小程序代码实现，不直接作为正式系统的接口合同或落地依据。

### 2.2 实际改造范围

- 本轮所有实际变更范围仅包括：
  - 后端
  - PC/Web 前端 `jasic-ui`
- 本轮不修改小程序代码。
- 如 C 端联调调整涉及与 B 端共用的字段口径、接口语义或页面链路，必须同步评估 B 端影响；若 B 端存在对应实现，默认一并对齐，不允许 C/B 两端同名业务字段长期漂移。
- 如某项需求只能通过修改小程序代码才能成立，必须先单独提出并确认，不默认纳入当前范围。

### 2.3 默认冲突处理

- 如小程序现状与当前正式系统基线冲突，优先级默认如下：
  - 对话中已明确确认的规则
  - `docs/00-实施清单.md` 中已确认的正式决策
  - 本文档中的已确认联调口径
  - 小程序源码
  - 设计图
- 如小程序现状明显超出当前正式范围，只记录为待确认事项，不直接按其落地。

## 3. 当前默认联调口径

### 3.1 登录与身份

- 本轮只收口后端正式登录合同，不要求落地小程序登录页面改造。
- `customerName` 默认使用当前登录客户的 `nickname`；如 `nickname` 为空，则回退使用手机号。
- 小程序登录页面现状只作为参考，不作为本轮实际改造对象。

### 3.2 网点与定位

- 服务网点完整列表默认保留“地址 + 电话”口径，不展示距离，不提供导航按钮，也不返回经纬度。
- 附近网点默认必须授权定位后才允许进入对应口径。
- 若用户未授权定位，默认退回完整列表口径，不默认退化为“伪附近网点”口径。

### 3.3 建单与寄修

- 当前建单联调默认以佳士有码报修链路为主。
- 非佳士 / 无码报修当前正式结论为：不纳入本轮，不因小程序双入口现状自动落地。
- 寄修正式口径默认不再使用单文本 `shippingInfo` 兜底。
- 寄修信息默认拆分为：
  - 寄件人姓名
  - 手机号
  - 地址
- 承修方“建维修订单”正式纳入小程序业务联调主流程。

### 3.4 查单与评价

- 查单、详情、补录寄件信息等能力，默认以当前正式系统已存在能力为基线做对齐。
- 评价模型当前正式方向调整为三维评分，不再沿用单评分作为联调目标口径。
- 三维评价本轮默认同步扩展到 PC 工单详情、客户评价展示和通知字段。

### 3.5 总部与网点视图

- 总部 / 网点视图当前正式结论为：继续沿用现有 `jasic-ui` 页面结构。
- 不因小程序已有对应视图，就默认扩展出新的 PC 页面范围。

### 3.6 终端用户联调收口方式

- 因本轮不修改小程序代码，终端用户报修、查单、评价相关联调，默认按“后端合同 + PC 辅助验证”方式收口。
- 后续如需把终端用户链路改为真实小程序落地，必须单独提出并确认。

## 4. 文档与确认规则

### 4.1 文档写法

- 小程序联调清单默认按 `docs/00-实施清单.md` 的风格维护：
  - 写分组
  - 写状态
  - 写边界
  - 写已确认口径
  - 写待确认事项
- 不提前写过细的落地实现细节。

### 4.2 待确认点处理

- 只要存在影响业务方向、范围边界、权限模型、状态流转或字段口径的不确定点，先沟通确认，再写入正式文档。
- 未确认的内容只能写成：
  - 待确认
  - 阻塞
  - 后置
- 不得把猜测、默认实现或 mock 页面现状伪装成已确认结论。

### 4.3 变更同步

- 当以下内容变化时，优先同步到联调文档：
  - 本轮范围变化
  - 小程序参考边界变化
  - 全局口径变化
  - C 端调整引起的 B 端字段口径或链路对齐结论
  - 明确新增或取消的联调模块
  - 原有阻塞项被确认

---

## 5. 当前默认约定

- 默认小程序只看业务，不看其 mock 是否已实现。
- 默认实际改造对象只有后端和 `jasic-ui`。
- 默认有问题先问，确认后再写文档、再做后续推进。
- 默认联调文档不写过细实现方案，先把业务边界和正式口径收紧。
