# 客户满意度评价通知完整落地方案

## 1. 文档目的

本文档用于定义“客户满意度评价通知”场景的完整落地方案，作为后续开发、联调、测试、验收的统一基线。

本方案既要满足当前“工单关闭后给客户发送小程序评价通知”的业务诉求，也要作为消息通知三期“从单点待办升级为可扩展通知平台”的第一步落地样板。

后续实现如与本文档冲突，以本文档为准；如需变更，应先补充评审结论，再调整实现。

## 2. 目标与范围

### 2.1 目标

- 支持工单关闭后，向满足条件的客户发送“小程序客户满意度评价通知”
- 支持该通知场景进入现有通知模板后台统一管理
- 支持通知场景与渠道配置分层设计，为后续短信、邮件等渠道扩展预留统一能力
- 支持事件入库、异步分发、异步发送、失败重试、跳过原因记录
- 保持关单主流程稳定，不因通知配置问题或渠道失败影响工单关单成功

### 2.2 范围

本次方案包含以下内容：

- 新增通知场景 `WORK_ORDER_EVALUATION_INVITE`
- 工单关闭后触发通知事件发布
- 通知事件异步消费
- 渠道配置分层设计
- 小程序订阅消息渠道发送能力接入
- 分发任务表设计
- 通知模板后台扩展
- 初始化模板与默认渠道配置
- 失败重试与跳过原因记录

### 2.3 非目标

本次方案不包含以下内容：

- 后台人工重发能力
- 催评策略
- 短信、邮件、企业微信等渠道的实际发送实现
- 用户偏好设置
- 多语言模板
- 条件表达式、循环渲染、脚本化模板能力
- 渠道编排规则引擎

## 3. 已确认业务结论

### 3.1 触发时机

- 触发节点固定为“工单关闭后”
- 不在维修完成时发送

### 3.2 触发条件

仅当以下条件满足时发布评价通知事件：

- 工单主状态为 `CLOSED`
- 工单评价状态为 `PENDING_EVALUATE`

说明：

- 该条件等价于“有故障、未评价、已关闭”的业务结论
- 实现上直接复用现有 `evaluateStatus` 计算结果，不重复自行判定

### 3.3 接收人与渠道

- 接收人为客户
- 当前场景默认启用渠道为 `MP_SUBSCRIBE`
- 当前场景默认小程序端为 `WechatMiniProgramScene.C`
- 未来允许同一场景配置多个渠道，但本次只初始化并启用小程序订阅消息

### 3.4 跳转规则

- 通知点击后跳转到评价页
- 跳转路径固定为 `pages/order/evaluate`
- 传参使用 `workOrderId`
- 默认页面路径模板为 `pages/order/evaluate?workOrderId=${workOrderId}`

说明：

- `workOrderId` 只作为路由参数变量，不参与消息展示字段映射
- 小程序页面读取 `workOrderId` 后，后端仍需校验工单归属与可评价状态，不能将 `workOrderId` 视为授权凭证

### 3.5 网点名称取值

- “网点名称”取工单关单时的 `currentAcceptCompanyId` 对应公司名称

### 3.6 幂等与发送次数

- 一张工单该场景只发一次
- 不做催评
- 不做后台人工重发

### 3.7 失败与跳过策略

- 配置缺失、渠道关闭、无 openid、未订阅等业务性不可发送场景，记录为 `SKIPPED`
- 第三方接口异常、渲染异常等技术失败场景，记录为 `FAILED`
- `FAILED` 最多重试 3 次，间隔 5 分钟
- `SKIPPED` 不重试
- 事件成功入库后，后续通知失败或跳过不影响关单主流程

## 4. 整体设计原则

### 4.1 分层原则

本次方案按以下四层设计：

1. 业务事件层
   描述“发生了什么”
2. 场景模板层
   描述“这个通知场景是什么”
3. 渠道配置层
   描述“这个场景在某个渠道上如何发送”
4. 分发发送层
   描述“这一次具体发给谁、发得怎么样”

### 4.2 解耦原则

- 业务代码只负责发布事件，不直接调用微信发送
- 模板场景与渠道配置解耦
- 站内待办消息模型与外部触达渠道模型解耦
- 渠道发送实现通过统一接口扩展，不写死小程序专用逻辑

### 4.3 扩展原则

本次设计必须支持后续继续接入：

- 短信
- 邮件
- 企业微信
- B 端小程序订阅消息

因此不允许：

- 将小程序 `templateId` 直接硬塞入现有站内模板字段
- 将 `openid` 作为唯一接收人抽象
- 将小程序字段名写死在业务代码中

## 5. 运行链路设计

### 5.1 总体链路

```text
工单关闭成功
    ->
判断 evaluateStatus 是否为 PENDING_EVALUATE
    ->
写入 sys_notify_event
    ->
通知事件消费 Job
    ->
根据 templateCode 查询模板头与渠道配置
    ->
按已启用渠道生成 sys_notify_dispatch
    ->
分发发送 Job
    ->
调用具体 NotifyChannelSender
    ->
更新 dispatch 状态 / 错误信息 / 重试信息
```

### 5.2 两段式异步说明

本方案采用“两段式异步”：

1. 事件消费阶段
   负责将事件展开为分发任务
2. 分发发送阶段
   负责真正调用第三方渠道发送

这样设计的好处：

- 事件消费与渠道发送解耦
- 后续多渠道扩展更清晰
- 重试粒度更细
- 排查链路更清楚

## 6. 数据模型设计

### 6.1 复用现有表

本方案复用以下现有表：

- `work_order`
- `work_order_evaluation`
- `sys_notify_event`
- `sys_notify_template`

### 6.2 新增表一：渠道配置表

建议新增：

- `sys_notify_template_channel`

用途：

- 描述某个通知场景在某个渠道上的发送配置

建议字段如下：

| 字段 | 类型 | 非空 | 说明 |
| --- | --- | --- | --- |
| id | bigint unsigned | 是 | 主键 |
| template_code | varchar(64) | 是 | 场景模板编码 |
| channel_type | varchar(32) | 是 | 渠道类型，如 `MP_SUBSCRIBE` |
| channel_enabled | tinyint(1) | 是 | 渠道是否启用 |
| channel_scene | varchar(32) | 否 | 渠道场景，如小程序 `B/C` |
| config_json | text | 是 | 渠道专属配置 JSON |
| remark | varchar(255) | 否 | 备注 |
| create_by | varchar(64) | 否 | 创建人 |
| create_time | datetime | 是 | 创建时间 |
| update_by | varchar(64) | 否 | 更新人 |
| update_time | datetime | 是 | 更新时间 |

建议索引：

- `uk_template_channel(template_code, channel_type, channel_scene)`
- `idx_channel_enabled(channel_type, channel_enabled)`

说明：

- `config_json` 用于承载不同渠道的差异化配置
- 不建议把小程序、短信、邮件的所有配置摊平成表字段

### 6.3 新增表二：分发任务表

建议新增：

- `sys_notify_dispatch`

用途：

- 描述一条通知事件拆出来的具体发送任务

建议字段如下：

| 字段 | 类型 | 非空 | 说明 |
| --- | --- | --- | --- |
| id | bigint unsigned | 是 | 主键 |
| event_id | bigint unsigned | 是 | 来源通知事件 ID |
| template_code | varchar(64) | 是 | 场景模板编码 |
| channel_type | varchar(32) | 是 | 渠道类型 |
| receiver_type | varchar(32) | 是 | 接收人类型 |
| receiver_id | bigint unsigned | 否 | 接收人 ID |
| receiver_address | varchar(128) | 否 | 接收地址快照，如 openid/手机号/邮箱 |
| biz_type | varchar(64) | 是 | 业务类型 |
| biz_id | bigint unsigned | 是 | 业务主键 |
| biz_no | varchar(64) | 否 | 业务编号 |
| dispatch_status | varchar(32) | 是 | 分发状态 |
| result_code | varchar(64) | 否 | 结果码 |
| result_message | varchar(500) | 否 | 结果说明 |
| retry_count | int | 是 | 已重试次数 |
| next_retry_time | datetime | 否 | 下次重试时间 |
| payload_json | text | 否 | 变量快照 / 发送上下文快照 |
| channel_response_json | text | 否 | 第三方返回快照 |
| sent_time | datetime | 否 | 成功发送时间 |
| create_time | datetime | 是 | 创建时间 |
| update_time | datetime | 是 | 更新时间 |

建议索引：

- `uk_dispatch_biz_channel_receiver(biz_type, biz_id, template_code, channel_type, receiver_type, receiver_id)`
- `idx_dispatch_status_retry(dispatch_status, next_retry_time)`
- `idx_event_id(event_id)`

说明：

- `receiver_id` 用于表达接收对象身份
- `receiver_address` 存具体发送地址快照
- 对当前场景，`receiver_type = CUSTOMER`，`receiver_address = openid`

### 6.4 config_json 结构设计

`sys_notify_template_channel.config_json` 对于 `MP_SUBSCRIBE` 渠道建议结构如下：

```json
{
  "scene": "C",
  "templateId": "",
  "pagePathTemplate": "pages/order/evaluate?workOrderId=${workOrderId}",
  "fieldMapping": [
    { "field": "thing1", "value": "${orderNo}" },
    { "field": "phone_number2", "value": "${customerMobile}" },
    { "field": "thing3", "value": "${companyName}" }
  ]
}
```

字段说明：

- `scene`
  指小程序场景，允许后续配置 `B` 或 `C`
- `templateId`
  微信订阅消息模板 ID
- `pagePathTemplate`
  点击消息后的跳转页面模板
- `fieldMapping`
  微信模板字段与系统变量的映射关系

## 8. 变量设计

### 8.1 变量快照策略

本场景采用“发布事件时快照”策略。

建议写入事件或分发上下文的变量包括：

- `workOrderId`
- `orderNo`
- `customerId`
- `customerMobile`
- `customerOpenid`
- `companyId`
- `companyName`
- `closedTime`

这样设计的好处：

- 发送内容不受后续业务数据变更影响
- 事件消费时减少二次查表
- 更利于后续多渠道共用

### 8.2 变量分组

建议将变量分为两类：

1. 展示变量
   用于小程序模板消息字段映射
2. 路由变量
   用于页面跳转模板渲染

### 8.3 展示变量

建议支持：

- `orderNo`
- `customerMobile`
- `companyName`
- `closedTime`

### 8.4 路由变量

建议支持：

- `workOrderId`

说明：

- `workOrderId` 仅用于 `pagePathTemplate`
- 不在 `fieldMapping` 中展示给用户

## 9. 模板设计

### 9.1 场景名称

- 模板名称：`客户满意度评价通知`
- 模板编码：`WORK_ORDER_EVALUATION_INVITE`

### 9.2 业务语义

本场景意图是：

- 告知客户该工单已完成闭环并可评价
- 引导客户尽快进入评价页提交满意度评价

### 9.3 默认展示字段建议

推荐展示字段如下：

- 维修工单：`${orderNo}`
- 联系电话：`${customerMobile}`
- 网点名称：`${companyName}`

如微信模板允许，也可补充：

- 关闭时间：`${closedTime}`

### 9.4 默认字段映射示例

默认初始化示例建议为：

```json
[
  { "field": "thing1", "value": "${orderNo}" },
  { "field": "phone_number2", "value": "${customerMobile}" },
  { "field": "thing3", "value": "${companyName}" }
]
```

如实际模板包含时间字段，可改为：

```json
[
  { "field": "thing1", "value": "${orderNo}" },
  { "field": "phone_number2", "value": "${customerMobile}" },
  { "field": "thing3", "value": "${companyName}" },
  { "field": "time4", "value": "${closedTime}" }
]
```

说明：

- 字段名应以实际申请到的微信订阅消息模板为准
- 初始化 SQL 中可先写默认示例，后续由管理员按真实模板字段调整

### 10.1 页面策略

不新增独立菜单，继续使用现有通知模板管理页，并在模板详情中扩展“渠道配置”区域。

### 10.2 模板头配置

在现有 `sys_notify_template` 上继续维护：

- 模板编码
- 模板名称
- 事件类型
- 变量说明
- 场景开关

### 10.3 渠道配置区域

针对每个模板场景，新增渠道配置子区域。

对本场景，默认初始化一条：

- `channel_type = MP_SUBSCRIBE`

## 11. 配置校验设计

### 11.1 保存时校验

保存渠道配置时应校验：

- `templateId` 非空
- `pagePathTemplate` 非空
- `pagePathTemplate` 中出现的变量必须属于允许变量集
- `fieldMapping` 不能为空
- `fieldMapping.field` 非空
- `fieldMapping.value` 非空
- `fieldMapping.value` 中出现的变量必须属于允许变量集

### 11.2 允许的表达式能力

第一版仅支持：

- 纯变量：`${orderNo}`
- 固定文本：`佳士售后服务`

不支持：

- 条件判断
- 循环
- 函数
- 任意表达式

### 11.3 发送时兜底校验

发送前仍需再次校验：

- 渠道配置是否完整
- `templateId` 是否为空
- `pagePathTemplate` 是否能成功渲染
- `fieldMapping` 是否能成功渲染

如校验失败：

- 不抛出阻断业务的异常
- 将当前分发任务标记为 `SKIPPED` 或 `FAILED`
- 写入 `result_code` 与 `result_message`

## 12. 类职责设计

### 12.1 业务发布层

建议新增或扩展：

- `WorkOrderNotifyFacade`
- `publishEvaluationInviteEvent(...)`

职责：

- 在工单关闭成功后发布评价邀请事件
- 只负责事件入库，不直接发微信

### 12.2 事件处理层

建议新增抽象：

- `NotifyEventHandler`

建议新增实现：

- `WorkOrderEvaluationInviteEventHandler`

职责：

- 识别 `WORK_ORDER_EVALUATION_INVITE`
- 查询模板头与渠道配置
- 生成分发任务

### 12.3 渠道发送层

建议新增抽象：

- `NotifyChannelSender`

方法建议：

- `boolean supports(String channelType)`
- `SendResult send(ChannelSendContext context)`

建议新增实现：

- `MiniProgramSubscribeSender`

职责：

- 解析 `config_json`
- 渲染 `pagePathTemplate`
- 组装微信模板消息字段
- 调用现有 `WechatMiniProgramService.sendSubscribeMessage(...)`

### 12.4 分发服务层

建议新增：

- `NotifyDispatchService`

职责：

- 创建分发任务
- 查询待发送任务
- 更新状态
- 处理重试
- 记录结果码与结果信息

## 13. 关单触发设计

### 13.1 触发位置

在工单关闭成功后触发。

当前建议挂在：

- `WorkOrderServiceImpl.close(...)`

在以下逻辑之后：

- 工单主状态更新成功
- 评价状态更新成功
- 关闭时间写入成功

### 13.2 发布条件

只有当：

- `workOrder.getEvaluateStatus() == PENDING_EVALUATE`

时才发布 `WORK_ORDER_EVALUATION_INVITE`。

### 13.3 事件键设计

建议使用唯一幂等键：

`WORK_ORDER_EVALUATION_INVITE:{workOrderId}:{customerId}`

这样可以确保：

- 同一工单
- 同一客户
- 同一评价邀请场景

只会生成一条事件。

## 14. 分发幂等设计

建议对 `sys_notify_dispatch` 增加幂等约束：

- `biz_type`
- `biz_id`
- `template_code`
- `channel_type`
- `receiver_type`
- `receiver_id`

这样即使事件重复消费，也不会重复生成同一接收人的同一渠道任务。

## 15. 发送状态与结果记录设计

### 15.1 状态定义

- `PENDING`
  已创建待发送
- `PROCESSING`
  正在发送
- `SUCCESS`
  已发送成功
- `FAILED`
  技术失败，可重试
- `SKIPPED`
  业务跳过，不重试

### 15.2 结果记录要求

无论成功、失败、跳过，都必须记录：

- `result_code`
- `result_message`

如有第三方返回结果，还应记录：

- `channel_response_json`

### 15.3 示例

1. 渠道关闭

- `dispatch_status = SKIPPED`
- `result_code = SKIPPED_CHANNEL_DISABLED`
- `result_message = MP_SUBSCRIBE 渠道未启用`

2. 渠道配置缺少模板 ID

- `dispatch_status = SKIPPED`
- `result_code = SKIPPED_CHANNEL_CONFIG_MISSING`
- `result_message = 渠道配置缺少 templateId`

3. 客户未绑定 openid

- `dispatch_status = SKIPPED`
- `result_code = SKIPPED_OPENID_MISSING`
- `result_message = 客户未绑定小程序 openid`

4. 用户未订阅

- `dispatch_status = SKIPPED`
- `result_code = SKIPPED_USER_NOT_SUBSCRIBED`
- `result_message = 用户未订阅客户满意度评价通知`

5. 微信接口异常

- `dispatch_status = FAILED`
- `result_code = FAILED_CHANNEL_REQUEST`
- `result_message = 微信订阅消息发送失败：{微信返回错误}`

## 16. 重试策略

仅对 `FAILED` 状态任务进行重试。

建议策略如下：

- 最大重试次数：3 次
- 重试间隔：5 分钟
- `SKIPPED` 不重试
- `SUCCESS` 不重试

建议在 Job 中按以下条件取数：

- `dispatch_status in (PENDING, FAILED)`
- `retry_count < 3`
- `next_retry_time <= now()`

## 17. 初始化数据建议

### 17.1 模板头初始化

建议初始化：

- `template_code = WORK_ORDER_EVALUATION_INVITE`
- `template_name = 客户满意度评价通知`
- `event_type = WORK_ORDER_EVALUATION_INVITE`
- `biz_type = WORK_ORDER`
- `message_type = EXTERNAL_NOTIFY`
- `notify_enabled = 1`

### 17.2 渠道配置初始化

建议初始化一条：

- `template_code = WORK_ORDER_EVALUATION_INVITE`
- `channel_type = MP_SUBSCRIBE`
- `channel_scene = C`
- `channel_enabled = 1`

默认 `config_json` 示例：

```json
{
  "scene": "C",
  "templateId": "",
  "pagePathTemplate": "pages/order/evaluate?workOrderId=${workOrderId}",
  "fieldMapping": [
    { "field": "thing1", "value": "${orderNo}" },
    { "field": "phone_number2", "value": "${customerMobile}" },
    { "field": "thing3", "value": "${companyName}" }
  ]
}
```

说明：

- `templateId` 留空，待真实微信模板申请完成后配置
- `fieldMapping` 为默认示例

## 18. 风险与兜底策略

### 18.1 风险点

- 微信模板字段名与默认示例不一致
- 客户未授权订阅消息
- 客户未绑定 openid
- 后台配置缺失或配置错误
- 微信渠道接口偶发失败

### 18.2 兜底策略

- 业务事件始终成功入库
- 配置问题或接收人问题按 `SKIPPED` 处理
- 第三方技术失败按 `FAILED` 处理并重试
- 不因通知问题阻断关单主流程
- 保存时强校验，运行时再次兜底校验

## 19. 验收建议

建议按以下用例验收：

1. 有故障工单关闭后，生成评价邀请事件
2. 事件消费后生成一条小程序分发任务
3. 渠道配置完整时，成功发送小程序订阅消息
4. 点击消息后跳转到 `pages/order/evaluate`，并带上 `workOrderId`
5. 已评价工单不会再次发送
6. 无故障工单关闭后不会发送
7. 无 openid 时记录 `SKIPPED_OPENID_MISSING`
8. 未订阅时记录 `SKIPPED_USER_NOT_SUBSCRIBED`
9. 微信接口异常时记录 `FAILED_CHANNEL_REQUEST` 并按策略重试
10. 同一工单同一客户不会重复生成评价通知

## 20. 本次方案结论

本方案确认“客户满意度评价通知”作为消息通知平台化的第一批落地场景，采用“事件入库 -> 分发任务 -> 渠道发送”的统一架构，不将小程序通知直接写死在业务层，也不与现有站内待办模型混用。

当前场景先落地 `MP_SUBSCRIBE + C 端小程序`，同时通过模板头、渠道配置、分发任务、统一 Sender 抽象，为后续短信、邮件、B 端小程序等渠道扩展预留完整空间。
