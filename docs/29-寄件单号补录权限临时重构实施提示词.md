# 29-寄件单号补录权限临时重构实施提示词

你现在在 `E:\桌面\jasic-after-sales` 项目中工作，请严格按以下要求完成“寄件单号补录权限临时重构”。

## 一、必须遵守的参考文档

1. 优先阅读并严格遵守：
   - `docs/00-项目协作约定.md`
   - `docs/28-寄件单号补录权限临时重构方案.md`

2. 本轮实现只能以 `docs/28-寄件单号补录权限临时重构方案.md` 作为业务基线。

3. 不要擅自回退到旧实现口径，不要擅自复用历史理解覆盖本轮确认结论。

## 二、本轮目标

将 B 端“上传寄件单号”能力从“当前受理方 + 派单权限”口径，重构为“建单人本人补录”口径，且本轮采用不改表的临时方案。

本轮必须完成以下目标：

1. B 端“上传寄件单号”动作仅允许建单人本人操作。
2. 临时通过首条 `CREATE` 流转记录的 `operatorUserId` 识别建单人。
3. 状态窗口沿用“待接单”口径：
   - `PENDING_ASSIGN`
   - `PENDING_TECH_ACCEPT`
4. 按钮只放列表，不放详情。
5. 只要建单人本人能看到该工单的列表，就允许展示按钮，包括“历史转出/只读”列表。
6. 不再按 `currentAcceptCompanyId`、`workorder:assign`、派单岗、调度岗、当前承接方等口径控制该动作。
7. 旧数据查不到首条 `CREATE` 流转，或者 `operatorUserId` 为空时，不允许补录。
8. C 端与 B 端并存时，按“最后一次提交生效”口径实现，不做额外互斥。

## 三、明确禁止事项

本轮禁止做以下事情：

1. 禁止修改业务基线为“当前受理方可补录”。
2. 禁止继续把“上传寄件单号”当作派单/调度动作处理。
3. 禁止为了兼容旧数据而放宽为“建单公司可补录”“当前受理公司可补录”“有派单权限即可补录”。
4. 禁止新增正式数据库字段，例如：
   - `create_user_id`
   - `creator_user_id`
5. 禁止顺手重构无关权限逻辑。
6. 禁止删除未改动区域原有注释。
7. 禁止为了方便阅读或减少 diff，随意清理旧注释。

## 四、实现提示

你应优先检查并调整以下区域，但以实际代码结构为准：

1. B 端工单权限判断服务
2. B 端工单列表可执行动作生成逻辑
3. B 端列表按钮展示逻辑
4. B 端“上传寄件单号”接口最终业务校验
5. 与首条 `CREATE` 流转查询相关的服务或 mapper

你在实现时必须特别注意以下事实：

1. `work_order` 主表当前没有正式 `createUserId` 字段。
2. `work_order_flow` 中已有 `actionType` 和 `operatorUserId`。
3. 建单时已写入 `CREATE` 流转，因此可以临时从首条 `CREATE` 流转回溯建单人。
4. 当前代码中可能已有 `createCompanyId`、`createEntryType`、`CREATOR_COMPANY` 等概念，但本轮不要把它们误当成“建单人本人”。
