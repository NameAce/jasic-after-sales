# 三类主体首页重构口径设计方案

## 1. 文档定位

本文档用于固化本轮确认后的首页重构方案，作为后续另起线程进行 `jasic-ui-antd` 首页重构优化的业务和技术基线。

本文档优先级低于后续线程中用户明确更新的最新口径；如果后续实现时发现本文档、当前代码、历史文档或实际数据之间存在冲突，应先说明冲突点、影响范围和建议处理方式，再继续落地。

本次方案只覆盖 B 端首页，不覆盖小程序端，不覆盖客户首页，不要求兼容首页相关历史代码。后续实现时，首页历史代码能复用则复用，不能复用可以直接删除，不需要为了保留历史设计而继续维护旧组件、旧接口、旧字段或旧文案。

## 2. 最终确认结论

### 2.1 首页主体范围

本期首页只保留三类主体：

| 主体 | 首页命名 | 本期定位 |
| --- | --- | --- |
| 平台主体 | 治理看板 | 平台级组织、账号、基础配置治理入口 |
| 总部主体 | 调度看板 | 总部当前承接工单池的调度和状态概览 |
| 服务网点主体 | 服务工作台 | 当前服务公司的承接工单和执行入口 |

客户主体首页本期不做。

服务网点主体一二级统一处理，不单独做一级管理二级的专属首页。

### 2.2 明确不做范围

本期不做以下内容：

- 客户首页。
- 三类主体的“我的事项”模块。
- SLA 指标。
- 风险指标。
- 总部的网点履约监控。
- 平台首页的工单相关数据。
- 平台首页的 CRM 同步状态。
- 平台首页的消息治理。
- 平台首页的趋势图。
- 平台基础配置完整度、评分、健康度等复杂质量指标。

### 2.3 核心约束

首页工单相关数据必须尽量和工单列表对得上。

具体要求是：

```text
首页卡片数字
= 首页指标统计条件
= 点击后 routeName + query 表达的筛选条件
= 工单列表后端查询条件
= 同条件工单列表 total
```

后续不能再出现首页按一套 SQL 统计，点击后列表按另一套查询条件展示，导致卡片数字和列表总数不一致的情况。

## 3. 总体设计原则

### 3.1 主体分离

首页接口、前端页面、组合逻辑应按主体拆分：

- 平台主体只关心治理数据。
- 总部主体只关心总部当前承接和调度数据。
- 服务网点主体只关心当前服务公司的承接和执行数据。

不再把平台治理、总部调度、网点履约、个人待办、客户服务进度混在同一个首页语义里。

### 3.2 状态名称复用列表已有口径

首页工单状态名称应尽量复用工单列表已有状态名称，不创造新的模糊状态名。

当前代码中工单列表已使用的主要状态包括：

| 状态编码 | 展示语义 |
| --- | --- |
| `PENDING_ASSIGN` | 待派单 |
| `PENDING_TECH_ACCEPT` | 待接单 |
| `IN_PROGRESS` | 维修中 |
| `COMPLETED` | 已完成 |
| `CLOSED` | 已关闭 |

后续实现应以当前后端枚举、列表返回的 `mainStatusLabel`、前端工单列表实际展示文案为准。若列表状态文案调整，首页应同步复用列表文案，不在首页单独维护另一套状态翻译。

### 3.3 趋势图按事件发生时间统计

卡片数字按当前状态统计，必须能和当前列表总数对齐。

趋势图按事件发生时间统计，不强行和某个当前状态列表总数对齐。趋势图文案必须表达清楚，例如“近 7 天流入/完成/转出趋势”，避免用户误以为趋势图是当前列表存量。

趋势周期固定为近 7 天。

### 3.4 点击跳转由后端返回

首页指标点击后的跳转目标建议由首页接口返回，前端只负责跳转，不在组件内部硬编码业务筛选口径。

建议统一返回结构：

```json
{
  "routeName": "after-sales_work-order",
  "query": {
    "viewScope": "CURRENT",
    "mainStatus": "PENDING_ASSIGN"
  }
}
```

后续如果列表查询口径调整，只需要调整首页接口返回的跳转参数和后端列表筛选逻辑，不需要逐个修改首页卡片组件。

## 4. 平台主体：治理看板

### 4.1 页面定位

平台首页命名为“治理看板”。

平台首页只展示平台治理类数据，不展示任何工单相关数据。平台用户进入首页后，应看到组织、账号、基础配置三类治理概览和管理入口。

### 4.2 模块结构

建议模块：

| 模块 | 说明 |
| --- | --- |
| 组织治理 | 展示总部、服务网点、启用/停用组织等组织治理概览 |
| 账号治理 | 展示用户、角色、启用/停用账号等账号治理概览 |
| 基础配置 | 展示产品、服务类型、字典、区域等基础配置规模和入口 |

### 4.3 指标建议

#### 4.3.1 组织治理

| 指标 | 统计口径 | 点击目标 |
| --- | --- | --- |
| 总部数 | 当前系统内总部主体数量 | 组织/公司列表，筛选总部 |
| 服务网点数 | 当前系统内服务网点主体数量，一二级网点本期统一纳入服务网点 | 组织/公司列表，筛选服务网点 |
| 启用主体数 | 当前启用状态的总部和服务网点数量 | 组织/公司列表，筛选启用 |
| 停用主体数 | 当前停用状态的总部和服务网点数量 | 组织/公司列表，筛选停用 |

客户主体不作为本期首页模块展示目标。如果组织表中存在客户类主体，应在本期首页统计中排除，除非后续用户重新确认纳入。

#### 4.3.2 账号治理

| 指标 | 统计口径 | 点击目标 |
| --- | --- | --- |
| 用户总数 | 当前系统用户总数，按用户管理列表同口径统计 | 用户列表 |
| 启用用户数 | 当前启用用户数 | 用户列表，筛选启用 |
| 停用用户数 | 当前停用用户数 | 用户列表，筛选停用 |
| 角色数 | 当前系统角色数量 | 角色列表 |

账号治理不做“我的事项”，不展示个人待办。

#### 4.3.3 基础配置

基础配置本期只做规模和入口，不做完整度、评分、健康度。

可选指标：

| 指标 | 统计口径 | 点击目标 |
| --- | --- | --- |
| 产品分类数 | 当前产品分类数量 | 产品分类或产品配置列表 |
| 产品数 | 当前产品资料数量 | 产品列表 |
| 服务类型数 | 当前服务类型配置数量 | 服务类型配置 |
| 字典配置项数 | 当前字典配置项数量 | 字典管理 |
| 区域配置数 | 当前区域配置数量 | 区域配置 |

如果某些配置模块当前没有稳定菜单或列表，不要为了首页单独引入复杂新模块；可以先作为不可点击数字或仅保留入口按钮。

### 4.4 平台接口建议

建议接口：

```text
GET /dashboard/platform/home
```

建议返回结构：

```ts
interface PlatformHomeVO {
  title: '治理看板';
  organization: HomeSectionVO;
  account: HomeSectionVO;
  basicConfig: HomeSectionVO;
}

interface HomeSectionVO {
  title: string;
  metrics: HomeMetricVO[];
}

interface HomeMetricVO {
  code: string;
  title: string;
  value: number;
  unit?: string;
  routeTarget?: HomeRouteTargetVO;
}

interface HomeRouteTargetVO {
  routeName: string;
  query?: Record<string, unknown>;
}
```

平台首页接口不得调用工单统计接口，不得依赖工单表。

## 5. 总部主体：调度看板

### 5.1 页面定位

总部首页命名为“调度看板”。

总部首页只看当前总部自己的工单调度池，核心口径为当前登录总部公司作为当前承接方的工单，即与工单列表 `viewScope = CURRENT` 对齐。

本期不做总部的网点履约监控，因此不展示“承修网点数”“网点待接单”“网点维修中”“网点完成排行”等指标。

### 5.2 指标建议

总部卡片指标建议：

| 指标 | 统计口径 | 点击列表口径 |
| --- | --- | --- |
| 当前工单总量 | 当前总部承接中的全部工单 | `viewScope=CURRENT` |
| 待派单 | 当前总部承接中，主状态为 `PENDING_ASSIGN` 的工单 | `viewScope=CURRENT&mainStatus=PENDING_ASSIGN` |
| 待接单 | 当前总部承接中，主状态为 `PENDING_TECH_ACCEPT` 的工单 | `viewScope=CURRENT&mainStatus=PENDING_TECH_ACCEPT` |
| 维修中 | 当前总部承接中，主状态为 `IN_PROGRESS` 的工单 | `viewScope=CURRENT&mainStatus=IN_PROGRESS` |
| 已完成 | 当前总部承接中，主状态为 `COMPLETED` 的工单 | `viewScope=CURRENT&mainStatus=COMPLETED` |
| 已关闭 | 当前总部承接中，主状态为 `CLOSED` 的工单 | `viewScope=CURRENT&mainStatus=CLOSED` |
| 已转出 | 当前总部曾经承接且由当前总部转出的工单 | 见 5.3 |

状态名称最终以工单列表展示文案为准。

### 5.3 已转出口径

“已转出”不能简单等同于 `hasTransfer = 1`。

原因是 `hasTransfer = 1` 只能表达工单发生过转单，不能表达当前主体是转出方。如果直接使用 `hasTransfer = 1`，可能把转入后当前仍承接的工单也算进去，导致“已转出”语义不准。

建议后续落地时补齐列表查询能力，使首页和列表都能表达同一口径：

```text
transferDirection = OUT
```

建议统计条件：

```text
存在转单流水：
actionType = TRANSFER
fromCompanyId = 当前总部公司 ID
```

建议点击列表口径：

```text
routeName = after-sales_work-order
query.transferDirection = OUT
```

如果后续不想扩展列表查询参数，则首页文案不应叫“已转出”，应改成“发生过转单”。本方案推荐保留“已转出”，并扩展列表查询能力，确保数字和列表对齐。

### 5.4 趋势图

总部趋势图固定近 7 天，按事件发生时间统计。

建议趋势线：

| 趋势 | 统计口径 |
| --- | --- |
| 流入总部 | 工单进入当前总部承接池的事件数，优先基于工单流水 `toCompanyId = 当前总部公司 ID` 统计 |
| 总部完成 | 当前总部完成维修或完成处理的事件数，优先基于工单流水中的完成类动作统计 |
| 总部转出 | 当前总部转出工单事件数，基于工单流水 `actionType = TRANSFER` 且 `fromCompanyId = 当前总部公司 ID` 统计 |

趋势图不是当前状态存量，不要求点击后列表总数和某个趋势点一致。页面文案应明确“近 7 天事件趋势”。

### 5.5 总部接口建议

建议接口：

```text
GET /dashboard/hq/home
```

建议返回结构：

```ts
interface HqHomeVO {
  title: '调度看板';
  workOrderPool: HomeSectionVO;
  transfer: HomeSectionVO;
  trend: HomeTrendVO;
}

interface HomeTrendVO {
  title: string;
  days: string[];
  series: HomeTrendSeriesVO[];
}

interface HomeTrendSeriesVO {
  code: string;
  name: string;
  values: number[];
}
```

总部首页所有工单卡片统计应优先复用工单列表同一套查询构造能力，避免另写一套无法对齐的 SQL。

## 6. 服务网点主体：服务工作台

### 6.1 页面定位

服务网点首页命名为“服务工作台”。

服务网点首页一二级统一，只看当前登录服务公司的业务，不做一级网点管理二级网点的特殊首页。

核心口径为当前服务公司作为当前承接方的工单，即与工单列表 `viewScope = CURRENT` 对齐。

### 6.2 指标建议

服务工作台卡片指标建议：

| 指标 | 统计口径 | 点击列表口径 |
| --- | --- | --- |
| 当前工单总量 | 当前服务公司承接中的全部工单 | `viewScope=CURRENT` |
| 待派单 | 当前服务公司承接中，主状态为 `PENDING_ASSIGN` 的工单 | `viewScope=CURRENT&mainStatus=PENDING_ASSIGN` |
| 待接单 | 当前服务公司承接中，主状态为 `PENDING_TECH_ACCEPT` 的工单 | `viewScope=CURRENT&mainStatus=PENDING_TECH_ACCEPT` |
| 维修中 | 当前服务公司承接中，主状态为 `IN_PROGRESS` 的工单 | `viewScope=CURRENT&mainStatus=IN_PROGRESS` |
| 已完成 | 当前服务公司承接中，主状态为 `COMPLETED` 的工单 | `viewScope=CURRENT&mainStatus=COMPLETED` |
| 已关闭 | 当前服务公司承接中，主状态为 `CLOSED` 的工单 | `viewScope=CURRENT&mainStatus=CLOSED` |
| 已转出 | 当前服务公司曾经承接且由当前服务公司转出的工单 | `transferDirection=OUT` |

历史参与不做核心 KPI。可以保留为入口或筛选能力，例如跳转到工单列表：

```text
viewScope=HISTORY
```

历史参与不应和当前承接工单混在同一组核心卡片里。

### 6.3 趋势图

服务工作台趋势图固定近 7 天，按事件发生时间统计。

建议趋势线：

| 趋势 | 统计口径 |
| --- | --- |
| 接单 | 当前服务公司接单事件数，优先基于 `TECH_ACCEPT` 动作统计 |
| 完成 | 当前服务公司完成维修事件数，优先基于 `REPAIR_FINISH` 或对应完成类动作统计 |
| 转出 | 当前服务公司转出事件数，基于 `TRANSFER` 且 `fromCompanyId = 当前服务公司 ID` 统计 |

如现有流水动作与上述名称存在差异，后续实现应以当前代码中的 `WorkOrderActionEnum` 和工单流水实际字段为准。

### 6.4 服务网点接口建议

建议接口：

```text
GET /dashboard/service/home
```

建议返回结构：

```ts
interface ServiceHomeVO {
  title: '服务工作台';
  currentPool: HomeSectionVO;
  transfer: HomeSectionVO;
  historyEntry?: HomeRouteTargetVO;
  trend: HomeTrendVO;
}
```

服务网点首页统计不应按一级、二级服务网点拆出两套接口或两套页面。

## 7. 列表对齐设计

### 7.1 工单列表查询能力

当前工单列表已有核心查询字段：

| 字段 | 说明 |
| --- | --- |
| `viewScope` | `CURRENT`、`HISTORY`、`ALL` |
| `mainStatus` | `PENDING_ASSIGN`、`PENDING_TECH_ACCEPT`、`IN_PROGRESS`、`COMPLETED`、`CLOSED` |
| `displayStatus` | `ALL`、`WAIT_ACCEPT`、`IN_PROGRESS`、`COMPLETED`、`CLOSED` |
| `hasTransfer` | 是否发生过转单 |

本期首页核心状态卡片优先使用 `viewScope + mainStatus` 对齐列表。

### 7.2 建议新增转出筛选

为保证“已转出”语义准确，建议新增列表筛选字段：

```ts
transferDirection?: 'OUT';
```

后端查询含义：

```text
transferDirection = OUT
表示当前登录公司作为转出方的工单。
```

后端可通过工单流水表判断：

```text
actionType = TRANSFER
fromCompanyId = 当前登录公司 ID
```

如果列表需要展示转出后当前不再承接的工单，应允许该筛选不被 `viewScope=CURRENT` 限制。具体可设计为：

```text
query.transferDirection = OUT
```

由后端根据当前登录主体自动限定转出方，不允许前端传入任意公司 ID 绕过权限。

### 7.3 首页指标和列表总数校验

后续开发应对每个工单卡片建立校验关系：

| 首页指标 | 列表 query | 验证方式 |
| --- | --- | --- |
| 当前工单总量 | `viewScope=CURRENT` | 首页值等于列表 total |
| 待派单 | `viewScope=CURRENT&mainStatus=PENDING_ASSIGN` | 首页值等于列表 total |
| 待接单 | `viewScope=CURRENT&mainStatus=PENDING_TECH_ACCEPT` | 首页值等于列表 total |
| 维修中 | `viewScope=CURRENT&mainStatus=IN_PROGRESS` | 首页值等于列表 total |
| 已完成 | `viewScope=CURRENT&mainStatus=COMPLETED` | 首页值等于列表 total |
| 已关闭 | `viewScope=CURRENT&mainStatus=CLOSED` | 首页值等于列表 total |
| 已转出 | `transferDirection=OUT` | 首页值等于列表 total |

总部和服务网点都应执行同样校验。

## 8. 前端设计建议

### 8.1 技术边界

本期前端目标为 `jasic-ui-antd`。

后续实现应沿用 `jasic-ui-antd` 当前的 Vue、Ant Design Vue、路由、请求封装、主题变量和组件组织方式，不引入新的前端技术栈。

### 8.2 页面组织

建议首页入口继续根据当前登录主体分流：

| 主体 | 页面组件建议 |
| --- | --- |
| 平台 | `platform-governance-home` |
| 总部 | `hq-dispatch-home` |
| 服务网点 | `service-workbench-home` |

实际文件命名应贴合当前项目目录习惯。

### 8.3 删除历史首页代码

首页相关历史代码不需要保留兼容。

后续实现时可以删除：

- 不再使用的旧首页组件。
- 不再使用的旧首页组合函数。
- 不再使用的旧首页 API 类型。
- 不再使用的旧首页跳转逻辑。
- 不再使用的旧图表模块。

删除前应确认没有其它页面引用。未被本次首页重构触达的非首页代码和注释，不要为了方便阅读随意删除。

### 8.4 前端交互规则

工单卡片点击：

- 如果接口返回 `routeTarget`，前端按 `routeName + query` 跳转。
- 如果接口没有返回 `routeTarget`，卡片只展示数字，不做点击。
- 前端不在卡片组件里自行拼业务筛选条件。

平台治理卡片点击：

- 有明确管理列表的，跳转对应列表。
- 没有稳定列表或菜单的，先不点击或跳到稳定入口。

趋势图点击：

- 本期不要求趋势点点击。
- 如果后续要做趋势点点击，必须单独定义事件日期和事件类型筛选条件，不能复用当前状态列表筛选条件。

## 9. 后端设计建议

### 9.1 分层约定

后端沿用当前项目分层：

```text
Controller -> Service -> Mapper
```

对象命名沿用：

```text
Entity / DTO / VO / Query
```

不引入新框架、新中间件、新存储方案或新的任务系统。

### 9.2 Controller 建议

建议按主体拆分首页接口：

```text
PlatformDashboardController
HqDashboardController
ServiceDashboardController
```

建议路由：

```text
GET /dashboard/platform/home
GET /dashboard/hq/home
GET /dashboard/service/home
```

如当前项目已有稳定首页 Controller，也可以在不扩大复杂度的前提下复用，但接口语义必须按主体清晰拆分。

### 9.3 Service 建议

首页 Service 不应直接拼散乱 SQL 口径。

工单相关统计建议复用或抽取与工单列表一致的查询构造能力：

```text
首页统计 Query
-> 工单权限上下文解析
-> 与列表一致的 scoped query
-> count
```

这样可以保证首页数字和列表 `total` 对齐。

### 9.4 Mapper 建议

如果现有 Mapper 已有列表统计能力，应优先复用。

如果必须新增首页聚合 SQL，应满足：

- 与列表查询条件使用同一套权限上下文。
- 与列表查询条件使用同一套状态过滤规则。
- 对新增 SQL 补充清晰注释，说明业务口径和为什么不能直接复用现有 SQL。
- 不为了首页性能提前引入缓存，除非后续压测或实际使用证明必要。

## 10. 注释和代码清理要求

后续实现必须严格遵守以下注释要求：

- 所有新增、修改或重构的代码，都必须补充完整且清晰的简体中文注释。
- 新增或重构类、接口时，应说明业务职责、适用范围、边界条件、关键流程和与其它模块的关系。
- 新增或重构方法时，应说明方法的业务目的、参数含义、返回值含义、核心处理流程，以及可能出现的异常场景、特殊分支或兼容处理。
- 方法内部关键业务步骤必须补充注释，重点说明业务目的和设计原因。
- 方法内部调用其它方法时，如果调用原因不够直观，必须在调用前说明为什么调用、希望达成什么业务效果，以及不调用会有什么影响。
- 注释应解释业务语义、约束条件和设计意图，不要只翻译代码字面含义。
- 修改代码时必须同步检查并更新相关注释，确保注释和实际实现一致。
- 未改动的代码区域，不得为了方便阅读、个人习惯或压缩篇幅随意删除原有注释。
- 如果原有注释与修改后的逻辑不一致，应一并修正。
- 如果原有注释仍然准确，应保留，不要随意清理。

首页相关历史代码可以完全不考虑兼容。能复用的复用，用不上的直接删除，不要保留废弃组件、废弃字段、废弃接口或废弃注释制造维护成本。

## 11. 单阶段落地建议

本期首页重构建议按一个阶段闭环落地，不再拆成多个实施阶段。

虽然实施过程内部仍可按“后端口径、前端页面、联调验收”的顺序推进，但对外交付应作为一次完整首页重构处理，避免中间状态长期存在旧首页和新首页并行、首页数字和列表口径不一致、旧组件未清理等问题。

目标：

- 固化三类首页接口返回结构。
- 平台首页只返回组织、账号、基础配置数据。
- 总部和服务网点首页工单卡片统计与工单列表查询条件对齐。
- 补齐“已转出”所需的列表查询口径，例如 `transferDirection=OUT`。
- 补齐近 7 天事件趋势统计。
- `jasic-ui-antd` 首页按平台、总部、服务网点三类主体展示不同页面。
- 平台展示治理看板。
- 总部展示调度看板。
- 服务网点展示服务工作台。
- 首页卡片跳转完全使用后端返回的 `routeTarget`。
- 删除不再使用的旧首页组件、旧组合函数、旧图表模块和旧 API 类型。
- 校验首页数字和列表总数。
- 校验不同主体权限下的数据边界。
- 校验趋势图近 7 天数据。
- 补齐必要的单元测试、Mapper 合约测试或接口级验证。

验收重点：

- 平台首页接口不查询工单表。
- 总部和服务网点每个工单卡片数字都能用列表同条件查出一致 `total`。
- 趋势图按事件发生时间统计，周期固定近 7 天。
- 三类主体进入首页后看到的模块符合本文档范围。
- 首页没有“我的事项”。
- 平台首页没有任何工单指标。
- 总部首页没有网点履约监控。
- 服务网点首页没有一级管理二级的专项模块。
- 不存在无引用的首页旧文件。
- 不存在首页旧接口继续被前端调用。
- 不存在首页卡片数字和列表总数明显不一致的问题。
- 注释与实际代码一致。
