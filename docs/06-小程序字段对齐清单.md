# 佳士售后系统 - 小程序字段对齐清单

> 本文档用于承接“以小程序字段为标准做增量对齐”的确认结果。
> 本轮只判断后端是否已有业务承载位，不要求字段名、接口名、返回结构与小程序完全一致。
> 小程序有而后端无的字段，整理为待补项；后端多出的字段，当前只登记待确认，不在本轮先删改。

---

## 1. 使用说明

### 1.1 参考范围

- 默认同时参考：
  - `docs/00-项目协作约定.md`
  - `docs/00-实施清单.md`
  - `docs/05-小程序联调拆分清单.md`
  - `mp/aftersale`
  - `mp/contractor`
- 本文档只服务于“字段是否存在”的增量核对，不负责接口命名、字段命名、结构重组的兼容方案。

### 1.2 状态说明

- `待补齐`：小程序业务字段已明确使用，后端当前没有稳定承载位
- `待单独确认`：字段存在，但更偏增强展示或扩展能力，需单独确认是否纳入本轮
- `本轮不纳入`：字段所在业务范围当前已有正式结论，不进入本轮补齐

### 1.3 判断原则

- 只看业务语义是否有承载位，不要求字段名完全一致。
- 只要后端某处已有稳定字段能承载该业务语义，就不记为缺失。
- 展示文案、时间轴标题、前端拼接结果这类可派生内容，不默认记为字段缺口。
- 小程序 mock 中明显属于演示性质的字段，不自动视为本轮正式必补字段。

---

## 2. 当前总体判断

- 当前后端对工单主链核心字段的承载已经比较完整，缺口主要集中在“媒体类字段”和“增强展示字段”。
- 当前最值得优先补的，不是状态流转或主表主键字段，而是小程序已实际使用、后端却没有承载位的图片、语音、回寄收件信息等字段。
- 当前更适合按场景拆分补齐，而不是按接口逐个调整。

## 4. 当前建议的落地顺序

1. 先补 `G1 建单与网点字段`
原因：这些字段最靠近建单主链，补齐后能直接支撑 C/B 两端基础合同完善。

2. 再补 `G3 收尾回寄字段`
原因：字段相对独立，业务语义清晰，不容易和状态机产生额外冲突。

3. 再补 `G2 工单详情与故障媒体字段`
原因：这组字段通常依赖前面建单媒体先有稳定承载，再做详情回显更稳妥。

4. 然后补 `G4 故障点历史字段`
原因：这部分偏结构化展示增强，适合在主链媒体字段稳定后收口。

5. `G5 增强展示字段` 单独确认后再决定是否进入本轮。

---

## 5. 当前结论

- 当前后端核心业务字段并不缺主链字段，缺口主要是媒体类字段、回寄收件字段和结构化历史展示字段。
- 当前最适合按场景分批补，不建议一次性把所有 mock 展示字段都并入正式模型。
- 本文档用于后续逐项确认和逐项落地；在你明确确认某一组后，再进入代码和数据库调整。
