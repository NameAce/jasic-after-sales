# 消息通知二期模板后台配置落地方案

## 1. 文档目的

本文档用于定义消息通知二期“模板后台配置”能力的完整落地方案，作为后续开发、联调、测试、验收的统一基线。

二期不再以“新增多少通知场景”为主目标，而是优先补齐“模板后台配置”基础能力，使后续新增通知节点时不再依赖硬编码标题、摘要和跳转信息。

后续实现如与本文档冲突，以本文档为准；如需变更，应先补充评审结论，再调整实现。

## 2. 二期目标与范围

### 2.1 二期目标

二期聚焦以下目标：

- 支持 B 端站内消息模板后台配置
- 支持平台管理员维护通知模板的内容、跳转方式和开关
- 支持模板预览、缓存刷新和运行时兜底
- 将一期已上线的 `WORK_ORDER_ASSIGNED` 场景改为通过模板生成消息内容
- 保持一期现有事件链路、接收人逻辑、状态流转逻辑不变

### 2.2 二期范围

二期包含以下内容：

- 通知模板数据表
- 内置模板初始化数据
- 平台管理员后台管理页面
- 模板查询、新增自定义覆盖、编辑、删除、预览、刷新缓存
- 模板渲染服务
- 运行时模板回退与错误日志
- 一期 `WORK_ORDER_ASSIGNED` 接入模板渲染

### 2.3 二期非目标

二期不包含以下内容：

- 客户端通知
- 短信、邮件、公众号、小程序订阅消息
- 模板触发规则配置
- 接收人规则配置
- 用户偏好配置
- 审核发布流
- 多公司、多角色、多语言模板隔离
- 任意表达式、条件判断、循环渲染
- 平台管理员以外角色的模板维护权限

## 3. 已确认设计结论

### 3.1 用户与渠道边界

- 二期模板配置只服务 B 端站内消息
- 模板作用范围为全局一套
- 仅 `PLATFORM admin` 可维护模板配置

### 3.2 场景边界

- 二期先只接一期已上线场景 `WORK_ORDER_ASSIGNED`
- 模板编码不允许后台自由新增
- 当前只允许系统预置场景编码

### 3.3 模板职责边界

模板只负责以下内容：

- 标题
- 摘要
- 跳转配置
- 场景开关
- 自定义覆盖开关

模板不负责以下内容：

- 触发时机
- 接收人
- 消息状态流转
- 业务动作驱动的 `DONE/INVALID`

### 3.4 模板形态

每个 `templateCode` 采用固定模型：

- 一条内置模板
- 最多一条自定义模板

说明：

- 内置模板通过初始化 SQL 预置入库
- 内置模板不允许编辑、不允许删除、只允许查看
- 自定义模板允许新增、编辑、删除
- 删除自定义模板后，系统自动回退内置模板

### 3.5 开关语义

二期拆分两个开关字段：

- `notifyEnabled`：通知总开关，控制该场景是否发送通知
- `overrideEnabled`：自定义覆盖开关，控制是否使用自定义模板内容

语义如下：

- 无自定义模板：默认按内置模板正常发送
- 存在自定义模板且 `notifyEnabled=0`：该场景整体不发通知
- 存在自定义模板且 `notifyEnabled=1`、`overrideEnabled=0`：回退使用内置模板内容
- 存在自定义模板且 `notifyEnabled=1`、`overrideEnabled=1`：使用自定义模板内容

### 3.6 渲染规则

- 模板变量只支持简单占位符替换
- 占位符格式固定为 `${variableName}`
- 不支持条件判断、循环、脚本和表达式
- 保存时校验占位符是否合法
- 预览时校验并提示
- 运行时如果自定义模板渲染失败，回退到内置模板，同时记录错误日志

### 3.7 跳转规则

- 跳转配置纳入模板
- 模板字段包含 `routeType` 与 `routeValueTemplate`
- `routeType` 改为枚举选择
- 二期先只开放 `WORK_ORDER_DETAIL`

## 4. 总体设计

### 4.1 设计原则

二期采用“半配置化”方案：

- 业务代码继续决定何时发通知
- 业务代码继续决定发给谁
- 模板系统决定通知内容如何生成
- 模板系统决定该场景是否发送

### 4.2 与一期关系

一期已经具备以下能力：

- 通知事件表 `sys_notify_event`
- 通知消息表 `sys_notify_message`
- 通知日志表 `sys_notify_message_log`
- 异步消费任务
- 站内待办状态流转
- 消息中心与红点

二期不推翻一期设计，只替换“消息内容生成”这一步。

### 4.3 二期运行链路

```text
工单业务发布事件
    ->
通知事件异步消费
    ->
根据 eventType/templateCode 查找模板
    ->
判定 notifyEnabled / overrideEnabled
    ->
渲染标题、摘要、跳转值
    ->
创建 sys_notify_message
    ->
写入 sys_notify_message_log
```

## 5. 数据模型设计

### 5.1 表设计原则

二期不复用 `sys_config`，单独建设模板表。原因如下：

- 模板是结构化对象，不是简单 key/value
- 后续需要支持预览、变量说明、覆盖开关、模板类型等能力
- 独立表更适合查询、缓存和后续扩展

### 5.2 表名

建议新增：

- `sys_notify_template`

### 5.3 字段设计

| 字段 | 类型 | 非空 | 说明 |
| --- | --- | --- | --- |
| id | bigint unsigned | 是 | 主键 |
| template_code | varchar(64) | 是 | 模板编码，当前固定 `WORK_ORDER_ASSIGNED` |
| template_name | varchar(128) | 是 | 模板名称 |
| template_source | varchar(16) | 是 | 模板来源：`BUILT_IN` / `CUSTOM` |
| biz_type | varchar(64) | 是 | 业务类型，当前固定 `WORK_ORDER` |
| event_type | varchar(64) | 是 | 事件类型，当前固定 `WORK_ORDER_ASSIGNED` |
| message_type | varchar(32) | 是 | 消息类型，当前固定 `TODO` |
| notify_enabled | tinyint(1) | 是 | 通知总开关：1启用，0停用 |
| override_enabled | tinyint(1) | 是 | 自定义覆盖开关：1覆盖，0不覆盖 |
| route_type | varchar(32) | 是 | 跳转类型，当前固定枚举 `WORK_ORDER_DETAIL` |
| title_template | varchar(128) | 否 | 标题模板 |
| summary_template | varchar(255) | 否 | 摘要模板 |
| route_value_template | varchar(128) | 否 | 跳转值模板 |
| variables_json | text | 否 | 可用变量说明快照 |
| remark | varchar(255) | 否 | 备注 |
| create_by | varchar(64) | 否 | 创建人 |
| create_time | datetime | 是 | 创建时间 |
| update_by | varchar(64) | 否 | 更新人 |
| update_time | datetime | 是 | 更新时间 |

### 5.4 唯一约束与索引

建议索引如下：

- `uk_template_code_source(template_code, template_source)`
- `idx_event_type(event_type)`
- `idx_biz_type(biz_type)`

### 5.5 数据约束

- 每个 `template_code` 必须存在且仅存在一条 `BUILT_IN`
- 每个 `template_code` 最多存在一条 `CUSTOM`
- 内置模板不允许删除
- 内置模板不允许编辑
- 后台不允许新增未知 `template_code`

### 5.6 初始化数据

二期初始化 SQL 至少写入一条内置模板：

- `templateCode = WORK_ORDER_ASSIGNED`
- `templateSource = BUILT_IN`
- `notifyEnabled = 1`
- `overrideEnabled = 0`
- `routeType = WORK_ORDER_DETAIL`
- `titleTemplate = 你有新的工单待处理`
- `summaryTemplate = 工单${bizNo}已派发给你，请尽快处理`
- `routeValueTemplate = ${bizId}`

## 6. 模板变量设计

### 6.1 变量白名单

二期固定允许以下变量：

- `bizId`
- `bizNo`
- `receiverId`
- `receiverName`
- `operatorId`
- `oldAssignedUserId`
- `newAssignedUserId`
- `assignType`
- `operationId`

### 6.2 变量来源

变量统一由后端渲染服务提供，不允许模板自行查询数据库拼装。

对于 `WORK_ORDER_ASSIGNED` 场景：

- 来自通知事件主字段
- 来自事件载荷 `NotifyAssignedEventDTO`
- 来自标准上下文对象

### 6.3 占位符校验规则

- 仅允许 `${变量名}` 形式
- 变量名必须命中白名单
- 未识别变量不允许保存
- 预览时若出现非法变量，直接提示错误

## 7. 渲染与回退规则

### 7.1 模板解析顺序

运行时解析顺序如下：

1. 根据 `templateCode` 查询内置模板与自定义模板
2. 若无自定义模板，直接使用内置模板
3. 若有自定义模板且 `notifyEnabled=0`，本次不生成消息
4. 若有自定义模板且 `notifyEnabled=1`、`overrideEnabled=0`，使用内置模板内容
5. 若有自定义模板且 `notifyEnabled=1`、`overrideEnabled=1`，优先使用自定义模板内容

### 7.2 内容回退规则

自定义模板允许“只配开关，不改内容”。因此：

- 当自定义模板内容字段为空时，允许按内置模板内容兜底
- 自定义模板存在但不覆盖内容时，不应阻塞通知发送

### 7.3 运行时失败回退

如果自定义模板出现以下问题：

- 变量渲染失败
- 渲染结果为空且不符合场景要求
- 标题、摘要、跳转值长度超限

则处理方式如下：

- 回退使用内置模板
- 写入错误日志
- 当前通知事件仍视为消费成功
- 不将通知事件标记为 `FAILED`

### 7.4 长度限制

渲染结果必须符合现有消息表长度约束：

- `title <= 128`
- `summary <= 255`
- `routeValue <= 128`

### 7.5 日志策略

建议日志内容至少包含：

- `templateCode`
- `templateSource`
- `eventId`
- `bizId`
- 错误原因
- 是否已回退内置模板

## 8. 缓存设计

### 8.1 缓存目标

模板配置读取频率高、变更频率低，适合使用缓存。

### 8.2 缓存内容

建议缓存键按 `templateCode` 组织，缓存值包含：

- 内置模板
- 自定义模板
- 变量说明

### 8.3 缓存刷新时机

以下操作后自动刷新缓存：

- 新增自定义模板
- 编辑自定义模板
- 删除自定义模板

后台页面仍保留“刷新缓存”按钮，风格与现有参数配置页保持一致。

### 8.4 启动加载

应用启动时可按需加载模板缓存；如未命中缓存，则从数据库读取后回填缓存。

## 9. 后端架构设计

### 9.1 模块落点

二期仍落在 `jasic-system` 模块内，建议包路径：

`com.jasic.aftersales.system.notify.template`

如不单独拆包，也可沿用现有 `notify` 结构，在 `domain/service/controller` 中新增模板相关对象。

### 9.2 建议新增类

- `NotifyTemplateController`
- `NotifyTemplateService`
- `NotifyTemplateRenderService`
- `NotifyTemplateResolver`
- `SysNotifyTemplate`
- `NotifyTemplateDTO`
- `NotifyTemplateQuery`
- `NotifyTemplateVO`

### 9.3 现有类改造点

重点改造：

- `NotifyEventConsumeServiceImpl`

当前该类直接硬编码：

- 标题
- 摘要
- 跳转类型
- 跳转值

二期改为：

- 根据事件类型解析 `templateCode`
- 调用模板解析与渲染服务
- 根据渲染结果创建消息

## 10. 接口设计

### 10.1 列表查询

- 方法：`GET /system/notify/template/list`

查询条件建议支持：

- `templateCode`
- `templateName`
- `templateSource`
- `eventType`

### 10.2 查看详情

- 方法：`GET /system/notify/template/{id}`

### 10.3 新增自定义模板

- 方法：`POST /system/notify/template/custom`

说明：

- 仅允许创建 `CUSTOM` 模板
- 同一 `templateCode` 已存在自定义模板时，不允许重复新增

### 10.4 更新自定义模板

- 方法：`PUT /system/notify/template/custom`

说明：

- 仅允许修改 `CUSTOM` 模板
- 内置模板调用时直接拒绝

### 10.5 删除自定义模板

- 方法：`DELETE /system/notify/template/custom/{id}`

说明：

- 删除后自动回退内置模板
- 内置模板不允许删除

### 10.6 预览模板

- 方法：`POST /system/notify/template/preview`

请求内容建议包含：

- `templateCode`
- `templateSource`
- `titleTemplate`
- `summaryTemplate`
- `routeType`
- `routeValueTemplate`
- `variables`

返回内容建议包含：

- `title`
- `summary`
- `routeType`
- `routeValue`
- `errors`

### 10.7 刷新缓存

- 方法：`POST /system/notify/template/refresh-cache`

## 13. 安全与稳定性要求

### 13.1 保存时校验

- 模板编码必须来自系统预置枚举
- 模板来源只能是 `CUSTOM`
- 占位符必须命中变量白名单
- `routeType` 必须命中系统支持枚举
- 非空内容的长度不得超过字段限制

### 13.2 运行时保护

- 模板渲染失败不能拖垮通知消费主链路
- 自定义模板异常优先回退内置模板
- 仅当内置模板也不可用时，才允许将事件标记为失败并重试

### 13.3 操作审计

模板的新增、编辑、删除、刷新缓存都应写入后台操作日志。

## 14. 分阶段落地计划

### Phase 1 数据层

- 新建 `sys_notify_template` 表
- 编写二期升级 SQL
- 写入 `WORK_ORDER_ASSIGNED` 内置模板初始化数据
- 建立唯一约束和索引

### Phase 2 后端基础能力

- 新增模板实体、Mapper、DTO、Query、VO
- 新增模板 Service、Controller
- 实现模板缓存
- 实现模板新增、编辑、删除、查询、刷新

### Phase 3 渲染能力

- 实现变量提取
- 实现占位符校验
- 实现模板预览
- 实现运行时渲染、长度校验和回退逻辑

### Phase 4 接入现有通知链路

- 改造 `NotifyEventConsumeServiceImpl`
- 用模板生成标题、摘要、跳转值
- 保持一期消息状态流转逻辑不变
- 保持一期事件消费幂等逻辑不变

### Phase 5 前端管理页

- 新增“通知模板”菜单与页面
- 完成列表、查看、新增自定义模板、编辑、删除、预览、刷新缓存
- 对齐现有系统参数页交互风格

### Phase 6 联调与验收

- 校验模板开关行为
- 校验覆盖与回退行为
- 校验保存校验与预览校验
- 校验运行时自定义模板失败后的内置回退
- 校验 `WORK_ORDER_ASSIGNED` 线上链路可正常生成消息

## 15. 测试重点

### 15.1 配置类测试

- 内置模板仅可查看不可编辑
- 自定义模板不可重复新增
- 自定义模板删除后正确回退内置模板
- 自定义模板允许只配置开关不配置内容

### 15.2 渲染类测试

- 合法变量可正确渲染
- 非法变量保存时报错
- 预览时可正确展示错误提示
- 标题、摘要、跳转值长度超限时触发回退

### 15.3 运行链路测试

- 无自定义模板时使用内置模板发送
- `notifyEnabled=0` 时不生成消息
- `overrideEnabled=0` 时使用内置模板内容
- `overrideEnabled=1` 时使用自定义模板内容
- 自定义模板渲染失败时回退内置模板

### 15.4 回归测试

- 一期红点逻辑不受影响
- 一期消息中心列表不受影响
- 一期 `READ/DONE/INVALID` 状态流转不受影响
- 一期异步消费重试机制不受影响

## 16. 实施建议

建议实际开发时遵循以下顺序：

1. 先完成表结构与初始化 SQL
2. 再完成后端模板基础能力与缓存
3. 再完成模板渲染与预览
4. 再接入 `WORK_ORDER_ASSIGNED`
5. 最后补前端管理页和联调

这样可以尽早打通“模板入库 -> 模板读取 -> 模板渲染 -> 消息生成”的最小闭环。

## 17. 后续扩展预留

二期设计需为后续能力预留扩展空间，但不在本期落地：

- 新增更多工单通知场景
- 支持普通告知消息模板
- 支持更多 `routeType`

- 支持公司级、角色级模板隔离
