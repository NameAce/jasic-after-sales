# 佳士售后系统 - 数据库设计文档

> 本文档详细描述系统的数据库表结构设计，包含当前已落地的17张系统核心表，以及 S0.4 阶段待实施的售后业务核心表草案。

---

## 一、设计规范

遵循《阿里巴巴Java开发手册》嵩山版数据库规约：

- 表名、字段名全小写 + 下划线分隔，不使用复数
- 表必备三字段：`id`（bigint unsigned 主键）、`create_time`（datetime）、`update_time`（datetime）
- 索引命名：主键 `pk_xxx`、唯一索引 `uk_xxx`、普通索引 `idx_xxx`
- 不使用外键与级联，外键概念在应用层解决
- 布尔字段用 `is_xxx`，类型 tinyint unsigned（1=是，0=否）
- 字符集 utf8mb4，排序规则 utf8mb4_general_ci
- 所有表使用 InnoDB 引擎

## 五、S0.4 售后业务核心表草案（待实施）

### 5.1 设计原则

- 主工单表只保存当前状态、列表查询快照和当前权限判断所需字段，不承载多轮维修明细。
- 报价、维修登记、故障点、复检、评价、通知事件均采用独立业务表，按时间追加记录。
- 本轮不单独设计“处理轮次表”，先通过流转历史和各业务记录表的公司归属识别处理阶段。
- 历史参与方可见能力正式采用方案 B：增加 `work_order_participant` 参与方快照表。
- 所有售后业务表继续遵循本文档统一规范，默认包含 `id`、`create_time`、`update_time` 三个基础字段。

### 5.2 业务表关系


状态字典（S0.3 正式基线）：

| 字段 | 编码 | 含义 |
|------|------|------|
| main_status | PENDING_ASSIGN | 待派单，当前受理公司已确定，但尚未指派维修员 |
| main_status | PENDING_TECH_ACCEPT | 待接单，维修员已被指派，等待维修员接单 |
| main_status | IN_PROGRESS | 维修中，维修员已接单，可进行报价、维修登记、转单 |
| main_status | COMPLETED | 已完成，维修动作已完成，等待复检/返回方式/关单 |
| main_status | CLOSED | 已关闭，工单已收尾完成，可进入客户评价 |
| evaluate_status | NOT_OPEN | 未开启评价，工单尚未关闭 |
| evaluate_status | PENDING_EVALUATE | 待评价，工单已关闭，等待客户评价 |
| evaluate_status | EVALUATED | 已评价，客户已完成评价 |

当前受理方 / 处理人语义（S0.3 正式基线）：

- `current_accept_subject_type`、`current_accept_company_id` 表示当前负责处理该工单的主体和公司，只在建单、转单时变化。
- `assigned_user_id` 表示当前被派单维修员，在派单时写入，在转单时清空；完成、关闭后保留为最后责任维修员快照，便于查询和追溯。
- 对外展示状态采用 4 个外显状态：`WAIT_ACCEPT / IN_PROGRESS / COMPLETED / CLOSED`。其中 `WAIT_ACCEPT = PENDING_ASSIGN + PENDING_TECH_ACCEPT`，该聚合态只用于展示与统计，不单独落库。

### 5.12 业务表汇总

| 1 | work_order | 工单主表 | 当前态与查询快照 |

| 9 | work_order_notify_event | 工单通知事件 | 不含模板配置 |
