# 消息通知一期分步落地方案

## 1. 文档目的

本文档用于把《消息通知一期总方案》拆解成可逐步执行、可中断恢复、可多人接力的实施步骤。

执行原则：

- 一次只推进一个阶段，阶段未完成前不跳到下一阶段
- 每完成一个阶段，都要同步更新本文档与验收清单
- 如果实现过程中发现与总方案冲突，先更新决策记录，再继续改代码

## 2. 接手顺序

新线程、新模型、新开发者接手前，必须按以下顺序阅读：

1. [11-消息通知一期决策记录](./11-消息通知一期决策记录.md)
2. [09-消息通知一期总方案](./09-消息通知一期总方案.md)
3. 本文档
4. [12-消息通知一期验收清单](./12-消息通知一期验收清单.md)

## 3. 交付边界

本次实施只允许交付以下内容：

- 新建 `sys_notify_event`、`sys_notify_message`、`sys_notify_message_log` 三张通知相关表
- 新建通知领域实体、枚举、Mapper、Service、Job、Facade
- 在工单派单、转派、详情查看、接单、关闭、完成等流程中接入一期通知逻辑
- 提供消息中心查询接口与顶部红点接口
- 提供一期范围内最小可用的前端消息中心页面

本次实施不允许顺手做：

- 旧通知逻辑迁移
- 旧表兼容适配
- 外部渠道接入
- 大规模 UI 美化
- 公告系统能力扩展

## 7. Phase 3：事件发布接入

### 7.1 目标

在工单实际派给维修员成功后，写入通知事件表。

### 7.2 输入

- 工单派单现有服务
- 通知事件服务骨架

### 7.3 输出

- 派单后可持久化通知事件

### 7.4 必须确认的实现要求

- `WORK_ORDER_ASSIGNED` 只在实际派给维修员时产生，不包含公司转单
- 事件表采用事务内 Outbox 模式，与派单主事务一并提交
- 必须生成 `eventKey`
- 必须保存 `oldAssignedUserId`、`newAssignedUserId`、`assignType`

### 7.5 任务清单

- [x] 定位工单派单服务方法

- [x] 生成 `operationId`
- [x] 实现 `publishAssignedEvent(...)`
- [x] 事件表落库状态默认为 `NEW`
- [x] 记录操作人、工单号、接收人

### 7.6 完成定义

- 派单一次，事件表新增一条记录
- 公司转单不会错误写入 `WORK_ORDER_ASSIGNED`
- 重复请求不会生成重复 `eventKey`

### 7.7 风险提示

## 9. Phase 5：状态流转接入

### 9.1 目标

接入已读、已处理、失效三类状态流转。

### 9.2 输入

- 已生成的待办消息
- 工单详情、接单、关闭、完成等业务流程

### 9.3 输出

- 可被业务驱动的 `READ`、`DONE`、`INVALID` 状态流转

### 9.4 任务清单

- [x] 实现 `markReadByBiz(...)`
- [x] 在工单详情接口中接入已读
- [x] 实现 `completeTodoByBizAndReceiver(...)`
- [x] 在 `TECH_ACCEPT` 业务动作中接入完成
- [x] 实现 `invalidateTodoByBiz(...)`
- [x] 在工单关闭中接入失效
- [x] 在工单完成中接入失效
- [x] 确认当前系统无独立工单作废业务场景，本期不纳入接入范围
- [x] 为 `READ/DONE/INVALID` 写日志

### 9.5 完成定义

- 查看详情会把当前工单待办改为 `READ`
- 接单动作会把待办改为 `DONE`
- 关闭、完成会把未完成待办改为 `INVALID`

### 9.6 风险提示

- `DONE` 必须由业务动作驱动，不能开放给前端直接修改
- 如后续新增工单作废流程，需要补接 `WORK_ORDER_CANCELLED` 失效链路

- 负责人：Codex
- 状态：已完成
