# 消息通知一期决策记录

## 1. 文档目的

本文档用于沉淀本次讨论中已经确认的关键设计决策。

作用：

- 防止上下文压缩后丢失关键结论
- 防止实现过程中被顺手改偏
- 为新线程、新模型、新开发者提供快速接手入口

除非明确评审通过，否则本文档中的已确认决策不得擅自变更。

## 2. 已确认决策

### D-001 一期只做 B 端内部用户

- 状态：已确认
- 结论：消息通知一期只服务于 B 端内部系统用户
- 影响：不考虑客户、小程序用户、外部访客

### D-002 一期只做站内信与红点

- 状态：已确认
- 结论：一期只支持站内消息中心与顶部红点
- 影响：不做短信、邮件、微信、小程序订阅消息

### D-003 一期只做一个事件

- 状态：已确认
- 结论：一期只做 `WORK_ORDER_ASSIGNED`
- 影响：首次派单和转派都通过同一个事件模型处理

### D-004 派单通知按待办消息建模

- 状态：已确认
- 结论：工单派单通知是待办，不是普通告知消息
- 影响：消息必须有待办状态流转

### D-005 每次派单都创建新消息

- 状态：已确认
- 结论：每次派单或转派都生成一条新的待办消息
- 影响：不覆盖旧消息，保留历史轨迹

### D-006 转派后旧待办自动失效

- 状态：已确认
- 结论：转派发生时，旧接收人的有效待办必须自动 `INVALID`
- 影响：避免旧处理人继续看到无效待办

### D-007 READ 与 DONE 必须严格区分

- 状态：已确认
- 结论：进入页面只算 `READ`，不能算 `DONE`
- 影响：待办是否真正完成，必须绑定真实业务动作

### D-008 DONE 绑定真实业务动作

- 状态：已确认
- 结论：一期默认使用 `TECH_ACCEPT` 作为完成待办的动作
- 影响：不得提供前端直接改 DONE 的接口

### D-009 红点统计有效待办数

- 状态：已确认
- 结论：红点统计 `PENDING + READ`
- 影响：已读但未处理的待办仍需显示红点

### D-010 进入工单详情自动已读

- 状态：已确认
- 结论：进入工单详情页时，将当前用户当前工单的 `PENDING` 待办改为 `READ`
- 影响：消息点击后先标已读，再跳工单详情

### D-011 工单关闭类动作使待办失效

- 状态：已确认
- 结论：结合当前系统业务现状，一期仅要求工单关闭、完成使未完成待办 `INVALID`；当前无独立工单作废场景，故不纳入一期验收范围
- 影响：一期失效原因至少覆盖 `WORK_ORDER_CLOSED`、`WORK_ORDER_COMPLETED`；如后续新增工单作废流程，再补充 `WORK_ORDER_CANCELLED`

### D-012 一期强绑定业务对象

- 状态：已确认
- 结论：一期所有消息必须绑定工单
- 影响：消息必须保存 `bizType/bizId/bizNo`

### D-013 一期不做上级、主管、协同人

- 状态：已确认
- 结论：由于当前系统没有稳定的上下级/协同人模型，一期接收人只使用 `assignedUserId`
- 影响：不支持抄送、按角色扩散通知、按上级升级

### D-014 一期不做消息删除

- 状态：已确认
- 结论：一期不做物理删除，统一用状态流转表示生命周期
- 影响：审计与排障更清晰

### D-015 一期前端只做两个列表

- 状态：已确认
- 结论：消息中心只做 `待处理` 与 `历史记录`
- 影响：不做复杂聚合和消息详情页

### D-016 `WORK_ORDER_ASSIGNED` 只描述“派给具体维修员”

- 状态：已确认
- 结论：`WORK_ORDER_ASSIGNED` 只在工单实际派给具体维修员时产生；当前系统里的公司转单 `transfer(...)` 不发布该事件
- 影响：通知接收人始终是 `newAssignedUserId` 对应的维修员；公司转单导致的旧待办失效放到后续状态流转阶段处理

### D-017 Phase 3 采用事务内 Outbox 落事件

- 状态：已确认
- 结论：Phase 3 将通知事件表作为 Outbox，在工单派单主事务内一并落库，不使用事务提交后的二次写入
- 影响：派单与事件记录具备同事务一致性；事件消费仍保持异步，不提前进入 Phase 4

## 3. 一期状态定义

### S-001 PENDING

- 含义：待处理且未读
- 是否计入红点：是
- 是否展示在待处理列表：是

### S-002 READ

- 含义：已读但未处理
- 是否计入红点：是
- 是否展示在待处理列表：是

### S-003 DONE

- 含义：已通过真实业务动作完成
- 是否计入红点：否
- 是否展示在历史列表：是

### S-004 INVALID

- 含义：已无继续处理意义
- 是否计入红点：否
- 是否展示在历史列表：是

## 4. 一期禁止事项

- 禁止把进入页面当成已处理
- 禁止跳过事件表直接写消息表
- 禁止在工单主事务内直接完成所有通知处理
- 禁止给前端开放直接改 `DONE` 或 `INVALID` 的接口
- 禁止在一期中引入外部消息渠道
- 禁止擅自接入更多业务事件
- 禁止将消息查询放开给非接收人

## 7. 新线程接手必读摘要

如果上下文有限，最少要先读下面这些结论：

- 一期只做 B 端
- 一期只做站内信 + 红点
- 一期只做 `WORK_ORDER_ASSIGNED`
- `WORK_ORDER_ASSIGNED` 只在实际派给维修员时产生，不包含公司转单
- 派单通知是待办，不是普通消息
- 转派旧待办失效，新待办重新生成
- `READ` 不等于 `DONE`
- `DONE` 绑定 `TECH_ACCEPT`
- 红点统计 `PENDING + READ`
