# 消息通知模板配置精简重构方案

## 1. 文档目的

本文档用于固化消息通知模块中“通知模板配置”的精简重构方案，作为后续另起线程落地优化的直接实施基线。

后续线程落地本方案时，只需要默认阅读：

1. `docs/00-项目协作约定.md`
2. 本文档

除非用户在当轮明确要求回看旧方案，否则不需要再读取旧通知一期、二期、模板配置重构或原型文档。

本次重构明确不保留历史模板配置数据和旧模板配置代码口径。旧 `sys_notify_template` / `sys_notify_template_channel` 可在升级脚本中直接删表重建；旧接口、旧页面交互和旧字段维护方式不保留兼容。

本文档是通知模板配置精简重构的当前唯一专项基线。旧通知相关方案只作为历史背景，不再决定本次数据模型、接口、页面交互、代码结构或验收标准。

## 2. 适用范围

本方案只处理“通知模板配置”和“模板运行时读取方式”的精简重构，重点包括：

- 通知场景注册表。
- `sys_notify_template` 精简表。
- `sys_notify_template_channel` 精简表。
- 模板后台维护接口。
- 渠道配置接口。
- 运行时按 `scene_code` 读取模板和渠道配置。
- PC 端通知模板配置页面。

本方案不重新设计整个消息通知模块，不主动改造以下主体模型：

- `sys_notify_event`
- `sys_notify_message`
- `sys_notify_message_log`
- `sys_notify_dispatch`
- 消息中心列表、红点、已读、完成、失效等主体流程
- 通知事件消费和外部分发任务的主体调度机制

如落地过程中发现上述主体模型必须调整，应先暂停说明原因、影响范围和替代方案，确认后再扩大范围。

## 3. 当前问题

当前模板配置页面和模型把系统内部识别通知场景的字段暴露给维护人员，例如：

- `biz_type`：业务类型
- `trigger_scene`：触发场景
- `notify_type`：通知类型
- `channel_scene`：渠道场景
- `receiver_type`：接收对象类型
- `receiver_desc`：接收对象说明
- `variables_json`：变量 JSON

这些字段对运行时建模有一定意义，但不应该成为模板维护人员的主要配置项。维护人员真正关心的是：

- 配置哪个通知场景。
- 标题和内容怎么写。
- 跳转到哪里。
- 小程序等外部渠道参数怎么填。
- 是否启用。

因此，本次重构目标是把“配置技术字段”改为“配置业务通知场景”。

## 4. 核心结论

本次模板配置重构采用：

```text
通知场景注册表 + 精简模板表 + 精简渠道表
```

核心字段统一收口为：

```text
scene_code
```

示例：

```text
WORK_ORDER_ASSIGNED_TODO
WORK_ORDER_EVALUATION_INVITE_MP_C
```

`biz_type`、`trigger_scene`、`notify_type`、`receiver_type`、`receiver_desc`、变量清单、默认路由等系统属性全部由后端通知场景注册表维护，不再作为模板表主字段，也不再由前端提交维护。

## 5. 明确不做

本次重构不做以下能力：

- 不保留旧模板数据。
- 不兼容旧模板接口。
- 不做后台自由新增未知通知场景。
- 不做接收人规则配置。
- 不做规则引擎。
- 不做条件表达式、脚本模板、循环模板。
- 不做用户通知偏好。
- 不做多语言模板。
- 不做公司级模板继承。
- 不做短信、邮件、企业微信真实发送。
- 不做复杂渠道编排。

## 6. 场景注册表

### 6.1 职责

后端新增或重构 `NotifySceneRegistry`，作为通知场景的唯一元数据来源。

注册表负责维护：

| 字段 | 说明 |
| --- | --- |
| `scene_code` | 通知场景编码，全局唯一 |
| `scene_name` | 通知场景名称，页面展示使用 |
| `biz_type` | 业务类型，运行时和排障使用 |
| `event_type` | 事件类型或触发场景，运行时匹配 handler 使用 |
| `notify_type` | 通知类型，如站内待办、小程序订阅消息 |
| `receiver_type` | 接收对象类型，仅系统理解 |
| `receiver_desc` | 接收对象说明，仅展示说明 |
| `channel_type` | 外部渠道类型，站内场景可为空 |
| `default_template_name` | 默认模板名称 |
| `default_title_template` | 默认标题模板 |
| `default_content_template` | 默认内容模板 |
| `default_route_type` | 默认跳转类型 |
| `default_route_value_template` | 默认跳转值模板 |
| `variables` | 可用变量元数据 |

### 6.2 首批场景

| 场景编码 | 场景名称 | 通知类型 | 接收对象 | 说明 |
| --- | --- | --- | --- | --- |
| `WORK_ORDER_ASSIGNED_TODO` | 工单派单 - 站内待办 - 维修员 | `IN_APP_TODO` | 维修员 | 工单派单后给当前维修员生成站内待办 |
| `WORK_ORDER_EVALUATION_INVITE_MP_C` | 客户评价邀请 - 小程序订阅消息 - C端客户 | `MP_SUBSCRIBE` | C端客户 | 工单完成后给客户发送评价邀请订阅消息 |

后续新增通知场景时，必须先扩展注册表，再允许后台维护模板。

## 7. 数据库设计

### 7.1 `sys_notify_template`

职责：保存某个已注册通知场景的模板内容和启停状态。

```sql
DROP TABLE IF EXISTS `sys_notify_template`;
CREATE TABLE `sys_notify_template` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键',
  `scene_code` varchar(64) NOT NULL COMMENT '通知场景编码',
  `template_name` varchar(128) NOT NULL COMMENT '模板名称',
  `title_template` varchar(128) DEFAULT NULL COMMENT '标题模板',
  `content_template` varchar(512) DEFAULT NULL COMMENT '内容模板',
  `route_type` varchar(64) DEFAULT NULL COMMENT '站内跳转类型',
  `route_value_template` varchar(128) DEFAULT NULL COMMENT '站内跳转值模板',
  `status` tinyint unsigned NOT NULL DEFAULT 1 COMMENT '状态：1启用，0停用',
  `remark` varchar(255) DEFAULT NULL COMMENT '备注',
  `create_time` datetime NOT NULL COMMENT '创建时间',
  `update_time` datetime NOT NULL COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_scene_code` (`scene_code`),
  KEY `idx_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='通知模板配置表';
```

说明：

- 一个 `scene_code` 只允许一条模板记录。
- 不再支持同一场景多条停用模板历史。
- 模板变更历史暂不单独建表，继续依赖操作日志。

### 7.2 `sys_notify_template_channel`

职责：保存外部渠道参数。当前主要服务小程序订阅消息。

```sql
DROP TABLE IF EXISTS `sys_notify_template_channel`;
CREATE TABLE `sys_notify_template_channel` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键',
  `scene_code` varchar(64) NOT NULL COMMENT '通知场景编码',
  `channel_type` varchar(32) NOT NULL COMMENT '渠道类型',
  `channel_enabled` tinyint unsigned NOT NULL DEFAULT 1 COMMENT '渠道状态：1启用，0停用',
  `config_json` text DEFAULT NULL COMMENT '渠道参数JSON',
  `remark` varchar(255) DEFAULT NULL COMMENT '备注',
  `create_time` datetime NOT NULL COMMENT '创建时间',
  `update_time` datetime NOT NULL COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_scene_channel` (`scene_code`, `channel_type`),
  KEY `idx_channel_enabled` (`channel_type`, `channel_enabled`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='通知模板渠道配置表';
```

小程序订阅消息 `config_json` 示例：

```json
{
  "templateId": "微信订阅消息模板ID",
  "pagePathTemplate": "pages/order/evaluate?workOrderId=${workOrderId}",
  "fieldMapping": [
    { "field": "thing1", "value": "${orderNo}" },
    { "field": "phone_number2", "value": "${customerMobile}" },
    { "field": "thing3", "value": "${companyName}" }
  ]
}
```

## 8. 运行时规则

### 8.1 模板渲染

发送侧不再按以下组合查询模板：

```text
biz_type + trigger_scene + notify_type + channel_scene
```

改为按 `scene_code` 查询模板：

```text
scene_code -> sys_notify_template
```

业务 handler 应明确使用对应场景编码，例如：

```java
NotifySceneCode.WORK_ORDER_ASSIGNED_TODO
NotifySceneCode.WORK_ORDER_EVALUATION_INVITE_MP_C
```

### 8.2 接收人规则

接收人仍由业务 handler 根据业务快照解析。

模板配置不决定“发给谁”，只决定“这个场景发出去的文案和渠道参数是什么”。

### 8.3 渠道配置

外部渠道发送按 `scene_code + channel_type` 查询渠道配置。

发送条件：

```text
模板启用 && 渠道启用
```

如果模板停用或渠道停用：

- 不发送外部通知。
- 记录明确的跳过原因，便于排障。

## 9. 后端接口

接口前缀继续使用：

```text
/system/notify/template
```

### 9.1 元数据接口

```text
GET /system/notify/template/options
```

返回：

- `sceneOptions`：可维护通知场景列表。
- `channelTypeOptions`：渠道类型列表。
- 每个场景的默认模板、默认路由、变量元数据、接收对象说明。

### 9.2 模板接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/system/notify/template/list` | 分页查询模板 |
| `GET` | `/system/notify/template/{id}` | 查询模板详情 |
| `POST` | `/system/notify/template` | 新增模板 |
| `PUT` | `/system/notify/template` | 修改模板 |
| `PUT` | `/system/notify/template/{id}/status` | 启用或停用模板 |
| `POST` | `/system/notify/template/preview` | 预览模板 |

新增模板请求建议：

```json
{
  "sceneCode": "WORK_ORDER_ASSIGNED_TODO",
  "templateName": "工单派单待办",
  "titleTemplate": "您有新的维修工单",
  "contentTemplate": "工单${orderNo}已派给您，请及时处理",
  "routeType": "WORK_ORDER_DETAIL",
  "routeValueTemplate": "${workOrderId}",
  "status": 1,
  "remark": ""
}
```

后端校验：

- `sceneCode` 必须存在于注册表。
- 同一 `sceneCode` 只能存在一条模板。
- 前端不得提交或覆盖 `bizType`、`triggerScene`、`notifyType`、`receiverType`。
- 模板变量只允许使用注册表声明的变量；如短期实现成本较高，至少要在预览和保存时给出明确错误。

### 9.3 渠道接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/system/notify/template/{sceneCode}/channels` | 查询场景渠道配置 |
| `PUT` | `/system/notify/template/{sceneCode}/channels` | 保存场景渠道配置 |

渠道配置只允许用于注册表声明了外部渠道的场景。站内待办场景不展示渠道配置入口。

## 10. 前端页面

### 10.1 列表页

列表建议展示：

| 列 | 说明 |
| --- | --- |
| 通知场景 | 直接展示场景名称 |
| 通知类型 | 来自注册表，只读展示 |
| 接收对象 | 来自注册表，只读展示 |
| 模板名称 | 模板记录字段 |
| 状态 | 启用 / 停用 |
| 更新时间 | 模板记录字段 |
| 操作 | 查看、编辑、启停、预览、渠道配置 |

不再单独展示“业务类型”“触发场景”两列。

筛选建议保留：

- 通知场景
- 通知类型
- 状态
- 模板名称

### 10.2 新增 / 编辑页

主表单字段：

- 通知场景
- 模板名称
- 启用状态
- 标题模板
- 内容模板
- 跳转配置
- 备注

只读辅助信息：

- 通知类型
- 接收对象
- 触发说明
- 可用变量

不出现以下可编辑字段：

- 业务类型
- 触发场景
- 通知类型
- 渠道场景
- 接收对象类型
- 接收对象说明
- 变量 JSON

### 10.3 渠道配置页

小程序订阅消息场景展示：

- 渠道启用状态
- 微信模板 ID
- 跳转页面模板
- 字段映射
- 备注

字段映射仍可用 JSON 或表格方式维护。推荐用表格方式降低出错率。

## 11. 旧方案和旧代码处理

本次明确采用“重构替换”而不是“兼容迁移”。

处理原则：

- 旧 `sys_notify_template` 和 `sys_notify_template_channel` 数据不保留。
- 旧模板接口不保留兼容。
- 旧页面字段不保留。
- 旧 `biz_type + trigger_scene + notify_type + channel_scene` 组合查询模板逻辑应被清理。
- 旧 `receiver_type / receiver_desc` 在模板表中的维护口径应被清理。
- 旧 `variables_json` 由前端或用户维护的口径应被清理，变量元数据统一来自场景注册表。

仍需保留或谨慎处理：

- `sys_notify_message`、`sys_notify_event`、`sys_notify_dispatch` 中的 `biz_type` 等运行时字段可继续保留，它们用于业务对象识别、权限校验、跳转和排障，不属于本次模板表精简对象。
- 如果某些运行时记录需要保存实际命中的模板信息，应优先保存 `scene_code` 和必要快照，不再依赖旧模板组合字段。

## 12. 改动规模判断

本次改动属于中到大改，但边界清楚。

改动大的原因：

- 模板表和渠道表需要删表重建。
- 模板后台接口入参、出参要改。
- 模板前端页面要重做交互。
- 运行时模板查询要从组合字段改为 `scene_code`。
- 现有模板相关 DTO、VO、Query、枚举和注册表需要明显收口。

改动可控的原因：

- 不保留历史数据。
- 不兼容旧接口。
- 不改消息中心主体模型。
- 不改 `sys_notify_message` 待办状态流转。
- 不改 `sys_notify_event` 事件主体链路。
- 不改 `sys_notify_dispatch` 外部分发主体链路，只调整模板和渠道配置查找方式。

## 13. 代码注释要求

本次重构涉及模板配置模型、场景注册表、渠道配置、发送链路和前端维护页面，后续落地时必须保留足够详细的简体中文注释，避免后续接手人员只看代码时丢失设计意图。

总体要求：

- 所有新增类必须写简体中文类注释，说明该类的业务职责、边界、不负责的内容，以及它和通知场景、模板、渠道、事件或分发之间的关系。
- 所有新增接口必须写简体中文接口注释，说明抽象目的、调用方约束、适用场景和实现边界。
- 所有新增或重构的方法必须写简体中文方法注释，说明方法目的、关键流程、参数含义、返回值含义和异常场景。
- 方法内部必须保留必要的简体中文步骤注释，说明关键业务判断、状态流转、幂等保护、启停校验、异常兜底、历史清理和数据权限边界。
- 方法内部调用其它方法时，如果调用目的不是一眼能看出来，必须在调用前用简体中文说明调用原因或期望达成的业务目的。
- 对 `scene_code` 解析、模板启停、渠道启停、模板缺失、渠道缺失、发送跳过、失败记录、人工重试、死信处理等关键逻辑，必须说明业务原因，不能只解释代码字面动作。
- 所有业务注释统一使用简体中文；`scene_code`、`template_code`、`handler`、`dispatch`、`payload`、`channel` 等关键字段或技术术语可以保留英文原词。
- 不允许使用空泛注释，例如“调用方法”“设置字段”“进入判断”“处理逻辑”等不能表达业务目的的注释。

历史注释处理要求：

- 开发过程中允许修改代码和同步调整相关注释。
- 如果代码逻辑被修改，相关注释必须同步更新，不能保留过期或误导性的旧注释。
- 不允许为了方便阅读、移动代码或减少文件长度而随意删除未改动区域的原有注释。
- 未涉及的代码区域，原则上不要主动清理、改写或删除原有注释。
- 如果发现原有注释明显错误、乱码、过期或与本次修改后的逻辑冲突，可以在修改对应代码时一并修正；但应控制在本次重构相关范围内。

验收要求：

- 新增类和新增接口没有空缺类注释或接口注释。
- 新增和重构方法没有空缺方法注释。
- 复杂方法内部能通过步骤注释看出业务意图。
- 关键方法调用前能看出为什么调用，而不是只看见机械调用链。
- 未改动区域的原有注释没有被无关删除。

## 14. 推荐分阶段

建议分 3 个阶段，不再拆得过细。

### Phase 1：后端模型和 SQL 收口

目标：先让后端模型干净。

范围：

- 新增 `NotifySceneRegistry` / `NotifySceneMeta` / `NotifySceneCode`。
- 重建 `sys_notify_template`。
- 重建 `sys_notify_template_channel`。
- 调整实体、DTO、VO、Query。
- 调整模板管理接口。
- 调整渠道配置接口。
- 调整模板渲染服务为按 `scene_code` 查询。
- 补充后端单测。

验收：

- SQL 可执行。
- 模板新增、修改、启停、预览接口可用。
- 渠道配置接口可用。
- 旧组合字段不再作为模板配置接口入参。

### Phase 2：运行时发送链路接入

目标：让现有通知发送按新模板模型运行。

范围：

- 工单派单站内待办 handler 使用 `WORK_ORDER_ASSIGNED_TODO`。
- 客户评价邀请小程序 handler 使用 `WORK_ORDER_EVALUATION_INVITE_MP_C`。
- 外部分发 payload 保存实际 `scene_code` 和必要模板快照。
- 排障记录中展示场景名称和模板名称。
- 清理旧模板组合查询逻辑。
- 补充通知消费、分发、重试相关单测。

验收：

- 工单派单可生成站内待办。
- 客户评价邀请可生成小程序分发任务。
- 模板停用后对应场景不发送，并有明确跳过原因。
- 渠道停用后外部通知不发送，并有明确跳过原因。

### Phase 3：前端页面重构和联调

目标：把维护体验改成按业务通知场景配置。

范围：

- 重构 `jasic-ui` 通知模板配置页面。
- 列表页改为展示通知场景、通知类型、接收对象、模板名称、状态。
- 新增 / 编辑页只提交 `sceneCode` 和模板内容。
- 渠道配置页按 `sceneCode` 维护。
- 可用变量改为注册表只读展示。
- 前后端联调。
