# 投诉与建议后端设计方案

> 本文档用于收口“投诉与建议”功能的后端设计口径，仅覆盖后端业务目标、数据模型、接口边界、查询规则、状态流转、配置依赖与实现约束。
>
> 本文档优先级低于当前线程中用户最新确认的口径；如果后续实现时发现本文档、当前代码、历史文档或实际数据之间存在冲突，应先说明冲突点、影响范围和建议处理方式，再继续落地。

---

## 1. 目标与边界

### 1.1 业务目标

本次“投诉与建议”后端能力统一定义为平台反馈单，业务目标是：

- 用户向平台提交反馈。
- 总部后台查看、受理并跟踪反馈。
- 终端用户与网点用户均可查看自己提交的历史反馈和详情。

### 1.2 本期边界

本期仅建设独立的反馈单后端能力，不纳入以下内容：

- 不拆分“投诉”和“建议”类型，统一作为同一业务对象处理。
- 不挂靠为工单子表，反馈单保持独立业务语义。
- 不支持附件。
- 不支持用户编辑、撤回、删除。
- 不支持处理过程记录。
- 不支持导出。
- 不做短时间重复提交拦截。
- 不扩展为多状态流转，仅保留“未受理 / 已受理”。

### 1.3 模块归属

- C 端接口放在 `jasic-customer` 模块。
- 网点端提交、网点端“我的反馈”、总部后台管理接口放在 `jasic-system` 模块。

---

## 2. 角色与权限

### 2.1 提交主体

系统只支持两类提交主体：

- 终端用户
- 网点用户

提交主体通过登录态和权限体系识别，不额外开放其它主体类型。

### 2.2 查看权限

- 终端用户只能查看自己提交的反馈列表与详情。
- 网点用户只能查看自己提交的反馈列表与详情。
- 总部后台管理端具备对应菜单/权限点后，可查看全部反馈数据。

### 2.3 后台可见范围

后台管理是否可见，不按 `hq_company_id` 做数据隔离，而是直接通过菜单/权限点控制。

`hq_company_id` 仍然作为反馈单业务归属字段保留，供后续业务分析、追溯和扩展使用。

## 3. 数据模型设计

### 3.1 表名

反馈主表统一命名为：

- `sys_feedback`

### 3.2 主表字段建议

建议主表至少包含以下字段：

| 字段名 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `submitter_type` | varchar(64) | 提交主体类型，存字符串枚举 |
| `submitter_id` | bigint | 提交人 ID；终端用户存客户 ID，网点用户存系统用户 ID |
| `submitter_name` | varchar(128) | 提交人姓名快照 |
| `submit_company_id` | bigint | 提交网点 ID；仅网点用户提交时有值，终端用户为空 |
| `submit_source_type` | varchar(64) | 提交来源类型，存字符串枚举 |
| `submit_source_name` | varchar(128) | 提交来源展示名称快照 |
| `contact_phone` | varchar(32) | 联系电话快照 |
| `related_work_order_id` | bigint | 关联工单 ID，仅终端用户场景按规则尝试回填 |
| `hq_company_id` | bigint | 归属总部 ID |
| `content` | varchar(500) / text | 反馈内容 |
| `status` | varchar(32) | 状态，存字符串枚举 |
| `accept_user_id` | bigint | 受理人系统用户 ID |
| `accept_user_name` | varchar(128) | 受理人姓名快照 |
| `accept_time` | datetime | 受理时间 |
| `create_time` | datetime | 创建时间，同时作为提交时间 |
| `update_time` | datetime | 更新时间 |

### 3.3 本期不需要的字段

本期明确不需要以下字段：

- 反馈编号字段
- 附件字段
- 逻辑删除字段
- 受理备注字段
- 处理结果字段
- 处理过程记录字段

## 4. 枚举设计

### 4.1 提交主体枚举 `submitter_type`

建议枚举值：

- `CUSTOMER`
- `SERVICE_COMPANY_USER`

### 4.2 提交来源枚举 `submit_source_type`

建议枚举值：

- `CUSTOMER_WORK_ORDER`
- `CUSTOMER_DIRECT`
- `SERVICE_COMPANY`

字段语义说明：

- `submitter_type` 表达“谁提交的”。
- `submit_source_type` 表达“来源是怎么形成的”。

两者不应混用。

### 4.3 状态枚举 `status`

建议枚举值：

- `UNACCEPTED`
- `ACCEPTED`

## 5. 字段取值规则

### 5.1 提交人快照规则

#### 5.1.1 终端用户提交

- `submitter_id`：保存客户 ID
- `submitter_name`：优先取客户昵称/姓名字段；如果为空，再回退手机号
- `contact_phone`：取当前登录客户手机号快照

#### 5.1.2 网点用户提交

- `submitter_id`：保存系统用户 ID
- `submitter_name`：取系统用户真实姓名；如果真实姓名为空，再回退登录名
- `contact_phone`：取当前登录系统用户手机号快照
- `submit_company_id`：取当前登录上下文对应的网点 ID

### 5.2 受理人快照规则

后台执行受理时：

- `accept_user_id`：保存当前受理系统用户 ID
- `accept_user_name`：取系统用户真实姓名；如果真实姓名为空，再回退登录名
- `accept_time`：写入当前时间

### 5.3 提交来源规则

#### 5.3.1 终端用户提交

终端用户提交时，先按当前用户查询“最新提交维修单”：

- 排序规则：按 `work_order.create_time desc` 取第一条

如果最新工单存在且能正确获取服务网点：

- `submit_source_type = CUSTOMER_WORK_ORDER`
- `submit_source_name = 最新工单对应的服务网点名称`
- `related_work_order_id = 最新工单 ID`
- `hq_company_id = 工单上的总部 ID`

如果终端用户没有任何工单：

- `submit_source_type = CUSTOMER_DIRECT`
- `submit_source_name = 终端用户`
- `related_work_order_id = null`
- `hq_company_id = 系统参数 default.hq.company.id`

如果终端用户有最新工单，但异常情况下该工单未取到服务网点：

- `submit_source_type = CUSTOMER_DIRECT`
- `submit_source_name = 终端用户`
- `related_work_order_id = null`
- `hq_company_id = 系统参数 default.hq.company.id`

#### 5.3.2 网点用户提交

网点用户提交时：

- `submit_source_type = SERVICE_COMPANY`
- `submit_source_name = 当前登录上下文对应的网点名称`
- `related_work_order_id = null`
- `hq_company_id = 系统参数 default.hq.company.id`

### 5.4 默认总部配置规则

系统默认总部 ID 参数键名固定为：

- `default.hq.company.id`

如果该参数缺失、为空、或对应公司无效，则提交时直接失败，并返回明确错误，例如：

- `默认总部配置缺失`

## 6. 内容校验规则

反馈内容字段使用 `content` 表示，校验规则如下：

- 必填
- 不允许纯空白内容
- 去除首尾空白后再校验长度
- 最小长度：5
- 最大长度：500

---

## 7. 状态流转与受理规则

### 7.1 状态定义

本期只保留两个状态：

- `UNACCEPTED`：未受理
- `ACCEPTED`：已受理

### 7.2 创建规则

反馈提交成功后：

- `status` 初始值固定为 `UNACCEPTED`
- `create_time` 作为提交时间使用

### 7.3 受理规则

后台“受理”动作只是登记“我看到了”，不代表进入复杂处理流程。

受理时仅更新：

- `status`
- `accept_user_id`
- `accept_user_name`
- `accept_time`
- `update_time`

### 7.4 重复受理限制

已受理数据禁止重复受理。

后端必须做并发保护，建议按“仅当 `status = UNACCEPTED` 时才允许更新”为条件执行原子更新，避免多人同时受理导致受理人和受理时间被覆盖。

---

## 8. 查询与排序规则

### 8.1 我的历史提交列表

终端用户与网点用户都支持查询自己的历史提交列表。

默认排序：

- `create_time desc`

即最新提交在最上方。

### 8.2 我的详情

终端用户与网点用户都支持查看自己提交的反馈详情。

详情接口允许返回：

- `related_work_order_id`

但仅作为关联信息展示，不把反馈单扩展成工单子流程。

### 8.3 后台管理列表

后台管理列表统一通过一个分页接口完成，增加查询字段：

- `viewType`

建议取值：

- `UNACCEPTED`
- `ACCEPTED`
- `ALL`

对应规则如下：

#### 8.3.1 未受理

- 条件：`status = UNACCEPTED`
- 默认排序：`create_time asc`

#### 8.3.2 已受理

- 条件：`status = ACCEPTED`
- 默认排序：`accept_time desc`

#### 8.3.3 全部

- 条件：不限制状态
- 默认排序：`create_time desc`

### 8.4 后台查询条件

后台管理列表只保留当前已确认的查询条件：

- `contact_phone`：模糊查询
- `submit_source_name`：模糊查询
- `create_time`：时间区间查询
- `accept_time`：时间区间查询

本期不额外增加导出、复杂筛选和扩展统计条件。

### 8.5 返回字段要求

列表与详情均返回完整快照字段，避免前端再次拼装：

- `submitter_name`
- `contact_phone`
- `submit_source_type`
- `submit_source_name`
- `related_work_order_id`
- `hq_company_id`
- `status`
- `accept_user_name`
- `accept_time`
- `create_time`

## 9. 接口设计建议

### 9.1 C 端接口

模块：

- `jasic-customer`

建议接口：

- `POST /customer/feedback`：终端用户提交反馈
- `GET /customer/feedback/list`：终端用户查询自己的反馈列表
- `GET /customer/feedback/{id}`：终端用户查看自己的反馈详情

### 9.2 网点端接口

模块：

- `jasic-system`

建议接口：

- `POST /system/feedback`：网点用户提交反馈
- `GET /system/feedback/my-list`：网点用户查询自己提交的反馈列表
- `GET /system/feedback/my/{id}`：网点用户查看自己提交的反馈详情

### 9.3 后台管理接口

模块：

- `jasic-system`

建议接口：

- `GET /system/feedback/manage/list`：后台分页查询反馈列表
- `GET /system/feedback/manage/{id}`：后台查看反馈详情
- `POST /system/feedback/manage/accept`：后台受理反馈

## 10. 实现约束

### 10.1 落库原则

- `submit_source_name`、`submitter_name`、`contact_phone`、`accept_user_name` 均按提交/受理时快照落库。
- 后续列表和详情直接读取快照字段，不实时回查用户表或公司表重新拼装。

### 10.2 工单关联原则

- 反馈单保持独立业务语义。
- `related_work_order_id` 仅用于来源追溯。
- 不将反馈单设计为工单子表。
- 不因为存在 `related_work_order_id` 就复用工单状态流转。

### 10.3 删除与修改原则

- 用户提交后不允许编辑。
- 用户提交后不允许撤回。
- 用户提交后不允许删除。
- 本期主表不设计逻辑删除字段。

### 10.4 时间字段原则

- `create_time` 同时承担提交时间语义。
- 不再额外增加近义的 `submit_time` 字段。
- 受理时间使用 `accept_time` 独立保存。

## 11. 需落地的后端对象建议

建议新增或扩展以下后端对象：

- `Entity`：`SysFeedback`
- `DTO`：提交 DTO、受理 DTO
- `VO`：我的列表 VO、我的详情 VO、后台列表 VO、后台详情 VO
- `Query`：我的列表查询对象、后台管理查询对象
- `Mapper`：`SysFeedbackMapper`
- `Service`：C 端服务、系统端服务、后台管理服务
- `Controller`：C 端控制器、系统端控制器、后台管理控制器

命名与分层遵循项目现有 `Controller -> Service -> Mapper` 结构。

## 12. 本期确认结论

本期“投诉与建议”后端设计已经明确以下关键结论：

- 统一使用独立平台反馈单模型，不拆投诉/建议类型。
- 表名固定为 `sys_feedback`。
- 状态只保留 `未受理 / 已受理`。
- 提交来源按提交时快照固化落库。
- 终端用户、网点用户都支持查看自己历史与详情。
- 后台管理按权限点控制是否可见，不按总部字段隔离数据。
- 默认总部依赖系统参数 `default.hq.company.id`。
- 本期不做附件、导出、删除、撤回、编辑、处理过程记录、防重复提交。

后续如需进入实现阶段，建议直接以本文档作为后端业务基线。
