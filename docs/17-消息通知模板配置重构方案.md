# 消息通知模板配置重构方案

## 1. 文档目的

本文档用于固化消息通知模块“通知模板配置”重构的最终确认口径，并拆分为可独立执行的阶段任务。

后续如按多线程、多轮方式推进，每个执行线程应先阅读：

1. `docs/00-项目协作约定.md`
2. `docs/00-实施清单.md`
3. 本文档

本文档作为本轮消息通知模板配置重构的直接实施基线。若与旧的通知模板、通知二期、评价通知相关文档冲突，以本文档为准；如确需调整，先补充变更记录，再修改代码或 SQL。

## 2. 重构背景

当前后台“通知模板”实现存在以下问题：

- “模板”概念过宽，同时承载通知场景、站内内容、小程序渠道参数、预览调试和缓存刷新。
- `BUILT_IN/CUSTOM` 双轨导致列表和维护心智复杂，一个场景可能在页面上出现多行。
- `NotifyTemplateServiceImpl` 同时负责后台 CRUD、渲染、渠道配置、变量校验和缓存，职责耦合高。
- 前端单页同时包含列表、模板编辑、渠道配置、预览等多个弹窗，维护成本高。
- 小程序订阅消息字段映射、默认预览数据、变量白名单等逻辑分散在前后端。

本次重构参考钉钉宜搭“流程节点 + 消息模板”的设计思路：模板挂在业务触发场景上，每个通知类型一条模板。模板负责通知内容和渠道参数，不负责复杂接收人规则和业务触发条件。

## 3. 设计目标

本次重构只解决以下问题：

1. 明确通知模板配置的业务粒度和边界。
2. 支持同一业务场景下多个通知类型同时启用。
3. 支持仅站内、仅外部渠道、站内加外部渠道等发送形态。
4. 拆清站内消息、站内待办、小程序订阅消息的行为差异。
5. 重建通知模板表结构和后台接口，去掉内置/自定义双轨。
6. 为后续通知记录、排障、重试保留清晰的模板和渠道快照基础。

## 4. 明确不做

本次重构不做以下能力：

- 不做规则引擎。
- 不做复杂渠道编排。
- 不做用户通知偏好。
- 不做订阅中心。
- 不做接收人配置规则。
- 不做多语言模板。
- 不做公司级模板继承。
- 不做短信、邮件、企业微信真实发送。
- 不做模板变更记录表，暂时依赖现有 `OperLog`。
- 不做“恢复默认”按钮，先保证新模型跑通。

## 5. 核心确认结论

### 5.0 代码注释要求

本次重构涉及通知模板、渠道配置、事件 handler、外部分发等多处协作边界，所有新增或重构代码必须保留详细注释。

总体要求：

- 类必须写 Javadoc，说明类的业务职责、边界、不负责的内容，以及和通知模板/渠道/事件/分发之间的关系。
- 接口必须写 Javadoc，说明抽象意图、适用场景、调用方约束和实现边界。
- public、protected、private 方法都必须写 Javadoc，说明方法目的、关键流程、参数含义、返回值含义和异常场景。
- 方法内部必须保留必要的步骤注释，说明关键业务判断、状态流转、幂等保护、启停校验、重复校验、缓存刷新、异常兜底和历史兼容点。
- 方法内调用其它方法时，如果调用目的不是一眼能看出来，必须在调用前说明调用原因或期望达成的业务目的。
- 对停用模板、启用唯一校验、渠道启停、模板缺失、渠道缺失、发送跳过、失败记录等关键逻辑，必须说明业务原因。
- 对旧模型废弃和兼容清理逻辑，必须说明兼容或清理的是哪一类旧数据、旧接口或旧语义。
- 注释尽量使用简体中文；`template_code`、`trigger_scene`、`handler`、`dispatch`、`payload`、`cache` 等关键字段或技术术语可以保留英文。
- 不允许使用空泛注释，例如“调用方法”“设置字段”“进入判断”“处理逻辑”等不能表达业务目的的注释。
- 不允许复制旧代码中不准确、过期或乱码的注释。

### 5.1 菜单和页面命名

- 后台菜单名：`通知模板配置`
- 原“通知模板管理”语义废弃。
- 页面应围绕“业务场景 + 通知类型”组织，而不是围绕 `BUILT_IN/CUSTOM` 组织。

### 5.2 模板粒度

每个通知类型就是一条模板。

示例：

```text
工单派单 - 站内待办
客户评价邀请 - 小程序订阅消息 - C端小程序
```

同一业务触发场景允许多个模板同时启用，例如未来可同时启用：

```text
工单派单 - 站内待办
工单派单 - 小程序订阅消息
```

### 5.3 模板唯一生效规则

模板生效组合为：

```text
biz_type + trigger_scene + notify_type + channel_scene
```

规则：

- 同一组合下只允许一条启用模板。
- 停用后允许新增同组合模板。
- 启用模板时必须检查同组合是否已有启用模板。
- 发送通知只读取启用模板。
- 模板不物理删除，只允许停用。

### 5.4 模板编码

- `template_code` 由后台手填。
- 新增后不可修改。
- `template_code` 全表唯一，不区分启用或停用。
- 停用模板仍占用原 `template_code`，避免历史消息和分发记录引用混乱。

### 5.5 模板状态

项目中配置类普遍使用 `status` 表达启用/停用，本模块沿用该风格：

```text
status = 1 启用
status = 0 停用
```

页面操作不提供“删除”，提供：

```text
启用
停用
编辑
预览
渠道配置
```

### 5.6 通知类型

当前固定三类：

| 编码 | 名称 | 行为 |
| --- | --- | --- |
| `IN_APP_MESSAGE` | 站内消息 | 进入 PC 消息中心和红点，只表达通知，不参与待办完成逻辑 |
| `IN_APP_TODO` | 站内待办 | 进入 PC 待办，有待办状态，可随业务状态完成或失效 |
| `MP_SUBSCRIBE` | 小程序订阅消息 | 只生成外部分发任务，不进入 PC 消息中心 |

### 5.7 接收对象

模板不配置复杂接收人规则，只保存展示和排障辅助字段：

```text
receiver_type
receiver_desc
```

示例：

```text
REPAIRER / 维修员
CUSTOMER / C端客户
```

实际接收人由事件 handler 根据业务快照解析，模板配置不决定“发给谁”的复杂规则。

### 5.8 后台新增边界

后台允许新增模板，但受后端预置组合约束：

- 只能基于后端预置的 `biz_type + trigger_scene + notify_type + channel_scene` 组合新增。
- 不允许新增未知业务类型。
- 不允许新增未知触发场景。
- 不允许新增未知通知类型。
- 同一组合只允许一条启用模板。

本轮必须提供元数据接口，供后台新增模板时选择预置组合。

### 5.9 小程序渠道配置

小程序订阅消息渠道参数继续放在 `sys_notify_template_channel`。

发送条件：

```text
模板启用 && 渠道启用
```

当前阶段字段映射允许自由编辑，先保证跑通；后端保留基础 JSON 解析和必填校验，不做过重的变量下拉约束。

### 5.10 旧模型处理

- 旧 `sys_notify_template`、`sys_notify_template_channel` 数据开发阶段无保留价值。
- SQL 可直接 `DROP TABLE IF EXISTS` 后重建。
- 旧接口不保留兼容。
- `BUILT_IN/CUSTOM` 双轨语义废弃。
- `/custom`、`/refresh-cache` 等旧接口语义废弃。

## 6. 数据模型设计

### 6.1 `sys_notify_template`

职责：保存一条通知模板配置。模板粒度为“业务类型 + 触发场景 + 通知类型 + 渠道场景”。

建议字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint | 是 | 主键 |
| `template_code` | varchar(64) | 是 | 模板编码，全表唯一，手填，新增后不可修改 |
| `template_name` | varchar(128) | 是 | 模板名称 |
| `biz_type` | varchar(32) | 是 | 业务类型，如 `WORK_ORDER` |
| `trigger_scene` | varchar(64) | 是 | 触发场景，如 `WORK_ORDER_ASSIGNED` |
| `notify_type` | varchar(32) | 是 | 通知类型：`IN_APP_MESSAGE/IN_APP_TODO/MP_SUBSCRIBE` |
| `channel_scene` | varchar(16) | 否 | 渠道场景；小程序可用 `B/C`，站内类型为空 |
| `receiver_type` | varchar(64) | 是 | 接收对象类型，仅用于展示和排障辅助 |
| `receiver_desc` | varchar(128) | 是 | 接收对象说明，简体中文 |
| `title_template` | varchar(128) | 否 | 标题模板 |
| `content_template` | varchar(512) | 否 | 内容模板 |
| `route_type` | varchar(64) | 否 | 站内跳转类型 |
| `route_value_template` | varchar(128) | 否 | 跳转值模板 |
| `variables_json` | text | 否 | 可用变量说明和示例 |
| `status` | tinyint | 是 | 1 启用，0 停用 |
| `remark` | varchar(255) | 否 | 备注 |
| `create_time` | datetime | 是 | 创建时间 |
| `update_time` | datetime | 是 | 更新时间 |

建议索引：

```sql
UNIQUE KEY uk_template_code (template_code)
KEY idx_biz_scene_type (biz_type, trigger_scene, notify_type, channel_scene)
KEY idx_status (status)
```

说明：

- MySQL 普通唯一索引无法直接表达“同组合只允许一条启用模板，同时允许多条停用模板”。该规则由服务层校验。
- 如果后续数据库版本和项目规范允许，可再评估使用生成列或部分唯一索引替代服务层校验。

### 6.2 `sys_notify_template_channel`

职责：保存外部渠道参数。当前主要服务 `MP_SUBSCRIBE` 小程序订阅消息。

建议字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint | 是 | 主键 |
| `template_code` | varchar(64) | 是 | 对应 `sys_notify_template.template_code` |
| `channel_type` | varchar(32) | 是 | 渠道类型，当前为 `MP_SUBSCRIBE` |
| `channel_scene` | varchar(16) | 否 | 渠道场景，小程序为 `B/C` |
| `channel_enabled` | tinyint | 是 | 1 启用，0 停用 |
| `config_json` | text | 否 | 渠道参数 JSON |
| `remark` | varchar(255) | 否 | 备注 |
| `create_time` | datetime | 是 | 创建时间 |
| `update_time` | datetime | 是 | 更新时间 |

建议唯一约束：

```sql
UNIQUE KEY uk_template_channel_scene (template_code, channel_type, channel_scene)
```

小程序订阅消息 `config_json` 示例：

```json
{
  "templateId": "微信订阅消息模板ID",
  "pagePathTemplate": "pages/order/evaluate?workOrderId=${workOrderId}",
  "fieldMapping": [
    { "field": "thing1", "value": "${orderNo}" },
    { "field": "phone_number2", "value": "${customerMobile}" },
    { "field": "thing3", "value": "${companyName}" }
  ]
}
```

## 7. 枚举和注册表设计

### 7.1 枚举要求

新增或调整枚举时，按项目现有风格设计：

- 枚举包含 `code` 和 `desc`。
- `desc` 使用简体中文。
- 提供 `getByCode` 和 `fromCode` 或同等解析方法。
- 对外返回元数据时同时返回编码和说明。

建议枚举：

```text
NotifyBizTypeEnum
NotifyTriggerSceneEnum
NotifyTypeEnum
NotifyReceiverTypeEnum
NotifyChannelTypeEnum
NotifyChannelSceneEnum
```

### 7.2 预置组合注册表

新增 `NotifyTemplatePresetRegistry` 或同等组件，集中维护后台允许新增的模板组合。

注册表职责：

- 返回可新增模板组合。
- 返回每个组合的业务类型、触发场景、通知类型、渠道场景、接收对象说明。
- 返回变量说明和示例变量。
- 为新增模板提供默认模板内容。
- 为后端校验提供白名单。

首批预置组合：

| 业务类型 | 触发场景 | 通知类型 | 渠道场景 | 接收对象 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `WORK_ORDER` | `WORK_ORDER_ASSIGNED` | `IN_APP_TODO` | 空 | `REPAIRER / 维修员` | 工单派单后给维修员生成站内待办 |
| `WORK_ORDER` | `WORK_ORDER_EVALUATION_INVITE` | `MP_SUBSCRIBE` | `C` | `CUSTOMER / C端客户` | 工单完成后给客户发送评价邀请订阅消息 |

后续如新增评价结果通知、维修完成通知等，只能先扩展注册表，再允许后台新增模板。

## 8. 接口设计

接口前缀继续使用：

```text
/system/notify/template
```

旧接口不保留兼容，接口语义直接重构。

### 8.1 后台模板接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/system/notify/template/options` | 查询可新增模板组合、枚举、变量元数据 |
| `GET` | `/system/notify/template/list` | 分页查询通知模板 |
| `GET` | `/system/notify/template/{id}` | 查询模板详情 |
| `POST` | `/system/notify/template` | 新增模板 |
| `PUT` | `/system/notify/template` | 修改模板；`template_code` 不允许修改 |
| `PUT` | `/system/notify/template/{id}/status` | 启用或停用模板 |
| `POST` | `/system/notify/template/preview` | 预览模板内容 |
| `GET` | `/system/notify/template/{templateCode}/channels` | 查询渠道配置 |
| `PUT` | `/system/notify/template/{templateCode}/channels` | 保存渠道配置 |

废弃：

```text
POST /system/notify/template/custom
PUT /system/notify/template/custom
DELETE /system/notify/template/custom/{id}
POST /system/notify/template/refresh-cache
```

### 8.2 权限点

保留并调整为新语义：

```text
system:notifyTemplate:list
system:notifyTemplate:view
system:notifyTemplate:add
system:notifyTemplate:update
system:notifyTemplate:remove
system:notifyTemplate:preview
```

说明：

- `remove` 权限本轮语义调整为停用，不做物理删除。
- 不再暴露 `system:notifyTemplate:refresh`，保存后自动刷新或更新缓存。

## 9. 服务拆分建议

建议拆分当前 `NotifyTemplateServiceImpl` 的职责。

### 9.1 `NotifyTemplateAdminService`

职责：

- 后台列表、详情、新增、修改、启停。
- 校验预置组合。
- 校验 `template_code` 唯一。
- 校验启用组合唯一。
- 组织元数据返回。

### 9.2 `NotifyTemplateRenderService`

职责：

- 根据 `template_code` 或组合查找启用模板。
- 渲染标题、内容、路由。
- 支持预览。
- 找不到模板或模板停用时返回明确结果，不能让批处理任务卡死。

### 9.3 `NotifyChannelConfigService`

职责：

- 维护 `sys_notify_template_channel`。
- 查询启用渠道配置。
- 保存小程序订阅消息模板 ID、页面路径和字段映射。
- 判断发送条件：模板启用且渠道启用。

### 9.4 `NotifyTemplatePresetRegistry`

职责：

- 集中注册允许后台新增的模板组合。
- 提供枚举说明、变量说明、示例变量、默认模板。
- 避免预置组合散落在 Controller、Service、前端页面里。

### 9.5 缓存策略

本轮不暴露“刷新缓存”按钮。保存模板或渠道配置后，由服务层自动刷新相关缓存。

如果实现成本较高，第一阶段可以先走数据库实时查询，待核心模型稳定后再加缓存，但接口层不再暴露人工刷新缓存。

## 10. 发送侧规则

### 10.1 事件仍只表达业务事实

`sys_notify_event` 继续只表达“发生了什么”，不承担最终接收人配置语义。

业务层只负责：

- 判断是否满足触发条件。
- 组装事件快照。
- 发布通知事件。

业务层不直接：

- 写 `sys_notify_message`。
- 写 `sys_notify_dispatch`。
- 调用微信发送。
- 读取通知模板配置。

### 10.2 Handler 决定接收人

接收人由 handler 根据事件快照解析。

模板中的 `receiver_type` 和 `receiver_desc` 只用于：

- 后台展示。
- 排障辅助。
- 让管理员理解模板发给谁。

### 10.3 三类通知类型行为

`IN_APP_MESSAGE`：

- 渲染模板后写入 `sys_notify_message`。
- 进入 PC 消息中心和红点。
- 不参与待办完成或失效。

`IN_APP_TODO`：

- 渲染模板后写入 `sys_notify_message`。
- 标记为待办类型。
- 后续可随业务状态完成、转派、失效。

`MP_SUBSCRIBE`：

- 不写 PC 消息中心。
- 读取启用模板和启用渠道配置。
- 写入 `sys_notify_dispatch`。
- 由外部分发任务调用小程序订阅消息发送。

### 10.4 模板缺失或停用处理

发送侧必须排除停用模板。

建议行为：

- 找不到启用模板：记录跳过或失败原因，不让整个批处理任务卡死。
- 模板启用但渠道停用：不生成外部分发，记录可解释原因。
- 小程序渠道配置缺失关键参数：生成失败或跳过时写明原因，便于通知记录排障。

## 11. 前端页面设计

菜单：`通知模板配置`

### 11.1 列表

建议字段：

- 模板编码
- 模板名称
- 业务类型
- 触发场景
- 通知类型
- 渠道场景
- 接收对象
- 状态
- 更新时间

操作：

- 查看
- 编辑
- 启用
- 停用
- 预览
- 渠道配置

### 11.2 新增模板

流程：

1. 调用 `/system/notify/template/options` 获取预置组合。
2. 用户选择业务类型、触发场景、通知类型、渠道场景。
3. 用户手填 `template_code` 和模板名称。
4. 根据预置组合填充默认接收对象、变量说明和默认内容。
5. 保存时后端校验组合是否合法、编码是否唯一、启用组合是否冲突。

### 11.3 编辑模板

规则：

- `template_code` 不允许修改。
- 停用模板允许编辑。
- 编辑后如模板仍为启用状态，必须校验同组合唯一。
- 保存后自动刷新缓存或使缓存失效。

### 11.4 渠道配置

当前主要用于 `MP_SUBSCRIBE`。

字段：

- 渠道类型
- 渠道场景

## 14. 后续扩展原则

后续新增通知场景时，必须遵循以下流程：

1. 先在 `NotifyTriggerSceneEnum` 和 `NotifyTemplatePresetRegistry` 中登记场景和可新增组合。
2. 明确通知类型是 `IN_APP_MESSAGE`、`IN_APP_TODO` 还是 `MP_SUBSCRIBE`。
3. 明确接收对象说明，但不在模板中配置复杂接收人规则。
4. 由 handler 根据业务快照解析实际接收人。
5. 后台再基于预置组合新增或启用模板。

禁止：

- 直接在前端硬编码新场景默认配置。
- 绕过注册表新增未知 `trigger_scene`。
- 在模板里混入业务状态流转规则。
- 在模板里混入复杂接收人规则。

## 15. 关键风险和处理建议

| 风险 | 说明 | 处理建议 |
| --- | --- | --- |
| 停用后新增同组合模板导致误启多条 | 同组合允许多条停用模板 | 启用时必须服务层校验同组合只有一条启用 |
| 小程序字段映射过自由导致发送失败 | 当前阶段先跑通，限制较轻 | 保存时做基础 JSON 和必填校验，发送失败进入通知排障 |
| 旧接口调用残留 | 前后端旧 `/custom`、`refresh-cache` 可能残留 | 阶段六统一 `rg` 清理 |
| 模板缺失导致事件消费失败 | 后台可能停用或未配置模板 | Handler 不应卡死整批任务，应写清楚跳过或失败原因 |
| 表名复用导致语义误读 | 表名不变但字段语义重建 | 文档、实体注释、接口说明必须明确旧双轨废弃 |

## 16. 最终确认摘要

本轮最终确认：

- 采用钉钉宜搭式“业务触发场景 + 通知类型模板”设计。
- 每个通知类型一条模板。
- 当前通知类型固定为站内消息、站内待办、小程序订阅消息。
- 同一场景允许多个模板同时启用。
- 接收人不做规则配置，只保存展示字段。
- 后台允许新增模板，但只能基于后端预置组合。
- 不再保留 `BUILT_IN/CUSTOM` 双轨。
- 站内消息和站内待办明确拆开。
- 小程序订阅消息字段映射当前自由编辑，先跑通。
- 模板配置页不展示通知记录，通知记录后续单独设计。
- 文档、SQL、后端、前端同步重构。
- 旧表可直接删除重建，旧数据无需保留。
- 旧接口不保留兼容。
- 模板不物理删除，只停用。
- 停用后允许新增同组合模板，但同组合只允许一条启用模板。
