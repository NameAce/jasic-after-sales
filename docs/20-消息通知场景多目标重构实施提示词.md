# 消息通知场景多目标重构实施提示词

> 本文档用于给后续另起线程的实施工作直接提供提示词模板。
> 使用时可按阶段直接复制对应提示词，作为新线程的首条任务说明。

---

## 1. 使用说明

- 本文档配套 [19-消息通知场景多目标重构方案.md](/D:/workspace/github/jasic-after-sales/docs/19-消息通知场景多目标重构方案.md) 使用。
- 新线程实施时，应明确以 `docs/19-消息通知场景多目标重构方案.md` 作为唯一业务与技术基线。
- 每次只推进一个阶段，避免单线程跨阶段大范围发散。
- 如果某一阶段实际改动明显扩大，可在该阶段内拆成 2 个小回合，但不要重新拆成过多子阶段。

建议使用方式：

1. 先复制对应阶段提示词。
2. 直接在新线程发送。
3. 如当轮有额外范围限制，可在提示词末尾补一段“本轮补充要求”。

---

## 2. 通用补充说明

以下约束建议每个阶段都默认带上，不单独省略：

- 当前任务必须以 `docs/19-消息通知场景多目标重构方案.md` 为唯一实施基线。
- 不要回退到旧“单场景单通知类型”的实现口径。
- 本轮不考虑历史表、历史数据迁移和兼容脚本，按新模型直接重构。
- 本轮暂不引入接收人规则中心、用户订阅偏好、多语言模板、复杂规则引擎。
- 所有新增或重构代码必须补齐详细简体中文注释。
- 类、接口、枚举、公开方法必须写完整 Javadoc。
- 复杂私有方法也必须写清业务职责、参数、返回值、异常场景。
- 方法内部关键步骤必须写详细简体中文注释。
- 方法内部调用其它方法时，如果调用原因或目的不明显，必须在调用前说明为什么调用、要达成什么业务目的。
- 修改代码时可以同步更新相关注释，但不要为了方便阅读随意删除未改动区域原有注释。
- 如果逻辑变了，注释必须同步更新。
- 默认沿用当前项目现有技术栈、现有分层和现有命名风格，不引入新框架。

## 3. 阶段一提示词

### 3.1 适用目标

- 落新模型基础结构
- 完成后台“通知场景配置”模型与页面重构
- 暂不进入完整执行链路重构

### 3.2 可直接复制提示词

```md
请按 `docs/19-消息通知场景多目标重构方案.md` 作为唯一实施基线，开始落地“阶段一：模型与后台配置重构”。

本轮目标：

1. 落地新通知场景与通知目标配置模型。
2. 后台配置入口改为“通知场景配置”。
3. 支持一个场景下配置多个通知目标。
4. 首批通知目标固定支持：
   - `IN_APP_MESSAGE`
   - `IN_APP_TODO`
   - `MP_SUBSCRIBE`
5. 支持目标配置的查询、保存、预览。

本轮明确范围：

- 通知场景注册模型
- 通知目标配置表或对应实体模型
- 后端配置接口
- 后台页面重构
- 目标配置预览能力
- 必要的枚举、DTO、VO、Query、Mapper、Service、Controller 调整

本轮明确不做：

- 不进入完整事件消费链路重构
- 不重构站内消息执行逻辑
- 不重构外部分发状态机
- 不引入接收人规则中心
- 不引入用户订阅偏好
- 不做历史数据迁移兼容

实现要求：

- 必须严格按文档中的“统一通知场景 + 多通知目标配置”模型落地。
- 后台配置视角必须从“模板管理/渠道配置”切换为“通知场景配置”。
- 一个场景下必须支持同时配置多个通知目标。
- `MP_SUBSCRIBE` 的渠道专属参数统一通过 `config_json` 承载，但页面上不要直接暴露原始 JSON 编辑。
- 预览接口要能够按 `sceneCode + targetType` 预览渲染结果。

代码与注释要求：

- 所有新增或重构代码必须补齐详细简体中文注释。
- 类、接口、枚举、公开方法必须写完整 Javadoc。
- 复杂私有方法也必须补齐方法注释。
- 方法内部关键步骤必须写详细简体中文注释。
- 方法内部调用其它方法时，如果调用原因或目的不明显，必须在调用前说明为什么调用以及希望达成什么业务结果。
- 修改代码时可以更新相关注释，但不要为了阅读方便随意删除未改动区域原有注释。
- 如果逻辑变了，注释必须同步调整。

交付要求：

1. 直接完成代码改动，不只停留在方案描述。
2. 完成后说明：
   - 改了哪些核心文件
   - 后台页面和接口如何调整
   - 当前已支持哪些通知目标配置
   - 本轮未做哪些内容
3. 必须执行必要的编译、测试或前端构建验证；如果无法完成，要明确说明阻塞点。

请先阅读相关现有代码和 `docs/19-消息通知场景多目标重构方案.md`，然后直接开始实施。
```

## 4. 阶段二提示词

### 4.1 适用目标

- 按新模型重构事件消费与目标分流执行
- 站内目标进入站内消息层
- 小程序目标进入外部分发层

### 4.2 可直接复制提示词

```md
请按 `docs/19-消息通知场景多目标重构方案.md` 作为唯一实施基线，开始落地“阶段二：执行链路重构”。

前提说明：

- 默认阶段一的通知场景与通知目标配置模型已经落地。
- 本轮以“一个通知事件可按多个通知目标分流执行”为核心目标。

本轮目标：

1. 重构通知事件消费链路，使其按 `sceneCode` 查询启用的多个 `targetType`。
2. 站内目标：
   - `IN_APP_MESSAGE`
   - `IN_APP_TODO`
   统一进入站内消息表或对应站内执行层。
3. 外部目标：
   - `MP_SUBSCRIBE`
   统一进入分发表，再由 sender 执行真实发送。
4. 统一模板渲染与目标分流逻辑。
5. 同一事件能够同时生成多个通知目标产物。

本轮明确范围：

- 事件实体、事件服务、事件消费逻辑
- 渲染服务
- 站内消息/站内待办落库逻辑
- 外部分发任务落库逻辑
- 小程序 sender 接入链路的适配
- 必要的测试与排障数据结构补齐

本轮明确不做：

- 不扩短信、邮件 sender
- 不引入用户订阅偏好
- 不引入复杂接收人规则中心
- 不做大规模后台页面继续改版
- 不处理历史表和历史数据兼容

实现要求：

- 事件链路必须从“单场景单通知类型”改为“单场景多通知目标”。
- 模板渲染必须按 `sceneCode + targetType` 读取配置。
- 站内消息和站内待办要能共存，但状态处理逻辑必须区分。
- 小程序目标必须统一走分发表，不允许继续在业务层直接发送。
- 分发任务必须固化发送快照，重试时不能回查最新配置。

代码与注释要求：

- 所有新增或重构代码必须补齐详细简体中文注释。
- 类、接口、枚举、公开方法必须写完整 Javadoc。
- 复杂私有方法必须写明业务职责、边界和异常场景。
- 方法内部关键流程必须写详细步骤注释，尤其是：
  - 事件状态流转
  - 目标分流
  - 模板渲染
  - 站内消息与待办分支差异
  - 分发表创建
  - sender 调用原因
- 方法内部调用其它方法时，如果业务目的不明显，必须在调用前说明原因和目的。
- 修改逻辑时同步更新注释，不要随意删除未改动区域原注释。

交付要求：

1. 直接完成代码改动。
2. 完成后说明：
   - 哪些事件链路代码已经按多目标重构
   - 站内消息/站内待办如何分流
   - 小程序通知如何进入分发表
   - 当前链路仍未覆盖哪些目标类型
3. 必须执行必要的编译、测试或链路验证；如果不能完成，要明确说明阻塞点。

请先阅读阶段一落地结果和 `docs/19-消息通知场景多目标重构方案.md`，确认当前代码状态后直接开始实施。
```

## 5. 阶段三提示词

### 5.1 适用目标

- 收口排障能力
- 事件、站内消息、分发任务形成全链路可视化
- 人工重试、死信处理闭环

### 5.2 可直接复制提示词

```md
请按 `docs/19-消息通知场景多目标重构方案.md` 作为唯一实施基线，开始落地“阶段三：排障与收口”。

前提说明：

- 默认阶段一、阶段二已完成基础模型与执行链路改造。
- 本轮重点不是再扩模型，而是把排障、查看、重试和状态收口做完整。

本轮目标：

1. 让排障页面能够清晰查看：
   - 通知事件
   - 同事件下的站内消息/站内待办
   - 同事件下的外部分发任务
2. 支持事件重试、分发重试。
3. 支持人工标记死信。
4. 统一场景、目标、状态展示口径。
5. 补齐必要的测试、状态说明和文档收口。

本轮明确范围：

- 排障查询接口
- 排障详情接口
- 排障列表页面或详情展示
- 事件重试
- 分发重试
- 死信处理
- 关键状态文案和日志补齐

本轮明确不做：

- 不新增短信、邮件等新目标类型
- 不继续扩大后台配置功能范围
- 不引入用户订阅偏好
- 不引入复杂运营报表

实现要求：

- 排障视角必须围绕“一个事件下有哪些通知目标产物”展开。
- 必须能明确区分：
  - 事件处理失败
  - 站内消息已生成
  - 外部分发失败
  - sender 跳过
  - 死信
- 人工重试和人工标记死信要走统一状态机，不允许绕过服务层直接改库。
- 展示口径要使用新的“场景 + 目标”模型，不要再回退到旧模板/旧通知类型混合表达。

代码与注释要求：

- 所有新增或重构代码必须补齐详细简体中文注释。
- 类、接口、枚举、公开方法必须写完整 Javadoc。
- 复杂私有方法也必须写清业务目的、边界和异常场景。
- 方法内部关键步骤必须写详细简体中文注释，尤其是：
  - 排障聚合查询
  - 事件详情组装
  - 分发详情组装
  - 人工重试原因
  - 标记死信原因
- 调用其他方法时，如果原因或目的不明显，必须在调用前说明为什么调用以及希望达成什么业务目的。
- 修改代码时同步更新注释，不要随意删除未改动区域原注释。

交付要求：

1. 直接完成代码改动。
2. 完成后说明：
   - 排障页面/接口现在如何体现“场景 + 多目标”
   - 事件、站内消息、分发任务如何关联展示
   - 重试、死信链路如何收口
   - 剩余未覆盖的边界是什么
3. 必须执行必要的编译、测试或链路验证；如果无法完成，要说明阻塞点。

请先阅读阶段一、阶段二落地结果和 `docs/19-消息通知场景多目标重构方案.md`，然后直接开始实施。
```
