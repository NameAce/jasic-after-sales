# 消息通知一期总方案

## 1. 文档目的

本文档定义售后系统一期消息通知能力的完整设计基线，用于指导后续实现、联调、验收与代码审查。

本文档只描述本次讨论确认的一期范围，不参考历史通知实现，也不兼容旧通知代码设计。后续实现如与本文档冲突，以本文档为准；如需调整，必须先更新决策记录文档，再调整代码。

## 2. 一期范围

### 2.1 目标

一期只解决一个高价值、低歧义、可闭环的通知场景：

- 工单派单后，维修员收到一条站内待办消息
- 工单转派后，旧维修员的待办自动失效，新维修员收到新的待办
- 维修员进入工单详情后，消息记为已读
- 维修员发生真实处理动作后，消息记为已处理
- 工单关闭、完成后，未完成待办自动失效
- 前端可展示消息中心与顶部红点

### 2.2 非目标

一期不包含以下内容：

- 客户端用户通知
- 短信、邮件、微信公众号、小程序订阅消息
- 系统公告、营销消息、运营消息
- 用户通知偏好设置
- 模板后台配置
- 管理员代操作消息状态
- 批量删除消息
- 复杂聚合展示
- 多业务类型统一接入

## 3. 核心业务结论

### 3.1 用户范围

一期只面向 B 端内部用户。

### 3.2 渠道范围

一期只支持：

- 站内消息中心
- 顶部红点

如项目当前已有 WebSocket 基础设施，则消息状态变更后可追加红点刷新推送；如果没有，则一期允许纯接口拉取。

### 3.3 事件范围

一期仅支持一个业务事件：

- `WORK_ORDER_ASSIGNED`

说明：

- 包含首次派单
- 包含转派
- 不再拆成两个不同事件类型
- 通过事件载荷中的 `assignType` 区分 `ASSIGN` 与 `TRANSFER`

### 3.4 业务对象绑定

一期消息全部强绑定业务对象。

当前固定绑定：

- `bizType = WORK_ORDER`
- `bizId = work_order.id`
- `bizNo = work_order.order_no`

## 4. 领域模型

### 4.1 模型总览

一期涉及三个核心领域对象：

1. `NotifyEvent`
   描述通知事件事实，只回答“发生了什么”
2. `NotifyMessage`
   描述用户可见的站内消息，只回答“谁看到了什么、当前状态是什么”
3. `NotifyMessageLog`
   描述消息状态流转日志，只回答“这条消息什么时候因为什么发生了什么变化”

### 4.2 领域职责边界

#### 4.2.1 NotifyEvent

职责：

- 承接业务系统提交的通知事件
- 作为事务后的异步处理入口
- 作为幂等和重试的基础载体

不负责：

- 直接作为用户可见消息
- 直接承载前端展示状态

#### 4.2.2 NotifyMessage

职责：

- 表示一条真正发送给某个用户的站内待办消息
- 提供红点统计、列表查询、详情跳转所需信息
- 承担已读、已处理、失效等状态

#### 4.2.3 NotifyMessageLog

职责：

- 留存状态变更轨迹
- 支持排障、审计、代码 review 验证

## 5. 一期业务规则

### 5.1 生成规则

- 每次派单成功后，生成一个通知事件
- 每次通知事件消费成功后，生成一条站内待办消息
- 每次转派成功后：
  - 旧接收人的有效待办变为失效
  - 新接收人生成一条新的待办
- 同一次业务操作不能生成两条等价的新待办

### 5.2 接收人规则

一期接收人只有一类：

- 当前工单指派维修员，也就是 `assignedUserId`

一期不支持：

- 上级
- 主管
- 协同人
- 抄送人
- 按角色批量接收

### 5.3 已读规则

- 用户进入工单详情页时，如果存在属于当前用户、属于当前工单、状态为 `PENDING` 的待办，则改为 `READ`
- 已读是幂等动作，重复调用不应报错
- `READ` 后消息仍然算有效待办，红点不应消失

### 5.4 已处理规则

- `DONE` 必须绑定真实业务动作
- 一期默认使用工单参与动作 `TECH_ACCEPT` 作为待办完成节点
- 如果接单动作之后发生了重复调用，完成逻辑应保持幂等

### 5.5 失效规则

以下场景会使未完成待办失效：

- 工单被转派，失效原因 `TRANSFERRED`
- 工单关闭，失效原因 `WORK_ORDER_CLOSED`
- 工单完成，失效原因 `WORK_ORDER_COMPLETED`

说明：

- 已 `DONE` 的消息不再转为 `INVALID`
- 只允许 `PENDING` 与 `READ` 进入 `INVALID`

### 5.6 红点规则

顶部红点统计规则：

- 当前登录用户名下
- `todoStatus in (PENDING, READ)`
- 按消息条数计数

不统计：

- `DONE`
- `INVALID`

## 6. 状态机设计

### 6.1 待办状态

- `PENDING`：待处理，未读
- `READ`：已读但未处理
- `DONE`：已处理
- `INVALID`：已失效

### 6.2 状态流转

```text
CREATE -> PENDING
PENDING -> READ
PENDING -> DONE
READ -> DONE
PENDING -> INVALID
READ -> INVALID
DONE -> 终态
INVALID -> 终态
```

### 6.3 状态流转含义

- `CREATE -> PENDING`
  通知事件消费成功，为接收人创建了一条新待办
- `PENDING -> READ`
  接收人进入工单详情页
- `PENDING/READ -> DONE`
  接收人完成真实处理动作
- `PENDING/READ -> INVALID`
  工单已不再需要该接收人继续处理

## 8. 事件与幂等设计

### 8.1 event_key 规则

建议生成规则：

`WORK_ORDER_ASSIGNED:{bizId}:{receiverId}:{operationId}`

说明：

- `bizId`：工单 ID
- `receiverId`：本次新接收人
- `operationId`：同一次派单操作唯一标识

### 8.2 operationId 规则

如果当前工单派单服务里没有稳定操作号，则在派单命令进入服务层时生成一个 UUID，并在同一事务内向下传递。

### 8.3 消费幂等

必须保证：

- 同一个 `event_key` 只会有一条事件记录
- 同一个事件即使重复消费，也不会重复创建消息
- 转派失效逻辑可重复执行而不报错

## 10. 接口设计

### 10.1 获取有效待办数

- 方法：`GET /system/notify/todo/count`

返回示例：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "count": 3
  }
}
```

### 10.2 查询消息分页

- 方法：`GET /system/notify/todo/page`

请求参数：

- `box`：`TODO` 或 `HISTORY`
- `pageNum`
- `pageSize`

规则：

- `TODO` 返回 `PENDING`、`READ`
- `HISTORY` 返回 `DONE`、`INVALID`

返回示例：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "total": 2,
    "rows": [
      {
        "id": 101,
        "title": "你有新的工单待处理",
        "summary": "工单 WO202604180001 已派发给你，请尽快处理",
        "bizType": "WORK_ORDER",
        "bizId": 88,
        "bizNo": "WO202604180001",
        "routeType": "WORK_ORDER_DETAIL",
        "routeValue": "88",
        "todoStatus": "PENDING",
        "invalidReason": null,
        "createTime": "2026-04-18 10:20:30"
      }
    ]
  }
}
```

### 10.3 按消息 ID 标记已读

- 方法：`POST /system/notify/message/{id}/read`

规则：

- 只能操作自己的消息
- 仅 `PENDING` 可转 `READ`
- `READ/DONE/INVALID` 再次调用直接返回成功

### 10.4 按业务对象标记已读

- 方法：`POST /system/notify/message/read-by-biz`

请求示例：

```json
{
  "bizType": "WORK_ORDER",
  "bizId": 88
}
```

规则：

- 进入工单详情页时调用
- 将当前用户、当前工单下所有 `PENDING` 待办改为 `READ`

## 11. 前端设计

### 11.1 页面结构

一期只做一个消息中心页面，包含两个 tab：

- `待处理`
- `历史记录`

### 11.2 列表字段

- 标题
- 摘要
- 工单号
- 创建时间
- 状态标签

### 11.3 点击行为

- 点击消息
- 先调用“按业务对象标记已读”
- 再跳转工单详情页

### 11.4 红点刷新策略

前端至少支持以下刷新时机：

- 登录成功后
- 页面初始化时
- 消息中心返回时
- 工单处理动作成功后

如果后端已有 WebSocket，可在此基础上追加推送刷新。

## 12. 与工单域的接入点

### 12.1 派单成功后

工单服务在事务成功后发布 `WORK_ORDER_ASSIGNED` 事件。

事件载荷至少包含：

- `workOrderId`
- `orderNo`
- `oldAssignedUserId`
- `newAssignedUserId`
- `operatorId`
- `assignType`
- `operationId`

### 12.2 进入工单详情页

调用：

- `markReadByBiz(WORK_ORDER, workOrderId, currentUserId)`

### 12.3 维修员接单

调用：

- `completeTodoByBizAndReceiver(WORK_ORDER, workOrderId, currentUserId, "TECH_ACCEPT")`

### 12.4 工单关闭/完成

调用：

- `invalidateTodoByBiz(WORK_ORDER, workOrderId, reason)`

## 13. 安全与权限规则

- 只允许当前登录用户查看自己的消息
- 只允许当前登录用户将自己的消息标为已读
- 不允许通过前端接口直接把消息改成 `DONE`
- `DONE` 只能由后端业务动作驱动
- `INVALID` 只能由后端业务状态变更驱动

## 14. 审计与排障要求

一期应优先支持以下排查能力：

- 根据工单 ID 查到关联的通知事件
- 根据工单 ID 查到发送给谁的消息
- 能看到消息当前状态
- 能看到消息何时已读、何时已处理、何时失效
- 能定位事件消费失败原因

说明：

- 当前一期上线不以“按工单 ID 显式查询全部通知消息”接口作为阻塞条件
- 如缺少该显式能力，可通过事件查询、当前用户消息分页与消息日志组合排查

## 15. 测试重点

### 15.1 正向场景

- 首次派单生成待办
- 转派后旧待办失效、新待办生成
- 进入详情页后待办已读
- 接单动作后待办完成
- 工单关闭后未完成待办失效

### 15.2 幂等场景

- 同一事件重复发布不重复创建消息
- 同一消息重复已读不报错
- 同一待办重复完成不报错
- 同一工单重复失效不报错

### 15.3 权限场景

- 用户不能修改他人消息状态
