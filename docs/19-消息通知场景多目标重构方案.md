# 消息通知场景多目标重构方案

> 本文档用于固化消息通知模块下一轮重构优化的最终实施基线。
> 后续如另起线程按本方案落地，以本文档为准，不再默认沿用旧“单场景单通知类型”或“模板表/渠道表割裂维护”的实现口径。

---

## 1. 文档定位

- 本文档是当前轮“消息通知模块重构优化”的唯一专项方案。
- 本文档聚焦通知场景建模、配置模型、执行链路、页面交互、分阶段实施和验收要求。
- 本文档默认不兼容历史表结构和历史数据迁移方案，按“新模型直接重构落地”讨论。
- 本文档暂不扩展以下能力：
  - 接收人规则中心
  - 用户订阅偏好
  - 多语言模板
  - 模板版本历史
  - 升级通知策略
  - 复杂编排引擎

说明：

- 当前轮目标是先把“一个通知场景可配置多个通知目标”这条主干模型重构正确。
- 接收人规则、订阅偏好等能力后续如确有需要，再基于本方案继续扩展，不在本轮提前设计过深。

---

## 2. 背景与问题

当前系统的通知模块已经具备以下基础能力：

- 通知事件入库
- 站内待办落库与状态流转
- 小程序外部分发任务与重试
- 通知模板后台配置
- 通知渠道配置

但当前实现存在以下核心问题：

1. 一个 `sceneCode` 当前只绑定一个 `notifyType`，无法表达“同一业务场景同时产出站内消息、站内待办、小程序通知中的多个目标”。
2. 后台配置入口更偏“模板管理 + 渠道配置”视角，不是“业务场景下配置哪些通知目标”的视角，业务理解成本偏高。
3. `站内消息 / 站内待办 / 小程序通知` 三类目标没有被抽象成统一的平级配置对象。
4. 当前渠道配置 DTO 和页面交互明显偏小程序专用，不利于后续扩短信、邮件等目标。
5. 站内侧更偏待办模型，尚未真正形成“站内消息 + 站内待办”双目标统一建模。

本轮重构要解决的问题只有一句话：

**让一个业务通知场景可以按需启用多个通知目标，并由系统分别落到站内或外部分发链路。**

---

## 3. 重构目标

本轮重构的明确目标如下：

1. 统一通知场景建模，场景只表达“什么业务事件发生了”。
2. 引入“通知目标”概念，通知目标表达“这个场景要生成什么通知产物”。
3. 第一批通知目标只支持：
   - `IN_APP_MESSAGE`：站内消息
   - `IN_APP_TODO`：站内待办
   - `MP_SUBSCRIBE`：小程序通知
4. 同一个场景允许启用其中一个、多个或全部目标。
5. 站内目标统一进入站内消息表。
6. 外部目标统一进入分发表，由 sender 执行真实发送。
7. 后台配置入口统一改为“通知场景配置”，而不是继续拆成割裂的模板管理和渠道配置入口。

本轮明确不做：

- 不做自由新增任意场景。
- 不做任意自定义接收人规则。
- 不做用户订阅退订。
- 不做渠道优先级降级或升级编排。
- 不做复杂规则引擎。

---

## 4. 设计原则

### 4.1 统一入口

- 后台统一从“通知场景配置”进入。
- 配置对象是“场景 + 通知目标”，而不是“端”。

### 4.2 场景与目标分离

- `sceneCode` 只表达业务语义。
- `targetType` 只表达通知产物类型。
- 两者不可混用。

### 4.3 站内与外部分治

- 站内消息和站内待办属于站内执行层。
- 小程序通知属于外部分发层。
- 配置入口统一，执行链路分治。

### 4.4 先收口再扩展

- 先把 `IN_APP_MESSAGE / IN_APP_TODO / MP_SUBSCRIBE` 做稳定。
- 后续若新增 `SMS / EMAIL`，只扩目标类型和 sender，不回头推翻模型。

### 4.5 注释必须完整

- 本轮属于多人、多线程可接力的重构，不允许靠上下文记忆理解代码。
- 所有新增或重构的类、接口、枚举、方法、关键流程都必须补齐详细简体中文注释。

## 5. 术语定义

| 术语 | 含义 | 说明 |
| --- | --- | --- |
| `scene` | 通知场景 | 业务动作触发后的统一场景标识 |
| `target` | 通知目标 | 当前场景要产出的通知类型 |
| `event` | 通知事件 | 一次真实发生的业务通知事实 |
| `message` | 站内消息产物 | 包括站内消息和站内待办 |
| `dispatch` | 外部分发任务 | 小程序、短信、邮件等外部通知任务 |
| `sender` | 发送器 | 某个外部通知目标的执行适配器 |
| `payload` | 快照负载 | 事件处理和分发重试使用的固定上下文 |

## 6. 总体方案

本轮最终采用以下方案：

**统一通知场景 + 多通知目标配置 + 站内执行层 / 外部分发层分治**

结构说明：

1. 一个通知场景由系统注册，后台不可随意新增未知场景。
2. 一个通知场景下可配置多条通知目标。
3. 每条通知目标独立控制：
   - 是否启用
   - 模板内容
   - 跳转方式
   - 渠道专属参数
4. 站内目标统一写入站内消息表。
5. 外部目标统一写入分发表，再由 sender 异步消费。

示例：

| 场景 | 通知目标 | 是否启用 |
| --- | --- | --- |
| 工单派单 | `IN_APP_TODO` | 是 |
| 工单派单 | `IN_APP_MESSAGE` | 否 |
| 工单派单 | `MP_SUBSCRIBE` | 否 |
| 工单关闭 | `IN_APP_MESSAGE` | 是 |
| 工单关闭 | `MP_SUBSCRIBE` | 是 |
| 评价邀请 | `MP_SUBSCRIBE` | 是 |

## 7. 模块划分

本轮按职责拆分模块，不按端拆多个平行系统。

### 7.1 `notify-scene`

职责：

- 通知场景注册
- 通知目标配置维护
- 模板变量元数据维护
- 后台“通知场景配置”接口

不负责：

- 站内消息状态流转
- 外部分发执行
- 渠道真实发送

### 7.2 `notify-message`

职责：

- 站内消息落库
- 站内待办落库
- 已读、完成、失效、计数、分页

不负责：

- 外部分发
- 场景配置维护

### 7.3 `notify-dispatch`

职责：

- 外部分发任务落库
- 抢占处理
- 失败重试
- 死信管理
- 发送结果回写

不负责：

- 场景配置维护
- 站内消息状态流转

### 7.4 `notify-sender`

职责：

- 按目标类型执行真实外部发送
- 首批至少保留 `MP_SUBSCRIBE` sender
- 后续可扩 `SMS / EMAIL`

不负责：

- 分发状态机维护
- 场景配置维护

## 8. 数据模型设计

本轮建议直接按新模型重构，核心只保留 5 张表。

### 8.1 `notify_scene`

职责：定义系统允许的通知场景。

字段建议：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `scene_code` | varchar(64) | 场景编码，全局唯一 |
| `scene_name` | varchar(128) | 场景名称 |
| `biz_type` | varchar(64) | 业务类型 |
| `event_code` | varchar(64) | 事件编码 |
| `status` | tinyint | 场景状态：1启用，0停用 |
| `remark` | varchar(255) | 备注 |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |

约束建议：

- `uk_scene_code(scene_code)`

说明：

- 场景表只表达“发生了什么通知场景”。
- 它不承载具体通知目标配置。

### 8.2 `notify_scene_target`

职责：定义某个场景要生成哪些通知目标。

字段建议：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `scene_code` | varchar(64) | 场景编码 |
| `target_type` | varchar(32) | 通知目标类型 |
| `enabled` | tinyint | 目标开关：1启用，0停用 |
| `title_template` | varchar(128) | 标题模板 |
| `content_template` | varchar(512) | 内容模板 |
| `route_type` | varchar(64) | 跳转类型 |
| `route_value_template` | varchar(256) | 跳转值模板 |
| `config_json` | text | 目标专属参数 |
| `remark` | varchar(255) | 备注 |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |

约束建议：

- `uk_scene_target(scene_code, target_type)`

目标类型首批固定为：

- `IN_APP_MESSAGE`
- `IN_APP_TODO`
- `MP_SUBSCRIBE`

说明：

- 这张表是本轮重构的核心。
- 同一场景下每种通知目标最多一条配置。
- 一个场景可以启用多个通知目标。

### 8.3 `notify_event`

职责：记录一次真实发生的通知事件。

字段建议：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `event_key` | varchar(128) | 幂等键，全局唯一 |
| `scene_code` | varchar(64) | 通知场景编码 |
| `biz_type` | varchar(64) | 业务类型 |
| `biz_id` | bigint | 业务ID |
| `biz_no` | varchar(64) | 业务编号 |
| `payload_json` | text | 业务快照 |
| `status` | varchar(32) | 事件状态 |
| `retry_count` | int | 重试次数 |
| `next_retry_time` | datetime | 下次重试时间 |
| `processing_time` | datetime | 开始处理时间 |
| `error_message` | varchar(500) | 最近一次失败原因 |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |

约束建议：

- `uk_event_key(event_key)`
- `idx_status_next_retry(status, next_retry_time)`
- `idx_processing_time(status, processing_time)`
- `idx_scene_biz(scene_code, biz_type, biz_id)`

说明：

- 事件表只回答“这次通知事实是否已被系统消费完成”。
- 事件表不直接关心站内还是外部目标。

### 8.4 `notify_message`

职责：统一承载站内消息和站内待办。

字段建议：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `event_id` | bigint | 来源事件ID |
| `scene_code` | varchar(64) | 通知场景编码 |
| `target_type` | varchar(32) | `IN_APP_MESSAGE` 或 `IN_APP_TODO` |
| `biz_type` | varchar(64) | 业务类型 |
| `biz_id` | bigint | 业务ID |
| `biz_no` | varchar(64) | 业务编号 |
| `receiver_id` | bigint | 接收人ID |
| `receiver_name` | varchar(64) | 接收人名称快照 |
| `title` | varchar(128) | 标题 |
| `content` | varchar(512) | 内容 |
| `route_type` | varchar(64) | 跳转类型 |
| `route_value` | varchar(256) | 跳转值 |
| `message_status` | varchar(32) | 消息状态 |
| `todo_status` | varchar(32) | 待办状态 |
| `read_time` | datetime | 已读时间 |
| `done_time` | datetime | 已完成时间 |
| `invalid_time` | datetime | 已失效时间 |
| `ext_json` | text | 扩展信息 |
| `create_time` | datetime | 创建时间 |

- `IN_APP_MESSAGE` 只走消息已读等状态。
- `IN_APP_TODO` 走待办已读、完成、失效等状态。
- 第一阶段先统一一张表承载，控制实现复杂度。

职责：承载外部通知目标的发送任务。

字段建议：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `event_id` | bigint | 来源事件ID |
| `scene_code` | varchar(64) | 通知场景编码 |
| `target_type` | varchar(32) | 当前首批为 `MP_SUBSCRIBE` |
| `receiver_address` | varchar(128) | 接收地址，如 openid |
| `title` | varchar(128) | 标题快照 |
| `content` | varchar(512) | 内容快照 |
| `dispatch_status` | varchar(32) | 分发状态 |
| `retry_count` | int | 重试次数 |
| `next_retry_time` | datetime | 下次重试时间 |
| `processing_time` | datetime | 开始处理时间 |
| `result_code` | varchar(64) | 结果码 |
| `result_message` | varchar(500) | 结果说明 |
| `payload_json` | text | 分发快照 |
| `channel_response_json` | text | 渠道响应快照 |
| `sent_time` | datetime | 发送成功时间 |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |

索引建议：

- `idx_dispatch_status_next_retry(dispatch_status, next_retry_time)`

说明：

- 所有外部通知统一走分发表。
- 分发表中的 `payload_json` 必须保存渲染后快照，重试时不回查当前配置。

## 10. 运行时链路

### 10.1 统一主流程

运行时统一按以下流程执行：

1. 业务动作发生。
2. 生成一条 `notify_event`。
3. 根据 `scene_code` 查询已启用的 `notify_scene_target`。
4. 遍历每个通知目标配置。
5. 根据变量渲染模板。
6. 如果目标是 `IN_APP_MESSAGE / IN_APP_TODO`，写入 `notify_message`。
7. 如果目标是 `MP_SUBSCRIBE`，写入 `notify_dispatch`。
8. 分发任务异步消费，sender 执行真实发送。
9. 分发结果回写任务状态。

### 10.2 站内目标处理

- `IN_APP_MESSAGE`：创建站内消息，支持已读、分页、红点计数。
- `IN_APP_TODO`：创建站内待办，支持已读、完成、失效、计数。

### 10.3 外部目标处理

- `MP_SUBSCRIBE`：先落分发表，再由 sender 发送。
- 分发失败进入重试。
- 超过重试次数进入死信。

## 11. `config_json` 约定

本轮只对 `MP_SUBSCRIBE` 约定结构。

示例：

```json
{
  "templateId": "微信订阅消息模板ID",
  "pagePathTemplate": "pages/order/evaluate?workOrderId=${workOrderId}",
  "fieldMapping": [
    { "field": "thing1", "value": "${orderNo}" },
    { "field": "phone_number2", "value": "${customerMobile}" },
    { "field": "thing3", "value": "${companyName}" }
  ]
}
```

约束：

- 后台页面不直接暴露原始 JSON 大文本编辑。
- 页面按字段拆开维护：
  - 模板 ID
  - 页面路径模板
  - 字段映射表格
- 保存时由后端或前端统一组装成 `config_json`。

## 14. 代码结构建议

建议保留并重构为以下职责边界：

### 14.1 `NotifySceneRegistry`

职责：

- 注册允许的 `sceneCode`
- 提供场景元数据
- 提供变量白名单
- 提供默认目标配置元数据

### 14.2 `NotifySceneTargetConfigService`

职责：

- 查询场景下所有目标配置
- 保存场景下所有目标配置
- 校验同一场景的目标配置完整性

### 14.3 `NotifyRenderService`

职责：

- 渲染标题、内容、跳转参数
- 校验变量是否合法

### 14.4 `NotifyEventService`

职责：

- 创建通知事件
- 事件状态流转
- 失败重试

### 14.5 `NotifyMessageService`

职责：

## 16. 注释与代码实现约束

本轮重构必须严格遵守以下注释要求。

### 16.1 总体要求

- 所有新增或重构代码的注释统一使用简体中文。
- 类、接口、枚举、公开方法必须写完整 Javadoc。
- 复杂私有方法也必须补齐方法注释。
- 方法内部关键步骤必须写详细注释。
- 方法内部调用其他方法时，若调用原因或目的不明显，必须在调用前说明“为什么调用、要达成什么业务目的”。

### 16.2 类注释要求

类注释必须说明：

- 该类的业务职责
- 该类处理的边界
- 该类不负责什么
- 该类与场景、目标、事件、站内消息、分发或 sender 的关系

### 16.3 方法注释要求

方法注释必须说明：

- 方法做什么
- 入参与返回值的业务含义
- 异常场景
- 状态变化的业务语义

### 16.4 方法内部注释要求

以下场景必须写方法内部详细注释：

- 事件状态流转
- 分发状态流转
- 幂等控制
- 模板渲染
- 目标分流
- 站内消息与待办分支差异
- 外部通知跳过、失败、重试、死信
- 调用其他服务或方法的业务目的

### 16.5 调用其它方法时的注释要求

如果方法内部调用其它方法，而调用原因不是一眼就能看懂，必须在调用前补充注释说明：

- 为什么此处必须调用该方法
- 调用后期望达成什么业务结果
- 如果不调用会带来什么问题

### 16.6 修改原代码注释的要求

- 开发过程中允许修改代码。
- 如果逻辑变了，必须同步更新相关注释。
- 未改动区域不要为了阅读方便随意删除原有注释。
- 不允许为了缩短文件或减少视觉噪音，删除与本轮改动无关的历史有效注释。
- 如果原注释已明显错误、过期或与新逻辑冲突，可在本次改动范围内一并修正。

### 16.7 禁止项

- 禁止只写“调用方法”“设置字段”“进入判断”这类低价值注释。
- 禁止新增英文业务注释。
- 禁止直接删除原有仍然有效的业务注释。
- 禁止只改代码不改注释。

## 19. 最终结论

本轮消息通知模块重构最终采用以下方案：

**以“通知场景”为统一入口，以“通知目标”为核心配置粒度，一个场景下可配置多个目标，首批支持 `站内消息 / 站内待办 / 小程序通知`；站内目标统一进入站内执行层，外部目标统一进入分发执行层；后台统一通过“通知场景配置”页面进行维护。**

本方案允许分阶段落地，但原则上只拆为：

1. 模型与后台配置重构
2. 执行链路重构
3. 排障与收口

后续另起线程按本文档实施时，应直接以本文档为基线推进，不再回退到旧“单场景单通知类型”的实现口径。
