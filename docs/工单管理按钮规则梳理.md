# 工单管理按钮规则梳理

> 口径说明：本文按当前代码实现整理，不默认套用旧需求文档。按钮显隐以 PC 工单管理为主，并结合后端实际权限兜底规则。

## 一、核心结论

工单管理按钮不是前端单纯按状态硬编码出来的，而是后端按以下条件综合计算 `availableActions` 后返回给前端：

1. 当前用户是否能查看该工单。
2. 当前用户与工单的业务关系。
3. 当前工单主状态。
4. 当前账号是否具备对应基础权限点。
5. 服务方式、建单人、当前受理公司等实例条件。

前端主要负责：

- 根据 `availableActions` 渲染按钮。
- 在「当前处理」和「历史转出/只读」视图下做少量展示过滤。
- 详情页额外过滤掉「上传寄件单号」入口。

## 二、通用规则

| 规则项 | 说明 |
|---|---|
| 列表访问 | 必须具备 `workorder:list`。列表、统计、详情接口都依赖该权限。 |
| 平台账号 | 当前代码明确拒绝平台账号参与工单业务。平台账号不默认查看或操作工单。 |
| 可见不等于可操作 | 能看到工单，只代表具备查看权，不代表能执行派单、接单、转单等动作。 |
| 按钮来源 | 行内按钮和详情按钮主要来自后端 `availableActions`。 |
| 后端兜底 | 每个动作接口都会再次调用后端权限服务校验，不能只依赖前端隐藏按钮。 |
| 历史视图 | 历史转出/只读视图原则上只读，只额外允许展示「上传寄件单号」这一例外动作。 |
| 详情页限制 | 详情页不展示「上传寄件单号」，该动作只在列表行内展示。 |

## 三、工单关系口径

| 关系 | 含义 | 操作倾向 |
|---|---|---|
| 当前受理公司 | 当前登录公司等于工单 `current_accept_company_id` | 管理动作的主要前提，如派单、转单、复检、关闭。 |
| 当前维修员 | 当前用户等于工单 `assigned_user_id` | 技师动作的主要前提，如接单、维修登记。 |
| 建单公司 | 当前登录公司等于工单 `create_company_id` | 当前主要用于关系识别；寄件单号补录进一步要求建单人本人。 |
| 历史参与方 | 当前公司曾处理或参与过，但现在不是当前受理方 | 默认只读。 |
| 总部观察者 | 总部基于参与关系或总部视角看到工单 | 默认只读。 |

## 四、主状态口径

| 主状态 | 中文含义 | 典型下一步 |
|---|---|---|
| `PENDING_ASSIGN` | 待派单 | 派单；寄修建单人可补寄件单号。 |
| `PENDING_TECH_ACCEPT` | 待接单 | 被派维修员接单；寄修建单人可补寄件单号。 |
| `IN_PROGRESS` | 维修中 | 当前维修员维修登记；当前受理公司可转单。 |
| `COMPLETED` | 已完成 | 当前受理公司可复检、转单、关闭。 |
| `CLOSED` | 已关闭 | 只读，不再展示业务操作按钮。 |

## 五、按钮规则明细

| 按钮 | 什么时候显示 | 谁能操作 | 谁不能操作 | 为什么 |
|---|---|---|---|---|
| 查询 | 进入工单列表后显示 | 有 `workorder:list` 且能进入页面的人 | 无列表权限的人 | 查询不改变业务状态，只读取可见范围内数据。 |
| 重置 | 进入工单列表后显示 | 有 `workorder:list` 且能进入页面的人 | 无列表权限的人 | 只重置筛选条件，不改变业务状态。 |
| 展开/收起筛选 | 搜索项超过折叠阈值时显示 | 有列表访问能力的人 | 无列表权限的人 | 只是前端筛选区交互。 |
| 工单号/查看详情 | 列表中工单号始终可点击 | 当前用户能查看该工单 | 无工单可见权的人、平台账号 | 详情接口仍会走 `canView`，防止通过链接、通知、待办绕过权限。 |
| 建维修订单 | 前端判断 `hasAuth('workorder:add')` 为 true 时显示 | 有 `workorder:add` 的账号 | 无 `workorder:add` 的账号；维修员模板默认没有 | 建单是新增业务对象，不依赖某一张工单状态，主要看基础权限点。 |
| 派单 | `availableActions` 包含 `ASSIGN` 时显示 | 当前登录公司是当前受理公司；工单状态为 `PENDING_ASSIGN`；账号有 `workorder:assign` | 历史参与方、总部只读观察者、非当前受理公司、非待派单状态、无派单权限的人 | 派单决定当前受理公司内由谁维修，只能由当前承接方在待派单阶段执行。 |
| 维修员接单 | `availableActions` 包含 `TECH_ACCEPT` 时显示 | 当前用户是该工单 `assigned_user_id`；状态为 `PENDING_TECH_ACCEPT`；有 `workorder:accept` | 未被派到该单的人、同公司其他维修员、管理岗但非被派维修员、非待接单状态、无接单权限的人 | 接单是被指派维修员确认开始处理，不能由公司内任意人代接。 |
| 转单 | `availableActions` 包含 `TRANSFER` 时显示 | 当前登录公司是当前受理公司；状态为 `IN_PROGRESS` 或 `COMPLETED`；有 `workorder:transfer` | 历史参与方、非当前受理公司、待派单、待接单、已关闭、无转单权限的人 | 转单会切换当前受理公司，并把工单重置为待派单，只能由当前承接方发起。 |
| 维修登记 | `availableActions` 包含 `REPAIR_FINISH` 时显示 | 当前用户是被派维修员；状态为 `IN_PROGRESS`；有 `workorder:repair` | 管理岗但不是当前维修员、同公司其他维修员、非维修中状态、无维修登记权限的人 | 维修登记代表实际维修完成，会把工单推进到 `COMPLETED`。 |
| 复检登记 | `availableActions` 包含 `REVIEW` 时显示 | 当前登录公司是当前受理公司；状态为 `COMPLETED`；有 `workorder:review` | 维修中未完成、已关闭、历史参与方、非当前受理公司、无复检权限的人 | 复检属于完成后的管理动作，不是维修员继续维修动作。 |
| 上传寄件单号 | 列表 `availableActions` 包含 `UPLOAD_SEND_EXPRESS` 时显示；历史转出/只读列表也允许显示；详情页不显示 | 工单可见；服务方式为 `MAIL`；状态为 `PENDING_ASSIGN` 或 `PENDING_TECH_ACCEPT`；当前用户是首条 `CREATE` 流转识别出的建单人本人 | 到店维修、维修中、已完成、已关闭、非建单人本人、旧数据无法识别建单人、不可见工单 | 当前代码把它定义为“建单人本人补物流资料”，不是派单员或当前受理方动作，也不要求 `workorder:assign`。 |
| 关闭工单 | `availableActions` 包含 `CLOSE` 时显示 | 当前登录公司是当前受理公司；状态为 `COMPLETED`；有 `workorder:close` | 非当前受理公司、历史参与方、总部只读、待派单、待接单、维修中、已关闭、无关闭权限的人 | 独立关单只允许 `COMPLETED -> CLOSED`。维修员接单时选择“无故障”的自动闭单不通过独立关闭按钮暴露。 |

## 六、列表视图差异

| 视图 | 展示逻辑 |
|---|---|
| 当前处理 | 展示后端返回的完整流程动作，如派单、接单、转单、维修登记、复检、关闭等。 |
| 历史转出/只读 | 原则上只读；即使后端返回多个动作，前端也只允许展示「上传寄件单号」这个例外动作。 |
| 全部视图 | 当前 PC 页面主要使用当前处理和历史转出/只读；后端查询对象支持 `ALL`，但列表操作列不按 `ALL` 展示动作。 |

## 七、详情页按钮差异

详情抽屉按钮同样来自详情接口的 `availableActions`，但有一个特殊过滤：

| 动作 | 列表页 | 详情页 |
|---|---|---|
| 派单 | 可显示 | 可显示 |
| 维修员接单 | 可显示 | 可显示 |
| 转单 | 可显示 | 可显示 |
| 维修登记 | 可显示 | 可显示 |
| 复检登记 | 可显示 | 可显示 |
| 关闭工单 | 可显示 | 可显示 |
| 上传寄件单号 | 可显示 | 不显示 |

原因：当前代码明确把「上传寄件单号」定义为列表行内补资料动作，避免用户误以为它仍是详情页内的当前承接方处理动作。

## 八、角色模板默认能力

| 角色模板 | 默认工单能力 |
|---|---|
| 管理员类 `js-admin` / `admin` | 工单列表、建单、派单、转单、复检、关闭。 |
| 维修员 `repairer` | 工单列表、维修员接单、维修登记。 |
| 平台账号 | 当前不参与工单业务，不默认具备工单查看或操作能力。 |

## 九、只读原因展示

当当前列表行没有可执行动作，并且后端返回 `readonlyReason` 时，前端会展示只读原因。

常见文案包括：

| 文案 | 典型原因 |
|---|---|
| 当前非受理方，仅可查看 | 当前公司是历史参与方，但不是当前受理方。 |
| 当前由网点处理，仅可查看 | 总部观察者视角，只能看，不能操作。 |
| 当前工单已关闭，仅可查看 | 工单已经关闭。 |
| 当前由其他维修人员处理 | 当前用户所在公司可见，但该单已派给其他维修员。 |
| 当前待派单，请由负责人员处理 | 状态待派单，但当前用户无派单动作能力。 |
| 当前待接单，请由负责维修人员处理 | 状态待接单，但当前用户不是被派维修员或无接单权限。 |
| 当前维修中，请由负责人员处理 | 状态维修中，但当前用户无维修或管理动作能力。 |
| 当前工单已完成，待复检或关闭 | 状态已完成，但当前用户无复检或关闭权限。 |

## 十、容易混淆的点

1. 有菜单权限不等于能操作所有工单。  
   例如有 `workorder:repair`，但不是这张单的当前维修员，仍不能维修登记。

2. 同公司不等于能操作。  
   同一当前受理公司内，派单、转单、复检、关闭看管理权限；接单、维修登记看是否为当前被派维修员。

3. 能看见不等于能点击。  
   历史参与方、总部观察者通常能看详情，但默认只读。

4. 上传寄件单号是特殊例外。  
   它不是派单员动作，也不是当前受理方动作，而是“寄修 + 待接单窗口 + 建单人本人”的补资料动作。

5. 关闭工单只处理已完成状态。  
   待接单时维修员选择“无故障”会在接单流程内部自动闭单，不单独展示关闭按钮。
