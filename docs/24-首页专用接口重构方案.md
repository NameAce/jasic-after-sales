# 首页专用接口重构方案

## 1. 文档目的

- 本文档用于固化 `jasic-ui-antd` 首页统计重构的最终确认方案，作为后续另起线程实施开发、联调、验收的唯一基线。
- 本次重构目标聚焦“首页专用接口整理与替换”，不扩大到整站路由体系、权限体系、菜单体系或非首页页面的全面重构。
- 本次方案仅包含后端接口与后端聚合能力重构，不包含前端页面改造；前端切换由前端同事后续单独实施。
- 本文档优先级低于当轮对话中用户的最新确认；若后续口径发生变化，应新增补充说明或替代方案文档，而不是直接继续沿用旧口径开发。

## 2. 背景与问题

### 2.1 当前首页分流现状

- 当前前端首页入口位于 `jasic-ui-antd/src/views/home/index.vue`。
- 首页不是按公司类型 `currentTypeCode` 分流，而是按当前登录主体类型 `currentSubjectType` 分流：
  - `PLATFORM`：平台首页
  - `HQ`：总部首页
  - 其它：服务主体首页
- 当前分流逻辑已经稳定运行，本次不调整为按具体公司类型再细分首页。

### 2.2 当前统计方式存在的主要问题

#### 2.2.1 首页统计口径混杂

- 部分首页数据来自真正的聚合接口，例如工单状态统计、总部网点汇总。
- 部分首页数据来自分页列表接口，再由前端自行按 `records` 做二次聚合。
- 这种做法会导致“列表页接口”和“首页统计接口”语义混用，后续维护时难以判断字段口径归属。

#### 2.2.2 分页列表二次聚合会失真

- 当前首页趋势图存在直接请求分页列表后，在前端根据返回记录按日期做计数的情况。
- 当记录数超过前端写死的 `pageSize` 时，趋势数据会被截断，统计结果天然不准确。
- 当前平台首页也存在类似问题，例如用公司列表、操作日志列表在前端取前若干页数据后自行汇总。

#### 2.2.3 部分展示文案与实际数据语义不完全一致

- 当前“消息数”实际更接近“历史待办数”，而不是广义的“全部消息数”。
- 当前“待办数”实际统计的是“待处理中的活跃待办”，包含“未读待办”和“已读未处理待办”。
- 如果继续沿用旧接口和旧命名，会造成前后端对字段含义的长期误解。

## 3. 本次重构目标

### 3.1 目标范围

- 为首页提供专用只读聚合接口，不再让首页依赖分页列表接口自行拼装统计。
- 按主体类型拆分首页接口入口，提升语义清晰度和后续扩展性。
- 统一首页统计字段命名、业务口径和返回结构。
- 保留现有能复用的稳定聚合能力，避免无意义重写。
- 输出后端实施基线，供后续前端同事按新接口协议接入。

### 3.2 非目标范围

- 本次不改为按 `currentTypeCode` 继续细分首页。
- 本次不改动非首页列表页、详情页、表单页的接口协议。
- 本次不重构系统权限架构、登录流程、公司切换流程和菜单分配逻辑。
- 本次不包含前端页面代码修改、前端接口切换和前端样式调整。
- 本次不为了首页改造而删除未修改区域的原有注释。

## 4. 最终确认口径

## 4.1 首页主体拆分口径

- `SERVICE` 主体先只保留一套首页，不按更细公司类型继续拆分。
- `HQ` 主体保留总部运营看板能力。
- `PLATFORM` 主体保留系统治理类首页，不混入工单业务看板。

## 4.2 首页统计字段业务口径

### 4.2.1 服务主体首页

- 待办数：包含“未读待办”和“已读未处理待办”。
- 消息数：明确调整为“历史待办数”，不再使用含糊的“消息数”语义。
- 趋势图时间窗口：固定最近 7 天。
- 工单趋势：按建单时间统计建单量，不改成接单量、完工量或关闭量趋势。

### 4.2.2 总部首页

- 保留总部首页独有的网点汇总与网点排行能力。
- 总部首页中的工单统计仍以总部权限上下文为准，不接受前端额外指定主体口径。

### 4.2.3 平台首页

- 平台首页只展示组织治理相关统计：
  - 公司总数
  - 启用公司数
  - 主体类型分布
  - 用户总数
  - 角色总数
  - 通知场景总数
  - 操作日志近 7 天趋势
  - 操作日志失败数
- 平台首页不混入工单业务统计。

## 4.3 接口组织方式

- Controller 按主体拆分，不再混合在一个总首页 Controller 中。
- 每个主体先提供一个 `home` 总览接口，一次返回该首页全部数据块。
- 前端后续应改为直接消费主体对应的 `home` 接口，不再自行汇总分页列表结果；但该项不属于本次后端实施范围。

## 5. 总体设计

## 5.1 Controller 拆分

- 新增 `PlatformDashboardController`
- 新增 `HqDashboardController`
- 新增 `ServiceDashboardController`

建议路由如下：

- `/dashboard/platform/home`
- `/dashboard/hq/home`
- `/dashboard/service/home`

说明：

- 路由命名采用主体维度拆分，便于接口语义清晰、权限控制清晰、Swagger 文档清晰。
- 后续如果某个主体首页需要扩展额外接口，也应继续挂在各自主体 Controller 下，不回退到混合 Controller。

## 5.2 Service 拆分

- 新增 `PlatformDashboardService`
- 新增 `HqDashboardService`
- 新增 `ServiceDashboardService`

说明：

- 首页编排逻辑放在各自主体的 Dashboard Service 中。
- 已有稳定聚合能力继续在底层复用，例如工单状态统计、总部网点汇总。
- 不强行抽象一个“大而全”的 DashboardService，避免三类主体的业务语义彼此污染。

## 5.3 Mapper 与 SQL 复用原则

- 现有可复用聚合能力优先复用：
  - 工单状态统计 `status-count`
  - 总部网点汇总 `hq-site-summary`
- 现有分页列表接口仅继续服务列表页，不再让首页直接拿来凑统计。
- 对于首页专用趋势、总览、分布统计，如当前没有稳定聚合 SQL，则新增首页专用 Mapper 查询，不复用列表分页 SQL 再做内存聚合。

## 6. 现有接口复用与淘汰策略

## 6.1 继续复用的稳定能力

### 6.1.1 工单状态统计

- 现有接口：`/system/work-order/status-count`
- 处理方式：保留，作为 `ServiceDashboardService` 与 `HqDashboardService` 内部可复用能力。
- 原因：该接口本身就是后端聚合查询，不依赖前端分页截断结果，统计语义稳定。

### 6.1.2 总部网点汇总

- 现有接口：`/system/work-order/hq-site-summary`
- 处理方式：保留，作为 `HqDashboardService` 内部可复用能力。
- 原因：该接口本身就是总部看板专用聚合能力，复用成本低，业务语义清晰。

### 6.1.3 最新动态列表

- 现有接口：`/system/notify/todo/page?box=HISTORY`
- 处理方式：可以继续用于“最新动态列表展示”这一类列表型数据。
- 原因：这里使用的是“取最近若干条列表记录”，不是拿分页结果做总数或趋势统计，风险相对可控。

## 6.2 不再继续用于首页统计的接口使用方式

### 6.2.1 不再使用分页工单列表拼趋势

- 现状：前端通过 `/system/work-order/list?pageSize=200` 拉取列表后按 `createTime` 自行统计近 7 天趋势。
- 问题：当数据超过 `pageSize` 时趋势必然失真。
- 调整：改为后端首页专用趋势聚合查询。

### 6.2.2 不再使用待办分页列表拼趋势

- 现状：前端通过 `/system/notify/todo/page?pageSize=200` 拉取待办列表后按 `createTime` 自行统计近 7 天趋势。
- 问题：同样会被分页截断。
- 调整：改为后端首页专用趋势聚合查询。

### 6.2.3 不再使用公司分页列表拼平台首页统计

- 现状：前端通过 `/org/company/list?pageSize=500` 自行计算公司总数、启用公司数、主体分布。
- 问题：数据量超过 `500` 后统计失真；同时首页统计语义与列表页分页语义混杂。
- 调整：改为平台首页专用组织概览聚合查询。

### 6.2.4 不再使用操作日志分页列表拼趋势

- 现状：前端通过 `/log/oper-log/list?pageSize=500` 统计近 7 天操作日志数量趋势与失败数。
- 问题：分页截断后统计失真。
- 调整：改为平台首页专用日志趋势聚合查询。

### 6.2.5 不再用列表 total 间接表达首页语义

- 现状：用户总数、角色总数、通知场景总数通过列表接口 `pageSize=1` 再取 `total`。
- 问题：技术上能用，但首页统计语义不清晰，后续很容易继续滥用列表接口。
- 调整：统一收敛到平台首页专用总览接口返回。

## 7. 目标接口设计

## 7.1 服务主体首页接口

### 7.1.1 接口定义

- 路径：`GET /dashboard/service/home`
- Controller：`ServiceDashboardController`
- 权限建议：与首页访问权限保持一致；如首页本身依赖工单权限，则在 Service 内部按能力分块兜底。

### 7.1.2 返回结构建议

```json
{
  "overview": {
    "activeTodoCount": 0,
    "historyTodoCount": 0,
    "workOrderTotal": 0
  },
  "workOrderStatus": {
    "all": 0,
    "pendingAssign": 0,
    "pendingTechAccept": 0,
    "inProgress": 0,
    "completed": 0,
    "closed": 0
  },
  "trend7d": {
    "dayKeys": ["2026-05-01", "2026-05-02"],
    "createdWorkOrderCounts": [0, 0],
    "activeTodoCounts": [0, 0]
  },
  "latestHistoryTodos": [
    {
      "id": 1,
      "title": "示例标题",
      "summary": "示例摘要",
      "bizType": "WORK_ORDER",
      "bizId": 1001,
      "routeType": "ROUTE",
      "routeValue": "1001",
      "todoStatus": "DONE",
      "createTime": "2026-05-01 10:00:00"
    }
  ]

```

### 7.1.3 字段说明

- `overview.activeTodoCount`：活跃待办数，口径为 `PENDING + READ`。
- `overview.historyTodoCount`：历史待办数，口径为 `DONE + INVALID`。
- `overview.workOrderTotal`：当前首页视角下工单总数。
- `workOrderStatus`：当前首页视角下各主状态统计。
- `trend7d.createdWorkOrderCounts`：最近 7 天建单量趋势。
- `trend7d.activeTodoCounts`：最近 7 天待办生成量趋势。
- `latestHistoryTodos`：首页最新动态列表，建议最多返回 10 条。

## 8. 实现约束

## 8.1 分层约束

- 严格沿用 `Controller -> Service -> Mapper` 分层。
- Controller 只负责参数接收、权限声明、结果返回，不承担聚合编排。
- Service 负责首页业务口径编排、复用旧能力、聚合多个 Mapper 结果。
- Mapper 负责首页所需聚合 SQL，不在 Controller 或前端中补做统计逻辑。

## 8.2 权限与数据范围约束

- 首页统计全部以后端当前登录上下文为准。
- 前端不得通过额外参数自行指定主体口径、公司口径或数据范围口径。
- `HQ`、`SERVICE`、`PLATFORM` 各自主体的首页接口只返回当前主体可见数据。
- 对于工单、待办、日志等数据，统计口径必须与现有权限模型保持一致，避免首页看见而列表页看不见，或反之。

## 8.3 旧接口兼容约束

- 现有列表接口继续保留，避免影响非首页页面。
- 首页切换到新接口后，不再新增任何“首页继续复用分页列表再聚合”的实现。
- 新旧接口并行期间，必须明确前端首页模块已经切换到哪一批新接口，避免一半新一半旧导致排查困难。

## 9. 注释与代码规范要求

### 9.1 总体要求

- 所有新增、修改或重构代码的注释统一使用简体中文。
- 所有新增类、接口、VO、DTO、Query、Mapper、Service、Controller 都必须补充完整类注释。
- 所有新增或修改的方法都必须补充完整方法注释。
- 方法内部关键业务步骤必须补充详细注释。
- 方法内部调用其它方法时，如果调用原因、业务目的或不调用的影响不够直观，必须在调用前补充注释说明原因和目的。

### 9.2 注释内容要求

- 类注释必须说明：
  - 业务职责
  - 适用范围
  - 与其它模块的关系
  - 是否属于首页专用聚合能力
- 方法注释必须说明：
  - 业务目的
  - 参数含义
  - 返回值含义
  - 核心处理流程
  - 权限或数据范围前提
  - 特殊兼容分支或异常场景
- 方法内部注释必须优先解释业务语义和设计意图，不能只翻译代码字面含义。

### 9.3 原有注释保护要求

- 开发过程中可以修改代码。
- 但不得为了方便阅读、压缩篇幅或个人习惯，随意删除未改动区域的原有注释。
- 如果代码逻辑改了，相关注释必须同步修改，确保实现与注释一致。
- 如果原有注释仍然准确，应直接保留，不得顺手清理。

## 10. 落地方式

由于本次仅改后端、前端由前端同事后续单独切换，因此本方案不再拆分多个开发阶段。

本次后端实施按“一次性交付后端能力，再配合联调验收”的方式推进即可。

## 10.1 后端一次性交付范围

目标：

- 新增三个 Dashboard Controller。
- 新增三个 Dashboard Service。
- 补齐首页专用 VO、必要的 Query、必要的 Mapper 聚合查询。
- 完成现有稳定聚合能力复用与首页专用新聚合能力补齐。
- 保留旧列表接口，避免影响非首页页面。
- 完成后端自测、自校验和接口文档说明。

交付要求：

- 三个主体的 `home` 接口均能返回最终确认结构。
- 所有首页统计均由后端聚合完成，不再依赖前端分页截断聚合。
- 首页专用字段语义明确，不继续沿用模糊旧命名。
- 注释完整，且与实现逻辑保持一致。

## 10.2 联调与验收配合说明

- 前端切换不在本次后端开发线程内实施。
- 后端交付完成后，由前端同事按本文档接口结构对接。
- 如联调时发现字段命名、空值约定、排序规则或统计口径需要微调，可在不改变已确认总体方案的前提下做小范围修正。
- 如联调时发现需要新增主体、改分流规则或扩大到前端页面重构，则应重新确认范围，不按本方案静默扩展。

## 11. 验收清单

- 是否已新增 `PlatformDashboardController`、`HqDashboardController`、`ServiceDashboardController`
- 是否已为三个主体提供首页专用 `home` 接口
- 是否已在后端侧提供完整首页聚合结果，不再要求前端使用分页列表接口自行拼装首页趋势统计
- 是否已明确“消息数”为“历史待办数”
- 是否已确认“待办数”口径包含已读未处理
- 是否已固定趋势窗口为最近 7 天
- 是否已保留总部首页网点汇总与排行
- 是否已保证平台首页仅展示治理类统计
- 是否已补齐新增和修改代码的中文详细注释
- 是否已避免删除未改动区域的原有注释

## 12. 风险与注意事项

- 如果后续业务又要求按 `currentTypeCode` 继续拆首页，则属于新范围，必须单独确认，不应直接在本方案基础上静默扩展。
- 如果首页统计口径与现有列表页权限口径不一致，优先修正后端聚合查询，不允许前端“看起来差不多”地兜底。
- 如果平台、总部、服务主体后续字段差异持续扩大，应继续坚持 Controller 和 Service 按主体分离，避免重新混回一个总接口。
- 如果联调时发现旧字段文案仍与新口径不匹配，应优先修正文案和字段命名，不应继续沿用含糊概念。
- 如果前端同事后续切换过程中提出额外页面交互诉求，应单独评估，不应回流成本次后端方案的范围膨胀。

## 13. 最终结论

- 本次首页统计重构采用“按主体拆 Controller、按主体拆 Service、首页统一改为专用总览接口”的方案。
- 现有稳定聚合能力继续复用，现有分页列表能力仅回归列表页用途。
- 本次仅实施后端改造，不再拆分多个开发阶段，按一次性交付后端能力的方式推进。
- 后续新线程开发、联调、验收，统一以本文档作为实施基线。
